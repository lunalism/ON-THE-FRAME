# 실험 계획 — ON THE FRAME

> **상태: 제안(P-006), 미승인.** 이 문서의 단계 구성, fixture, 측정 방법, 판정 기준, 구조 제안은 모두 실험용 제안이며 제품 사양이나 확정 결정이 아니다. 각 단계의 착수는 소유자 승인이 필요하다.
>
> - **진행 상황(2026-10-10):** E1-a(A-001)와 E1-b(A-002)를 작업 승인([DECISIONS.md](DECISIONS.md) §2.1)에 따라 실행했다. E1-b는 소유자 관찰에서 프리뷰 화면이 검어 실제 시각 표시가 실패했고, 원인(빈 비디오 트랙)을 고쳤다. 수정된 창은 소유자 재확인에서 정성적으로 통과했고(2026-10-10), 낮은 부하의 재생 재검사에서 프레임 누락이 재현되지 않았다. 소유자가 끝 프레임 유지(D-018)와 E1 완료 기준을 정했고 끝 프레임 유지를 구현했다. 끝 프레임 소유자 재확인도 정성적 통과해 **E1 완료(2026-10-10, 시험한 Mac의 짧은 FHD 통합 실험에 한함)**. 높은 부하의 프레임 누락은 E1 차단 요소가 아닌 안정화·성능 후속 과제다. 결과와 한계는 [experiments/e1-fhd/README.md](../experiments/e1-fhd/README.md)에 있다.
> - **E2(A-003, 2026-10-10):** E2(짧은 4K 컷 편집, A-003)를 구현·실행했다(2026-10-10): 헤드리스 검사는 모두 통과했다. 프리뷰 재생 시작 시 소스 프레임이 어긋나던 현상(직전 소스 버퍼 재전달 관찰)은 프레임 타이밍 변경 뒤 원래 조건에서 나타나지 않았지만, 변경 뒤 1회 관찰된 소스 프레임 불일치가 재현되지 않아 해결되지 않았다. 소유자 화면 관찰은 정성적 통과로 보고되었지만(2026-10-10) 이 정확도 결함을 해소하지 않으므로 E2는 완료가 아니다. 4K 제품 지원·3시간 지원을 입증하지 않는다. 작업 승인 A-003이 정한 범위(최종 타임라인 10초 등)는 아래 §6의 더 넓은 제안과 다르다. 10초는 승인 범위이며 계획에서 임의로 줄인 것이 아니다([experiments/e2-4k/README.md](../experiments/e2-4k/README.md) §7). E3는 승인되지 않았다.
>

## 3. 공통 조건

### 3.1 측정 환경

- 개발 기기 1대: macOS 26.6.2, Apple M2, 메모리 16GB, Xcode 27.0 ([ENVIRONMENT.md](ENVIRONMENT.md)).
- 디스크 여유 공간(2026-10-09 관찰): 저장소가 있는 데이터 볼륨 약 271GiB, 시스템 볼륨 약 25GiB ([ENVIRONMENT.md](ENVIRONMENT.md)). 시스템 볼륨의 여유 공간이 작으므로 큰 임시 파일과 캐시는 시스템 기본 임시 디렉터리가 아니라 **출력 대상과 같은 볼륨**에 둔다(TECHNOLOGY-EVALUATION §3.5.1의 제안과 같음).
- Release 빌드, 전원 연결, 다른 무거운 작업 없음. 결과는 다른 기기·OS로 일반화하지 않는다.

### 3.2 측정 도구 (설치 없음)

이 기기에 있는 기본 도구만 쓴다(존재 여부만 확인, 사용법 검증은 실험 시).

| 측정 | 도구 후보 |
| --- | --- |
| 최대 메모리 | `/usr/bin/time -l` |
| 시간에 따른 메모리 | `/usr/bin/footprint` 또는 `vmmap --summary`를 주기적으로 실행, 또는 실험 코드 안에서 직접 기록 |
| 상세 프로파일링(필요 시) | Xcode에 포함된 `xctrace`(Instruments) |
| 파일 무결성 | `shasum -a 256` |
| 디스크 사용 | `df`, `du` |
| fixture 생성 | `afconvert`, `sips`, 또는 실험 코드(AVAssetWriter로 테스트 패턴 영상 생성) |

### 3.3 공통 fixture 원칙

- 기본 fixture는 **합성(synthetic) 미디어**로 만든다. 영상에는 프레임 번호, 소스 ID, 주기적 플래시를 그려 넣고, 오디오에는 같은 시점의 클릭을 넣어 프레임 정확도와 A/V 동기화를 측정할 수 있게 한다.
- 생성 파라미터와 SHA-256을 기록한다. 미디어 파일은 저장소에 커밋하지 않는다.
- 소유자의 실제 촬영본·음원 사용은 선택 사항이며 소유자 승인이 필요하다(§8).

## 4. 메모리·디스크 구조 제안 (제안, 미승인)

T-01(3시간)과 T-02(4K)에서 메모리 사용이 "디코딩된 전체 프레임 수"나 "전체 오디오 샘플 수"에 비례해 늘지 않도록 다음 구조를 제안한다. 모두 [추론]이며 E1~E3에서 측정으로 확인한다.

### 4.1 내보내기: 제한된 버퍼링 (bounded buffering)

- **당겨오기(pull) 방식 파이프라인**: 디코딩 → 합성 → 인코딩을 프레임 단위로 흘리고, 인코더가 받을 준비가 될 때만 다음 프레임을 만든다.
  - [문서][SDK] `AVAssetWriterInput`의 `isReadyForMoreMediaData`와 `requestMediaDataWhenReady(on:using:)`는 비실시간 소스(예: `AVAssetReader`)를 쓸 때 입력이 준비되지 않으면 데이터 공급을 멈추라고 안내한다. 이 두 API는 macOS 27.0 SDK에서 deprecated로 표시되어 있고, 대체 API로 안내된 입력 receiver의 async `append`(`AVAssetWriter.inputPixelBufferReceiver(for:pixelBufferAttributes:)`)는 **macOS 26.0 이상**이다 [S23].
  - [추론] 목표 최소 macOS가 26보다 낮으면(P-004 제안은 14 또는 15) 가용성 분기로 두 방식을 함께 쓰거나, deprecated API를 유지해야 한다. 이것만으로 최소 macOS를 올릴 이유는 되지 않으며(TECHNOLOGY-EVALUATION §5.1 원칙), O-01 결정 시 함께 고려한다.
- **처리 중인 프레임 수 상한**: 합성 출력 버퍼를 `CVPixelBufferPool`(재사용 가능한 픽셀 버퍼 집합 [문서][S24])에서 받고, 동시에 처리 중인 프레임 수를 작은 상수로 제한한다. 상수 값은 실험 중 정하는 일반 구현 선택이다.
- **오디오**: 내보내기 오디오는 짧은 구간(예: 수백 ms~1초) 단위로 읽고 쓴다. 전체 PCM을 메모리에 올리지 않는다.
- [계산] 4K BGRA 프레임 1장 = 3840 × 2160 × 4바이트 ≈ 33.2MB. 처리 중 프레임을 8장으로 제한하면 합성 버퍼는 약 265MB다. 반대로 3시간 30fps(324,000프레임)를 메모리에 쌓는 구조는 불가능한 규모다. 따라서 상한은 필수다.

### 4.2 스펙트럼 분석 캐시

- **원본 미디어 단위 분석**: 선택 소스의 원본 파일을 스트리밍으로 읽어(짧은 구간 단위) FFT 결과(밴드 값)를 계산한다. 타임라인 배치와 무관하게 원본 시간 기준으로 저장하므로, 트림·이동 시 재분석 없이 TECHNOLOGY-EVALUATION §3.3.2의 대응식으로 조회한다.
- **디스크 캐시**: 분석 결과를 원본 파일 식별 정보(경로 북마크, 크기, 수정 시각 등)와 분석 파라미터(창 크기, 홉, 밴드 수)를 키로 하는 캐시 파일에 저장한다. 원본 미디어 파일 자체는 수정하지 않는다(R-40).
- **메모리 창(window)**: 메모리에는 현재 재생·내보내기 위치 주변의 고정 길이 구간(예: 앞뒤 수십 초)만 올리고, 나머지는 디스크에서 필요할 때 읽는다(LRU 등).
- [계산] 밴드 64개, 초당 60개 분석값, float32 기준 3시간 원본 1개 ≈ 64 × 4 × 60 × 10,800 ≈ 166MB(float16이면 약 83MB). 디스크에는 충분히 둘 수 있지만, 전부 메모리에 올릴 필요는 없다.
- 분석은 백그라운드로 진행하고 진행률을 기록한다. 내보내기는 필요한 구간의 분석이 끝났는지 확인한 뒤 진행한다.

### 4.3 기타

- **타임라인 모델**: 클립 수에 비례하는 메모리만 쓴다(프레임 수에 비례하지 않음).
- **자막**: 자막별 레이아웃 결과를 캐시한다. 크기는 자막 개수에 비례한다.
- **프리뷰 버퍼링**: `AVPlayer`의 내부 버퍼링은 앱이 직접 제어하지 않는다. 측정만 한다.
- **UI용 썸네일·파형**: 실험 범위 밖. 같은 원칙(디스크 캐시 + 메모리 창)을 적용할 것을 제안한다.

| 편집 구성 | 영상 소스를 트림·분할·이동해 컷 5~8개로 약 60초 타임라인 구성. S를 트림·오프셋해 배치. 영상 클립 자체 오디오는 **무관 오디오**로 취급(격리 검사, DR-09) |
| 출력 (실험용 제안) | 3840×2160, 30fps, SDR, 출력 코덱 H.264 또는 HEVC(소유자 선택. 기본 제안은 E1과 비교하기 쉬운 H.264), AAC + LPCM 대조. **4K60과 HDR은 다루지 않는다** |
| 검사 | 표준 검사 + 컷 경계 프레임 정확도(내보낸 프레임에 그려진 소스 ID·프레임 번호가 기대값과 일치), 컷별 A/V 동기화(플래시와 클릭), 영상 클립 오디오가 있을 때의 격리, 자막·스펙트럼의 4K 배치(위치·크기 지정 방식이 해상도에 따라 어떻게 변하는지 기록) |
| 탐색 검사 | 프리뷰에서 컷 경계, 타임라인 끝(마지막 프레임, 끝 1초 전, 끝을 넘는 위치)으로 탐색. 표시 프레임의 소스 ID·프레임 번호가 기대값인지, 탐색 응답 시간(기록만) |
| 측정 | 최대 메모리와 시간에 따른 메모리, 프리뷰 재생 중 드롭 프레임 수(기록만), 내보내기 시간, 출력·임시·캐시 디스크 사용량 |
| 완료 기준 | 모든 검사 결과와 측정값이 기록되었다. 4K에서 E1 대비 새로 발견된 제약이 정리되었다 |
| 진행 상황 | A-003으로 실행(2026-10-10). 승인 범위: 3840×2160, 30fps, SDR, H.264/AAC, 최종 타임라인 10초(이 표의 60초 제안보다 좁은 승인 범위). 구성: 소스 6~8초, 컷 4개, LPCM 대조 없음. 헤드리스 19/19 통과. 프리뷰 재생 시작 현상은 프레임 타이밍 변경으로 완화(관찰), 변경 뒤 1회 관찰된 소스 프레임 불일치는 해결되지 않음. 소유자 화면 관찰은 정성적 통과(자동 정확도 증거 아님). E2 미완료. 상세는 [experiments/e2-4k/README.md](../experiments/e2-4k/README.md) |
| 다음 단계 진행 조건 | 소유자 검토. 컷 경계·동기화·출력 보호에 해결되지 않은 불합격이 없다. 메모리 사용이 4.1의 상한 구조대로 동작한다는 근거(예: 길이가 다른 두 내보내기에서 최대 메모리 차이가 작음)가 있다. E3의 디스크 예산이 승인되었다 |

## 7. 단계 E3 — 길이 확대와 3시간 검증

### 7.1 단계

각 단계는 이전 단계의 진행 조건(§7.4)을 만족해야 시작한다.

| 하위 단계 | 해상도 | 길이 | 비고 |
| --- | --- | --- | --- |
| E3-1 | FHD | 10분 | 장시간 측정 방법 검증 |
| E3-2 | FHD | 60분 | |
| E3-3 | 4K | 10분 | |
| E3-4 | 4K | 60분 | |
| E3-5 | FHD | 3시간 | 프로젝트 저장/다시 열기 포함 |
| E3-6 | 4K | 3시간 | **복합 케이스**: 컷 편집, 다수 자막, 선택 소스 스펙트럼, 무관 오디오, 프리뷰 탐색, 내보내기, 취소·실패 검사. 이 케이스 통과 전에는 3시간·4K 지원을 주장하지 않는다 |

### 7.2 fixture (실험용 제안)

- **디스크 절약형**: 짧은 합성 소스 몇 개를 타임라인에서 반복 사용해 긴 타임라인을 만든다. 소스 디스크 사용은 작지만, 서로 다른 긴 원본을 많이 쓰는 실제 상황과 디코더 동작이 다를 수 있다.
- **실사용형**: 서로 다른 긴 원본(예: 30~60분 소스 여러 개)을 쓴다. 디스크 사용이 크므로 디스크 예산 승인이 필요하다.
- 선택 소스 S: 플레이리스트를 흉내 낸 3시간 오디오(곡 단위 구간 + 무음 간격 + 60초마다 클릭 마커).
- 자막: 곡 단위로 다수(예: 수십~수백 개) 배치.
- 영상: 일정 간격(예: 수 분)마다 컷, 영상 플래시와 오디오 클릭을 60초마다 맞춰 넣음.

### 7.3 검사와 측정

| 항목 | 방법 |
| --- | --- |
| 동기화 드리프트 | 내보낸 파일에서 60초마다 있는 마커마다 `n_obs − n_exp`(TECHNOLOGY-EVALUATION §6.4.3 정의)를 측정해 시간에 따른 변화를 기록. 오디오 클릭과 영상 플래시의 차이, 스펙트럼 반응과 클릭의 차이를 각각 기록 |
| 끝부분 탐색 | 타임라인 마지막 프레임, 끝 1초 전, 끝을 넘는 위치, 마지막 컷 경계로 탐색. 표시 프레임·자막·스펙트럼 값이 기대값인지, 응답 시간(기록만) |
| 메모리 증가 | 일정 간격으로 메모리를 기록. 워밍업 이후 구간에서 증가 추세(기울기)를 계산. 길이가 다른 단계 간 최대 메모리를 비교 |
| 디스크 사용 | 내보내기 전 여유 공간, 임시 파일 최대 크기, 분석 캐시 크기, 최종 출력 크기, 완료·취소 후 남은 파일 |
| 내보내기 시간 | 벽시계 시간과 실시간 대비 비율(기록만, 목표 없음 — O-09 미정) |
| 취소 | 진행률 초반·중반·후반(예: 5%, 50%, 95%)에서 취소. T_ack, T_stop, T_cleanup 측정, 큰 임시 파일 정리 확인 |
| 실패 정리 | 쓰기 불가 경로, 내보내기 중 원본 접근 불가(이름 변경), 디스크 부족. 디스크 부족은 작은 디스크 이미지(`hdiutil`로 생성)를 출력 대상으로 써서 시뮬레이션하는 것을 제안(소유자 승인 필요) |
| 기존 출력 보호 | 큰 기존 파일이 있는 경로에 대해 덮어쓰기 거부·승인 후 취소·실패를 실행하고 SHA-256으로 보존 확인 |
| 원본 보호 | 모든 케이스 전후 원본 fixture SHA-256 비교 |
| 프로젝트 저장/열기 | 3시간 프로젝트 저장·다시 열기 시간과 결과 동일성(E3-5, E3-6) |

### 7.4 진행 조건과 판정 기준 (실험용 제안)

| 항목 | 제안 기준 |
| --- | --- |
| 동기화 드리프트 | 모든 마커에서 `|n_obs − n_exp| ≤ 1`, 시간에 따라 한 방향으로 누적되는 경향이 없음 |
| 메모리 | 워밍업 이후 증가 추세가 길이에 비례하지 않음(구체적 허용 기울기는 E1·E2 측정 후 제안). 최대 메모리가 기기 메모리(16GB)에 근접하지 않음 |
| 디스크 사전 확인 | 시작 전 여유 공간 ≥ (예상 출력 + 예상 임시 + 캐시) × 1.5 |
| 끝부분 탐색 | 모든 탐색에서 기대 프레임 표시, 오류 없음 |
| 취소·실패·출력 보호 | TECHNOLOGY-EVALUATION §6.4.4 항목 모두 충족. T_stop + T_cleanup 1초 기준은 실험용 제안이며, 큰 파일 정리에 시간이 더 걸리면 측정값을 보고하고 기준 재검토를 제안 |
| 다음 하위 단계 진행 | 위 기준 충족 + 결과 기록 + 60분 이상 실행은 소유자 승인 |

### 7.5 디스크 용량 계산 (가정)

[계산] 비트레이트는 가정값이며 코덱·품질 결정(O-03, O-04)이 아니다.

| 경우 | 가정 비트레이트 | 3시간(10,800초) 출력 크기 |
| --- | --- | --- |
| FHD | 10 Mbps | 약 13.5GB |
| 4K | 40 Mbps | 약 54GB |
| 4K | 80 Mbps | 약 108GB |

임시 출력이 최종 출력과 같은 크기라면 승격 전까지 같은 볼륨에 그만큼 공간이 필요하다(이동은 같은 볼륨에서 복사 없이 이뤄질 것으로 예상 [추론]). 실사용형 fixture를 쓰면 원본 크기가 더해진다. 데이터 볼륨 여유 공간 약 271GiB(관찰값) 안에서 가능해 보이지만, 실제 크기는 측정 전까지 알 수 없다.

## 8. 승인 구분

승인은 **단계(작업) 승인**과 **제품 정책 결정**을 구분한다. 단계가 승인되면 그 단계 안의 일상적 설정은 따로 승인받지 않는다.

### 8.1 소유자 승인이 필요한 것

- **단계 착수**: E1-a, E1-b, E2, E3 및 E3의 각 하위 단계. 착수 시 [CLAUDE.md](../CLAUDE.md) 단계 규칙을 승인 범위에 맞게 갱신한다.
- **큰 자원을 쓰는 실행**: 단계 승인에 적힌 디스크·시간 범위를 넘는 실행, 60분 이상 내보내기, 장시간 기기 점유, E3 디스크 예산(실사용형 fixture 포함), 디스크 이미지 생성·마운트를 통한 디스크 부족 시뮬레이션.
- **제품 정책 결정**: 실험 기준을 제품 기준(O-09, O-11)으로 채택, 출력 코덱·해상도·프레임레이트·색 처리 정책(O-03, O-04), 방식 A에서 B로의 전환(P-003), 최소 macOS·CPU(O-01).
- **외부 자료·저장소 조작**: 소유자의 실제 촬영본·음원을 fixture로 쓰는 것, 도구 설치, 실험 코드·결과의 commit·push·merge, 실험 산출물 범위를 넘는 저장소 설정 변경.

### 8.2 승인된 단계 안에서 Claude Code가 정하는 것

승인된 단계의 범위(해상도, 길이, 디스크 상한 등 승인에 적힌 조건) 안이라면 다음은 Claude Code가 정하고 결과에 기록한다. 이 값들은 실험 설정이며 제품 한계·사양이 아니다.

- 실험 fixture 설정: 패턴 디자인, 톤 주파수, 마커 간격, 자막 문구·폰트·위치, 밴드 수 범위 안의 배치, 출력 비트레이트 같은 인코더 세부 값
- 실험 코드의 구조, 파일 배치, 이름, Swift package와 Xcode 프로젝트 중 선택(실험 디렉터리 안에 한함)
- 버퍼 풀 크기, 처리 중 프레임 수 상한, 오디오 청크 길이
- 분석 캐시의 청크 크기·파일 형식·메모리 창 길이, FFT 창 크기·홉·창 정렬
- 측정 샘플링 간격, 로그 형식, 반복 횟수, 판정 허용치(제품 기준이 아님을 표시)
- 임시 파일 이름과 위치(출력 대상과 같은 볼륨 원칙 안에서), 생성 산출물에 한정한 무시 규칙

판단이 애매하거나 제품 정책처럼 보이면 승인 필요 항목으로 취급한다.
