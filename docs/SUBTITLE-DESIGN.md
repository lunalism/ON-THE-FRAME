# 자막 설계 검토 — ON THE FRAME

> **상태: 제안(소유자 미승인), 2026-10-12 작성.** 기준 커밋 `de9be25`(브랜치 `chore/pre-subtitle-stabilization`). 구현·프로젝트 형식 변경은 하지 않았다.
> 대상: R-20(직접 입력), R-21(타이밍·글꼴·크기·색·정렬·위치), R-30(프리뷰·내보내기 일치), T 도구(D-027·D-028), 파생 요구사항 DR-02(실행 취소)·DR-07(한글 표시, 소유자 미승인).
> 소유자 지시(2026-10-12)로 한국어·일본어·영어·여러 줄 글자, 저장·다시 열기, 실행 취소·다시 실행을 범위에 넣는다. 자동 받아쓰기·고급 애니메이션은 나중 확장이다.
>
> 표시: **[확인]** 지금 저장소에서 읽어 확인한 사실, **[이전 기록]** 앞서 보고된 실험·검증 기록, **[제안]** 이 문서의 제안(미승인), **[미정]** 소유자 결정이 필요한 것.

## 1. 지금 구조에서 확인한 것

- **모델 [확인]**
  - `Clip`은 모두 `mediaID`·`sourceIn`이 있고 원본 범위(`sourceOut ≤ mediaFrames`) 검사를 받는다(`Timeline.swift` 7–42, 426–447). 미디어가 없는 글자 항목은 `Clip`에 맞지 않는다.
  - 레인 종류는 `video`·`audio`뿐이다(`Timeline.swift:231`, 자막·스펙트럼은 나중에 넣는다는 주석).
  - 두 종류만 가정하는 곳:
    - 두 클립 배열, 리플 편집의 `shifted`/`crossing`
    - `isValid`의 레인 순서·종류별 1개 이상 규칙, `laneLabel`·`pairedLane`
    - 붙여넣기 반복, `ProjectFile` 버전 2 이상의 레인 종류 집합 검사(`Set(kinds) == [.video, .audio]`, `ProjectFile.swift:96`)
    - 앱 쪽 비교 약 40곳
  - `durationFrames`는 두 배열의 끝과 저장된 길이로 정한다(351–366).
- **기록 [확인]:** 실행 취소는 타임라인 전체 스냅숏이다(`EditHistory`, 864–920). 끌기 하나가 한 단계다.
- **형식 [확인]**
  - 현재 형식 5, 형식 1–5 읽기다. 더 새 버전은 `newerVersion`으로 열지 않는다.
  - 모르는 키는 조용히 무시된다. 그래서 스키마를 바꿀 때마다 버전을 올렸다(D-023).
  - 저장은 임시 파일에 쓰고 다시 읽어 `== timeline`을 확인한 뒤 바꿔치기한다(`ProjectStore.writeProject`, 1620–1672). 실패하면 기존 파일을 그대로 둔다. 새 필드는 저장·읽기에서 정확히 같아야 한다.
- **렌더링 [확인]**
  - 프리뷰(`AVPlayerItem`)와 내보내기(`AVAssetExportSession`)는 같은 `CompositionPlanner.plan` 결과를 쓴다. 기본 합성기와 레이어 지시(변형)를 쓰고, 사용자 정의 합성기는 없다.
  - 끌기 중 정지 화면(`InteractivePreview`)은 따로 그리는 표시 전용 경로다.
  - 내보내기 확인은 영상 트랙 1개, 길이, 소리 트랙 수다(`ExportService.swift` 154–163).
- **실험 [이전 기록]**
  - E1: 사용자 정의 합성기 + CoreText 한 줄 자막. 합성기 출력이 오프라인·`AVPlayer` 재생 모두 직접 그린 것과 비트 단위로 같았다. 자막 경계 프레임 59/60/239/240도 일치했다(`experiments/e1-fhd/README.md`).
  - E2: 실제 원본 프레임 위에 자막을 그렸다(한 줄 `CTLine`, 줄바꿈 없음). 사용자 정의 합성기가 원본 프레임을 잘못 받는 문제가 미해결로 남았다(`experiments/e2-4k/README.md`).
  - 엔진 제품 타깃은 E2Core에 기대지 않는다(`Package.swift`).
- **입력 [확인]**
  - V·C는 물리 키 코드(9·8)로 도구만 바꾼다(D-030).
  - 텍스트 입력 중(`NSText`가 첫 응답자)이면 편집기 단축키를 처리하지 않는다. ⌘Z/⇧⌘Z는 텍스트 실행 취소로 넘긴다(`KeyRouting.swift`).
  - 편집 메뉴는 붙여넣기 그룹을 바꿔 "붙여넣고 스타일 맞추기"·표준 "삭제"가 없다(CP-07).

## 2. 권하는 사용자 흐름 [제안]

1. **T = 텍스트 도구 고르기만 한다(D-027·D-030과 같은 방식).**
   - 수정 키 없는 T(물리 키 코드 17, 한국어 입력 소스의 ㅅ 포함)로 바꾼다. 툴바 세 번째 단추, 타임라인 메뉴 "텍스트 도구 T"로도 바꾼다.
   - T를 누른다고 자막이 생기지 않는다. 같은 키를 다시 누르거나 반복해도 그대로다. 끌기 중·텍스트 입력 중에는 바꾸지 않는다. 프로젝트에 저장하지 않는다.
2. **만들기:** 텍스트 도구로 자막 레인의 빈 곳을 누르면 그 프레임(가장 가까운 프레임, 붙음 없음)에 기본 길이의 자막이 생긴다.
   - 실행 취소 한 단계이고, 새 자막이 선택된다.
   - 왼쪽 "클립 조정" 탭의 글 칸에 초점이 가서 바로 입력한다.
   - 자막 레인이 없으면, 타임라인의 영상 레인 위 빈 곳을 눌러 자막 레인 "S1"과 자막을 한 단계로 만든다.
   - 메뉴 "자막 추가"(기본 단축키 없음)는 어느 도구에서든 재생 헤드에 같은 방식으로 만든다.
3. **고치기:** 텍스트 도구로 기존 자막을 누르면 고르고 글 칸에 초점을 준다. 선택 도구로는 보통 클립처럼 고르고 옮기고 트림한다(§5).
4. **모양:** 왼쪽 패널에서 글꼴·크기·색·정렬·위치(X·Y)를 숫자·선택으로 바꾼다. 선택 도구로 프리뷰의 자막 상자를 끌어 옮긴다(한 단계, Esc 취소, D-031).
5. **확인:** 프리뷰 재생과 내보내기가 같은 모양·같은 프레임 구간을 보인다(R-30).

## 3. 모델 [제안]

- **자막 레인 + 미디어 없는 자막 항목.**
  - `LaneKind.subtitle`과 `Timeline.subtitles: [SubtitleItem]`을 둔다.
  - `SubtitleItem { id, lane, start, length, text, style }`. 시각은 정수 프레임이다(D-023).
  - 링크·원본 구간은 없다.
- **고른 까닭:**
  - `Clip`에 넣으면 미디어 필드와 원본 검사를 모두 예외 처리해야 한다.
  - 전체에 자막 트랙 하나만 두면, 같은 시각에 제목과 가사처럼 두 자막을 함께 띄울 수 없다.
  - 레인 여러 개(같은 레인 안 겹침 금지)는 D-024의 규칙을 그대로 쓴다.
- **레인 규칙:**
  - 자막 레인은 모든 영상 레인 위에 둔다(목록 맨 위). 영상 위에 그리고, 위 자막 레인이 아래 자막 레인 위에 그린다.
  - 자막 레인은 0개여도 된다. 영상·소리 레인의 "1개 이상" 규칙은 그대로다.
  - 레인 이름 표시는 S1, S2…(바깥쪽으로 번호가 커짐)다.
- **시각:**
  - 반 열린 구간 `[start, start + length)`이다. 영상 클립·E1/E2 자막과 같다.
  - 최소 길이는 1프레임이다.
  - 끝 프레임 유지(D-018)는 그 프레임의 자막 상태를 그대로 보인다.
- **기본 길이 [미정]:** 제안 3초(90프레임). 같은 레인 다음 항목에 닿으면 그 앞까지 줄인다. 1프레임도 들어가지 않으면 거부하고 이유를 보인다.
- **영상 끝을 넘는 자막 [미정]:** 제안은 지금 `placing`처럼 타임라인 길이를 늘리는 것이다.
  - 영상이 없는 구간은 기존 규칙대로 검정 위에 자막을 그린다.
  - 내보내기의 "영상 원본 하나 이상" 조건은 그대로다.
- **글자:**
  - 입력한 그대로 저장하고, 줄바꿈은 `\n`이다.
  - 빈 글자로 확정하면 바꾸지 않고 이전 값으로 돌아간다(레인 이름과 같은 방식). 글자 수 제한은 두지 않는다.
- **스타일**(모두 정수, 저장·읽기에서 정확히 같게):
  - `fontName`: PostScript 이름
  - `fontSize`: 출력 1080p 기준 포인트 × 10
  - `color`: RGBA 0–255
  - `alignment`: left·center·right
  - `position`: 출력 픽셀 1/1000 정수, `ClipTransform`과 같은 좌표계(왼쪽 위 원점, 1920×1080)
  - 배경 상자·외곽선·그림자는 R-21에 없다 [미정]. 첫 구현은 글자색만 두고, 넣을지는 소유자가 정한다.

## 4. 텍스트 편집·초점·IME·실행 취소 [제안]

- **글 칸:** 왼쪽 패널의 여러 줄 글 칸(AppKit `NSTextView` 감싸기)을 쓴다.
- **키:**
  - Return은 줄바꿈이다.
  - 확정은 초점이 떠날 때와 ⌘Return이다. 확정 하나가 타임라인 실행 취소 한 단계다.
  - Esc는 편집을 시작한 때 값으로 되돌리고 초점을 놓는다.
- **IME:**
  - 조합 중(`hasMarkedText`)인 Return·Esc·방향 키는 입력기 몫이다. 확정·취소로 쓰지 않는다.
  - 한국어 조합 중 초점이 떠나면, 조합을 끝낸 글자로 확정한다.
- **실행 취소 주인:**
  - 글 칸에 초점이 있으면 ⌘Z/⇧⌘Z는 글 칸의 텍스트 실행 취소다(지금 KeyRouting 규칙).
  - 확정 뒤에는 타임라인 기록이 맡는다. 확정할 때 글 칸의 실행 취소 기록을 비워 두 기록이 섞이지 않게 한다.
- **입력 중 프리뷰:** 입력하는 글자를 기록 없이 프리뷰에 바로 보일지 [미정]. 첫 단계는 확정 때 갱신을 제안한다.
- **편집기 단축키:** 텍스트 입력 중 V·C·T·Space·Delete·⌘C·⌘V는 글 칸 몫이다(지금 규칙 그대로).

## 5. 타임라인 편집 [제안]

- **기존 동작 재사용:** 선택·옮기기(같은 종류 레인 사이)·양쪽 트림·삭제(빈틈)·리플 삭제는 클립과 같은 규칙이다.
  - 리플 삭제·리플 트림·삽입은 자막 레인에도 적용한다. 걸치는 항목이 있으면 거부한다(D-024).
  - 일반 삭제는 다른 항목의 시각을 지킨다(D-020 비고).
- **자르기(⌘K·C 도구):** 두 조각 모두 같은 글자·스타일을 가진다.
- **복사·붙여넣기:** 앱 안 클립보드에 자막 항목을 넣고, 같은 레인 고르기 규칙(원래 레인 → 가까운 자막 레인 → 새 레인)으로 붙인다.
- **연결(⌘-클릭 연결)·트림 손잡이 페이드:** 자막에는 없다.
- **CP-08·CP-01 보호:** 누름 대기 지우기, 끌기 중 편집 막기는 자막 항목에도 같은 경로로 적용한다.

## 6. 위치·크기와 좌표 [제안]

- **1920×1080은 지금 제품 제약이다 [확인]**
  - 프로젝트 설정은 `RenderSettings.m1`(1920×1080, 30 fps)만 읽는다(`ProjectFile.decode`가 다른 설정을 거부).
  - 내보내기는 `AVAssetExportPreset1920x1080`이다.
  - 영상 변형(`ClipTransform`)도 이 출력 픽셀로 저장한다. 지금 다른 출력 크기는 없으므로 실제로 필요한 크기 조정은 없다.
- **자막 좌표는 이 출력 픽셀을 기준 좌표 공간으로 쓰자는 제안이다 [제안]**
  - 나중에 다른 출력 크기(예: 4K, 목표일 뿐 미지원)가 생기면, 위치·글자 크기·여백을 `출력 너비/1920`(같은 16:9) 배율로 늘린다.
  - 비율이 다른 출력은 그때 정한다. 영상 변형과 같은 규칙이어야 한다.
- **좌표:** 출력 1920×1080 픽셀이고, 프리뷰는 `PreviewOverlay`와 같은 배율 `k = min(w/1920, h/1080)`로 그린다.
  - 글자 크기 1 pt = 출력 1 px(1080p 기준)이다. 4K 출력이 생기면 출력 크기 비율로 늘린다(지금 출력은 FHD뿐).
- **위치:** 자막 상자의 기준점이다.
  - 가로는 정렬에 따라 왼쪽 끝·가운데·오른쪽 끝이고, 세로는 상자 아래 끝이다.
  - 기본 위치 [미정]: 제안은 가로 가운데, 아래에서 90 px.
- **줄바꿈 너비:** 출력 폭 − 좌우 여백(제안 각 96 px, [미정])이다. 넘으면 CoreText 규칙으로 자동 줄바꿈한다(한글은 어절, 일본어는 글자 단위, 영어는 단어). 직접 넣은 줄바꿈은 지킨다.
- **크기:** 프리뷰 모서리 끌기 크기 조절은 첫 구현에 넣지 않는다. 숫자로만 바꾼다(R-21 충족).

## 7. 글꼴 [제안]

- **저장:** PostScript 이름으로 저장한다(정확한 굵기·모양).
- **글꼴 목록:** 이 Mac에 설치된 글꼴 목록에서 고른다.
- **글자 대체:** 한 글꼴에 없는 글자(예: 한글 글꼴의 일본어 한자)는 CoreText 기본 대체 목록을 따른다. 레이아웃 검사가 대체된 글꼴과 빠진 글자(.notdef)를 기록한다(E1 방식).
- **글꼴이 없을 때(다른 Mac·삭제):**
  - 시스템 글꼴 같은 크기로 그린다.
  - 정보 패널과 내보내기 전에 "없는 글꼴" 경고를 보인다.
  - 파일의 글꼴 이름은 바꾸지 않는다. 글꼴을 다시 설치하면 원래대로 그린다.
  - 내보내기를 막을지 [미정]. 제안은 경고 뒤 허용이다.
- **기본 글꼴 [미정]:** 제안은 Apple SD Gothic Neo(E1·E2에서 쓴 글꼴). 일본어 가나·한자는 대체 글꼴로 그린다.
- **배포:** 글꼴을 파일에 넣지 않고 글자 모양만 영상에 그린다. 상업 배포 때 글꼴 이용 조건은 나중 질문이다(Q-14~Q-19 쪽, 막지 않음).

E1에서 화면 전체를 그리는 합성기 출력이 오프라인·재생 모두 같았다[이전 기록]. 이것은 같은 합성기 안의 일치일 뿐, 지금 기본 합성기와의 동등을 보이지 않는다(§13·§14). 끝 프레임 유지·정지 화면도 같은 함수를 쓴다. 스펙트럼(다음 기능)도 같은 자리에 들어간다. | 지금 기본 합성기가 하는 영상 쌓기를 다시 구현한다.   - `AVPlayerItem`이 애니메이션 도구를 받지 않는다는 점은 이번에 문서 본문으로 확인하지 못했다. 기존 지식이다.
  - 사용자 정의 합성기(`customVideoCompositorClass`)는 재생과 내보내기 모두에 쓸 수 있다.
- **제안 A의 안전장치:**
  - 자막을 그리기 전에, 새 합성기가 지금 기본 합성기와 같은 영상을 내는지(동등성) 먼저 증명한다(§10 S1).

  - 합성기·정지 화면·프리뷰 상자 잡기(hit-test)가 같은 레이아웃을 쓴다.

## 9. 형식 6과 호환 [제안]

- **형식 6:** 레인 종류 `subtitle`과 `subtitles` 배열을 더한다. 저장은 늘 6이다.
- **읽기:**
  - 형식 1–5 파일은 자막 없이 그대로 연다.
  - 형식 5 이하에 `subtitle` 레인이 있으면 잘못된 파일로 거부한다.
  - 레인 종류 검사(`ProjectFile.swift:96`)는 "영상·소리 각 1개 이상, 자막은 형식 6에서만 0개 이상"으로 바꾼다.
- **더 새 버전(7 이상):** 지금처럼 열지 않는다(`newerVersion`). 원본은 건드리지 않는다.
- **실패:** 저장은 지금처럼 임시 파일 → 다시 읽기 → 같음 확인 → 바꿔치기다. 실패하면 기존 파일 그대로, 저장하지 않은 상태로 남는다. 자막 값은 정수·문자열만 써서 다시 읽은 값이 정확히 같게 한다.
- **자막 없는 프로젝트의 저장 형식 [미정, 두 안]:**
  - (가) 늘 형식 6으로 쓴다(지금까지의 버전 올림과 같음). 단순하지만, 자막이 없는 프로젝트도 이전 앱에서 열리지 않게 된다.
  - (나) 자막 레인이 하나도 없으면 형식 5로 쓰고, 있을 때만 6으로 쓴다. 이전 앱 호환을 더 지키지만, 쓰는 형식이 내용에 따라 바뀐다.
    - 저장 확인이 형식별로 정확해야 한다.
    - 자막을 모두 지우고 저장하면 5로 내려간다. 이것을 사용자가 알아야 하는지도 정해야 한다.
  - 이 문서는 어느 쪽도 정하지 않는다.
- **[미정] 이전 버전 앱과의 호환:**
  - 형식 5 파일을 새 앱에서 열어 저장하면 형식 6이 되어 이전 앱에서 열리지 않는다. 지금까지의 버전 올림(2→5)도 같았다.
  - 그대로 둘지, 처음 저장할 때 한 번 알릴지는 소유자가 정한다.

## 12. 구현 전에 소유자가 정할 것

1. **렌더링 방식 A**: 사용자 정의 합성기 하나로 영상 + 자막. S1 동등성 증명 뒤 앱에 연결한다. 실패하면 B/C를 다시 검토한다.

   - 형식 5 파일을 저장하면 6으로 올라가 이전 앱에서 열리지 않는 것(지금까지와 같음)
3. **T와 만들기 흐름**:
   - T는 도구 고르기만 한다. 자막 레인 클릭으로 만들고, 레인이 없으면 S1을 함께 만든다. 메뉴 "자막 추가"는 재생 헤드에 만든다.

   - 모두 제안이다. 소유자가 정하거나 S5 전에 바꿀 수 있다.
5. **영상 끝을 넘는 자막·없는 글꼴**: 타임라인 길이를 늘리고 검정 위에 그림, 없는 글꼴은 대체·경고 뒤 내보내기 허용(제안).

## 13. S1 비교 계약(2026-10-12, 비교를 돌리기 전에 씀)

실험 합성기(`ExperimentalCompositor`, 엔진 안, 앱은 쓰지 않음)가 지금 기본 합성기와 같은 영상을 내는지 보는 기준이다. 결과를 보고 기준을 고르거나 넓히지 않는다.

**정확히 같아야 하는 것(하나라도 다르면 동등 아님):**

- 출력 크기 1920×1080, 프레임 수, 프레임 시각(1/30 s 격자)
- 프레임마다 보이는 원본과 원본 프레임(화면 코드 판정 `ExportJudge`, 섞인 fps 원본 포함), 레인 쌓음 순서, 빈틈(검정), 끝 빈틈, 마지막 프레임
- 변형된 레이어의 기하: 판 색 격자 판정(`OverlayJudge.judgeGrid`, 40 px 격자)과 경계 위치. 기본 합성기와 같은 픽셀 경계(반올림 규칙 포함)여야 한다.
- 회전 원본(`otf-rot90`)의 방향
- 실험 합성기가 받은 원본 프레임 시각이 요청 시각보다 미래가 아니어야 한다(E2의 "다음 프레임을 받음" 결함 검사)

**다를 수 있는 것(측정해서 기록하되 기준을 정하지 않음):**

- 화소 값: 두 합성기는 YCbCr → RGB 변환과 크기 조절 보간(필터)이 다를 수 있다. 같은 프레임의 화소 차이를 다음으로 잰다.
  - 화면 전체 PSNR, 최대 채널 차이, 다른 화소 수
  - 변형 경계 밖(판 안쪽)의 차이와 경계 근처의 차이를 따로 잰다
- 판정: 위의 정확 항목이 모두 같고 화소 차이가 "색 변환·보간 차이"의 모양일 때만 "같은 그림, 화소 차이 있음"으로 적는다. 즉 판 안쪽 평평한 곳의 차이가 작고 고르며, 차이가 경계에 몰려 있어야 한다.
  - 이 경우에도 "비트 단위 동등"이라고 하지 않는다.
  - 허용 수치는 이 단계에서 정하지 않는다. 측정값을 근거로 소유자 결정용 제안만 낸다.
- 회귀와 가르는 방법: 원본 프레임 하나 어긋남은 화면 코드가 다르다. 기하 어긋남은 격자·경계가 다르다. 레인 순서 오류는 격자 색이 다르다. 색 채널 바뀜은 판 색 분류가 다르다. 그래서 화소 차이만으로 판정하지 않는다.

**함께 볼 것:**

- 실험 합성기의 오프라인 렌더(`AVAssetReaderVideoCompositionOutput`) ↔ 같은 합성기의 `AVPlayer` 프리뷰 프레임 ↔ 같은 합성기로 내보낸 파일
  - 이 셋이 서로 맞는 것은 "실험 합성기 안의 일치"일 뿐이다. 기본 합성기와의 동등을 증명하지 않는다.
- A-010 엄격 검사(`InputCompatibilityTests`)는 기본 합성기 경로 그대로 돌린다(완화하지 않음).
- 취소(`cancelAllPendingVideoCompositionRequests`)와 동시 요청: 취소 뒤에 끝난 요청이 잘못된 프레임을 내지 않는다.

### 15.2 크기 조절 보간

- **비교 대상:** 세밀한 무늬 원본(1·2·4 px 줄무늬, 바둑판, 기울기, 평평한 칸)을 확대 1.5배·축소 40.05%·축소 75%로 놓고, 같은 오프라인 리더 버퍼로 기본과 비교했다(2화소 간격 표본).
- **결과:**

  | 보간 | 평평한 곳 평균 차이 | 세부 PSNR |
  | --- | --- | --- |
  | linear | 1.17–1.24 | 27.8–29.2 dB |
  | lanczos | 1.17–1.36 | 18.0–24.3 dB |
  | bicubic | 1.17–1.36 | 17.7–23.5 dB |
  | nearest | 1.18–1.25 | 14.8–16.4 dB |

  - linear가 셋 모두에서 가장 가까웠다.
- **표본 좌표 가설(반 화소 기준 차이):** 출력 공간에서 ±0.25·±0.5 화소를 옮기면 모두 더 나빠졌다(9.8–20.4 dB). 그래서 표본 위치 기준은 같고, **기본 합성기의 보간 필터 모양 자체가 다르다**(Core Image의 네 방식 어느 것과도 같지 않음).
- **결론:** 세부가 있는 곳의 차이(세부 PSNR 약 28–29 dB, 최대 60–69)는 해결하지 못했다.
  - 판·사진처럼 평평한 곳은 평균 약 1의 차이다.
  - 경계 보정 뒤 회전 원본은 내보낸 파일끼리 최대 1(PSNR 93 dB), 오프라인 최대 2였다.

### 15.3 오프라인 리더 색 차이(측정 경로 불일치, 미해결)

- 변형 시나리오에서 기본 합성기의 오프라인 출력 버퍼 색 첨부가 프레임마다 달랐다.
  - 프레임 0(맨 아래 1080p 파랑 판): BT.709
  - 프레임 60(맨 아래 640×480 빨강 판): SMPTE-C 원색·BT.601 행렬
  - 실험 합성기는 늘 BT.709다(맨 위 레이어에서 옮김).
- 비교는 색 첨부를 무시하고 RGB 값을 그대로 비교했다. 그래서 다른 색 공간의 값을 비교한 셈이다(초록 판 R 0 등).
- 두 합성기로 각각 내보낸 H.264는 같은 자리 색이 2 이내로 같다.
- 관찰은 두 번이다. 둘 다 "기본 합성기가 출력 색 공간을 맨 아래 레이어 원본에 맞춘다"와 맞지만, 그 규칙은 확인하지 않았다.
- SD(601)와 HD(709) 원본이 섞인 경우의 색 처리는 두 합성기가 다를 수 있는 남은 차이다.

### 16.1 소수 경계(배율·방향을 넓혀 가설별 측정)

- **방법:** 먼 쪽 가장자리 여유 δ(줄 위 마지막 화소 가운데 ↔ 원본 끝, 원본 화소)를 맞춘 20경우를 만들었다.
  - 초록 판: 원본 화소당 0.60·1.125·1.35 출력 화소 × δ 0.1·0.2·0.3·0.4
  - 표식 원본: 90°·180°·270° 회전·좌우 뒤집기 × δ 0.15·0.35, 원본 화소당 0.84·1.5
  - 기본 합성기의 네 가장자리를 다섯 가설과 맞췄다.
  - 표식은 그려진 화소 범위(밝기 > 8)로 쟀다. 밝기 가운데 지남으로 재면 흰·회색 사분면 경계에서 화소 안쪽에 떨어져 가설 판정이 틀린다(첫 실행에서 확인하고 고침).
- **결과(기본 합성기 가장자리 네 개가 모두 맞은 경우 수):**

  | 가설(먼 쪽 문턱) | 맞음 |
  | --- | --- |
  | 원본 0 | 10/20 |
  | 원본 0.125 | 13/20 |
  | **원본 0.25** | **20/20** |
  | 원본 0.375 | 13/20 |
  | 출력 0.25 px | 17/20 |

  - 원본 좌표 0.25 문턱은 §15.1의 0.20(그림)·0.25(안 그림) 측정과 함께 (0.20, 0.25] 안이다.
  - 방향이 바뀌어도(먼 쪽이 출력의 왼쪽·위로 가도) 원본 좌표 기준으로 맞았다.
- **계약:** 실험 합성기(기본 선택)는 20경우 모두 기본과 가장자리(0.15 px)·방향(사분면)이 같다. §15의 15경우 측정과 소수 경계 회귀 시험(X +401)도 그대로 통과한다.
- **한계:** 경험 규칙이며 Apple 문서로 확인하지 않았다. 축 정렬 변형만이다. 배율 0.60–1.5, 원본 640×360·1280×720에서만 쟀다.

### 16.2 크기 조절 차이(밝기·색차 나눔) — §15.2의 결론을 바로잡음

- **방법:**
  - 무늬 두 가지: 회색만(색차 일정) / 색 무늬
  - 경우 셋: 확대 1.5배 화면 가득, 축소 0.75(정수 사각형 240,135 1440×810), 축소 40.05% 소수 위치
  - 같은 오프라인 리더 BGRA 버퍼의 첫 표본(표시 시각 둘 다 0)
  - 출력 색 첨부: 이 경우들은 두 합성기 모두 BT.709
  - Y·Cb·Cr(BT.709 계수)을 레이어 안쪽 평평·세부, 레이어 가장자리 띠(3 px), 바깥으로 나눴다
- **결과(기본 대 실험 linear):**

  | 무늬 | 밝기 Y 차이 | 색차 차이 |
  | --- | --- | --- |
  | 회색 | 모든 영역 최대 2, 평균 0.3–0.9(세부 PSNR 50.5–51.3 dB) | 최대 0.5 |
  | 색 | 최대 1.6–3.9, 평균 0.4–0.7(세부 PSNR 51.0–51.8 dB) | 평평 평균 0.6(최대 2.3–20.7), **세부 최대 39–41, 평균 7.5–7.9** |

  - **밝기 보간은 기본과 사실상 같다(최대 2).** §15.2의 "세부 PSNR 28–29 dB, 필터 모양이 다르다"는 RGB 채널 최대 차이로 잰 것이며, 그 차이는 색 세부의 **색차** 처리에서 온다.
  - 가장자리 띠의 밝기 차이도 최대 2로 경계 덮음 차이는 없다. 색차는 색 무늬 경계에서 최대 5–18.
- **색차 가설 확인:**
  - 원본을 YCbCr 4:2:0으로 받아 Core Image가 RGB로 바꾸게 해도 색차 차이는 줄지 않았다(세부 최대 39–49, 평균 9.6–12.6).
  - VTPixelTransferSession 참조(기본·평균 축소 방식)는 두 합성기 어느 것과도 맞지 않았다(회색 세부 밝기 PSNR 20–31 dB). "기본 합성기가 VT 크기 조절을 쓴다"는 가설은 맞지 않는다.
  - 기본 합성기가 색차를 어떻게 보간하는지는 확인하지 못했다(미해결).
- **출력 색 고정:**
  - 두 videoComposition에 BT.709 색 속성을 주어도 이 경우들의 값은 같았다(이미 709).
  - SD 원본(640×480) 하나일 때:
    - 그대로 두면 두 합성기 모두 SMPTE-C/601 첨부, 같은 값(±1)이다.
    - 709로 고정하면 기본은 변환해 판 값에 가까워진다([40,41,219] 대 판 (220,40,40)).
    - 실험 합성기는 변환하지 않는다. 첨부도 원색 709·행렬 601로 섞인다. 제품은 색 속성을 두지 않으므로 지금 경로에는 해당하지 않지만, 색을 고정하게 되면 실험 합성기가 직접 변환해야 한다.

- **실행(새 프로세스마다 한 번):** 실험 frameDuration 7, 실험 원본 트랙 2, 기본 3. 결과는 모든 실행에서 같았다.
  - 준비 직후 항목 시각 520/600(프레임 26), E2 기록과 같다.
  - 표시된 프레임의 원본 코드: 모두 기대값과 같다(불일치 0). 받은 원본 movie time = 요청 시각: 301/301(어긋남 0), 미래·빠진 원본 0. E2의 "앞선 원본(A33)을 받음"은 재현되지 않았다.
  - **첫 재생에서 프레임 2가 요청되지 않는다(실험 9/9, 두 타이밍 구성 모두).**
    - 요청 차례는 26, 0, 0, 1, 3, 4…이고, 화면은 0, 1, 3으로 넘어간다.
    - 기본 합성기는 3/3 모두 프레임 2(A32)를 보였다.
    - 그리기 시간은 요청마다 2–7 ms(최대 약 11 ms)이고, t1과 t3 요청이 1 ms 안에 왔다. 그리기 지연이 아니라 AVFoundation이 사용자 정의 합성기에 요청을 만들 때 생기는 빠짐으로 보인다(추정).
    - 이것은 E2 실패 기록의 "프레임 2는 요청되지 않았다"와 같은 모양이다. 잘못된 원본은 없었지만, 프리뷰 재생 시작에서 기본보다 프레임 하나를 덜 보인다.
  - 요청 하나는 취소로 끝났다(탐색 앞의 t26으로 보임). 나머지 300개는 성공했다.
- **판단:** E2는 닫지 않는다(조건이 완전히 같지 않고, 원본 오류는 재현되지 않았을 뿐이다).

### 16.7 판정과 권고

- **기본 합성기와의 동등은 여전히 성립하지 않는다.** 남은 차이:
  - (1) **색 세부의 색차 보간.** 밝기는 최대 2로 같다. 색이 촘촘히 바뀌는 곳의 색차는 최대 약 40–49, 평균 약 8–13이고, 평평한 곳은 평균 약 0.6이다. 원인 미해결.
  - (2) **프리뷰 재생 시작에서 프레임 하나 빠짐.** 사용자 정의 합성기 경로에서 정확 탐색 뒤 재생할 때 일어난다(E2 조건 9/9). 합성기 안에서 고칠 수 없다: 요청이 오지 않는다. 내보내기·오프라인은 해당 없음.
  - (3) **섞인 색 공간의 출력 태그.** 내보낸 값은 3 이내다. 태그·규칙은 확인하지 않았다.
- **맞은 것:** 시각·원본 선택·쌓음·빈틈·방향·가장자리(경험 규칙, 측정 35경우 모두)·밝기 보간·첫 재생 원본·취소 처리.
- **권고(소유자 결정 필요, 미승인):**
  - **(가′) 겉모습 차이를 명시적으로 받아들이고 방식 A로 간다(이 문서의 권고).** 계약(§13)의 "화소"·"프리뷰 시작"을 다음처럼 새로 정하는 것을 소유자에게 묻는다.
    - 밝기 차이 ≤ 2
    - 색 세부의 색차 차이는 기록만
    - 프리뷰 재생 시작의 프레임 하나 빠짐은 받아들이고 소유자 화면 확인으로 본다
  - (나) 기본 합성기를 영상에 두고 자막만 다른 경로로 얹는다. 예: 방식 B(Core Animation).
    - (1)·(2)는 생기지 않는다.
    - 대신 프리뷰(AVSynchronizedLayer)와 내보내기(AVVideoCompositionCoreAnimationTool)가 다른 그리기 경로라 R-30(일치) 증명 부담이 생긴다.
  - (다) 색차 원인을 더 판다. 예: 기본 합성기 출력을 YCbCr로 직접 읽어 평면별로 비교. 기간을 정해 한 번 더 조사한다. 결과가 보장되지 않고 (2)는 남는다.
- S2(모델·형식 6)·S3(앱 연결)로 자동으로 넘어가지 않는다.
