## 0. 요약

- 전용 스펙트럼 레인의 독립 스펙트럼 클립(투명 배경)이 오디오 소스 하나를 **계보 키**로 참조한다. 자른 조각들은 같은 키를 이어받고(연결 유지), 복사본은 새 키다(독립).
- 분석은 그 키의 조각들이 가리키는 **원본 파일**을 원본 시각으로, 소스 클립의 클립 음량·페이드·음소거와 그 레인의 음량·음소거를 **표본마다** 곱한 뒤 한다. 다른 오디오나 전체 믹스는 넣지 않는다.
- 채널은 채널마다 FFT 한 뒤 **에너지를 평균**한다(L/R 평균 뒤 FFT는 반대 위상이 사라짐 — 측정).
- 프리뷰와 내보내기는 같은 분석 함수·같은 그리기 코드를 쓴다. 내보내기는 구조 R에 섞는다(영상 전체 BGRA 왕복 없음). 프리뷰는 디스플레이 링크 + 항목 시각(제안). SP-0 Debug 실험(§10): 멈춤·탐색 뒤는 실제 표시와 대체로 맞고 전환 때 1~2콜백 어긋남, 멈춘 뒤 영상 층이 한 프레임 앞을 보인 채 남는 경우가 있음(경계 직전 멈춤, fixture·실제 미디어 판별 범위에서 확인; 대책 미채택), 재생 중 실제 표시는 자동 확인 못 함 — 관문 G-P는 통과가 아님. 점검 정리 §10.19.
- 소유자 결정(2026-10-25): 같은 계보의 조각이 같은 시각에 겹치면 경고하고 대상 파일 전에 내보내기를 막는다(D-S8, §1.4). 프리뷰 통합을 진행하고 멈춘 뒤 표시 어긋남은 이 단계의 받아들인 한계(G-P 부분 확인). 막지 않는 결정: 두 색·부드러움의 뜻(D-S6, SP-2), 기본값 확정(D-S5). SP-1A 단계 계획·1단계 구현은 §15. 소리 계보 P-S1 (나) 승인(2026-10-25): 자르기는 스펙트럼 유무와 무관하게 늘 계보, 계보가 있으면 형식 8(§15.1).

## 1. 모델과 사용 흐름

### 1.1 레인과 그리기 순서

- **[승인]** 전용 스펙트럼 레인, 독립 스펙트럼 클립, 투명 배경(바탕 단색 층 없음). 합성 순서 **자막 > 스펙트럼 > 영상**.
- **[권고]** `LaneKind.spectrum`, 레인 순서(위 → 아래) = 자막 → 스펙트럼 → 영상 → 오디오. 스펙트럼 레인끼리는 위 레인이 위.
  - **[근거]** `isValid`(Timeline.swift:462-490)는 새 종류의 위치를 제약하지 않음 — 규칙을 더해야 함. `addingLane(outward:)`(:890), `laneLabel`(:410, 그 밖 = "S"), `pairedLane`(:413-417, 자막만 뺌), 앱의 "그 밖 = 자막" 삼항식(TimelineView.swift:313-316, ContentView.swift:696-737, 1054-1057)에 스펙트럼 갈래를 더해야 한다.

### 1.2 스펙트럼 클립

**[권고]** `SpectrumItem { id, lane, start, length, sourceKey: UUID?, style }`.
- `sourceKey`: 소스 오디오의 **계보 키**(§1.3). 파일 이름·목록 위치가 아니다 **[승인]**. nil = 아직 고르지 않음.
- 만들기: 오디오 클립(또는 연결된 영상의 소리)을 고른 채 "스펙트럼 추가" → 그 클립의 키를 소스로, 그 클립 구간 그대로. 아무것도 안 고르면 재생 헤드에서 5초, 소스 없음(§1.5).
- 편집 **[승인]**: 고르기·옮기기·트림·삭제·복사·붙여넣기·실행 취소/다시 실행을 자막과 같은 규칙으로. 스펙트럼 클립은 소스와 따로 움직인다(독립 클립).
- 스펙트럼 클립의 [start, start + length)는 **언제 보이는가**만 정한다. 그 안의 프레임 k에서 분석하는 소리는 같은 타임라인 시각(+ 오프셋, §2.4)에 그 키의 조각이 내는 소리다(DR-05). 그래서 소스를 옮기거나 트림해도 그 소리와 맞는다(R-12).

### 1.3 소스 연결 — 계보 키

**[승인]** 자른 소스의 조각들은 스펙트럼 연결을 유지한다. 복사한 오디오 클립은 독립이고 원래 소스에 조용히 붙지 않는다.

**[권고]** 오디오 클립에 저장되는 `origin: UUID?`(계보 키, nil이면 자기 ID가 키). 키 = `origin ?? id`.

| 소스에 한 일 | 계보 키 | 스펙트럼 |
|---|---|---|
| 자르기(몇 번이든) | 두 조각 모두 원래 키를 이어받음(`splitting`이 두 조각에 새 ID를 줘도 `origin`은 원래 키) | 모든 조각을 따라감, 원본 시각 그대로 |
| 옮기기·트림·재연결 | 그대로 | 따라감(조각의 지금 위치·원본 시작으로) |
| 복사·붙여넣기 | 새 클립은 새 키(`origin` = nil) | 원래 소스만 따름 |
| 스펙트럼만 복사·붙여넣기 | — | 같은 키 참조(같은 프로젝트 안) |
| 삭제(모든 조각) | 키의 조각이 0개 | 소스 없음(§1.5) |
| 실행 취소·다시 실행 | 스냅샷에 `origin`이 함께 있음 | 같은 ID·키로 되살아나 다시 이어짐 |
| 저장·다시 열기 | `origin`을 저장(형식 8) | 그대로 |

- 다른 클립에 자동으로 다시 붙지 않는다 **[승인]**.
- 소스 목록(§1.6)의 항목 하나 = 계보 하나. 고르면 키를 저장한다.

### 1.4 같은 계보의 조각이 겹칠 때

- 자른 조각을 다른 레인으로 옮겨 같은 시각에 둘 이상이 덮을 수 있다. 조용히 섞거나 아무거나 고르지 않는다 **[승인]**.
- **[권고]** 그 프레임은 "겹침" 상태: 스펙트럼을 그리지 않고, 타임라인 스펙트럼 클립의 그 구간에 경고, 정보 패널에 "같은 소스의 조각 2개가 겹침(레인 A1·A2, 00:00:03–00:00:07)". 내보내기는 **[결정 필요] D-S8**: (가) [권고] 소스 없음과 같이 이유를 보이며 거부, (나) 그 구간만 비워 내보내기.
- 겹치지 않는 구간은 그대로 그린다(시제품 시험 §9.A).

### 1.5 상태: 소스 없음 / 조각 없음 / 겹침

| 상태 | 뜻 | 그리기 | 내보내기 |
|---|---|---|---|
| 소스 없음 | 키가 nil이거나, 키의 조각이 하나도 없음(지워짐), 원본 파일을 찾을 수 없음 | 그리지 않음, 타임라인 경고 무늬·"소스 없음" | **[승인]** 어떤 스펙트럼(레인·시각)인지 밝히고 대상 파일을 건드리기 전에 거부 |

## 2. 오디오 분석

### 2.1 원칙

- **[근거]** 실험은 소스 파일만 `AVAssetReader`로 디코딩해 원본 시각으로 분석했고 통과했다. 재생 오디오를 두드리는 방식(`MTAudioProcessingTap`)은 플레이어 음소거 때 0이 들어왔다(e1-fhd README); Apple 문서도 그 결정성을 말하지 않는다. → **[권고]** 소스 파일을 직접 디코딩.

### 2.2 디코딩·표본 대응

- 분석 표본율 R은 고정(권고 48 kHz, 리더가 바꿔 줌). 프레임 ↔ 표본은 **프로젝트 fps와 R로 정수 계산**: `sample(k) = ⌊(2·k·R + fps) / (2·fps)⌋`(절반 올림). 48 kHz·30 fps에서만 1600/프레임으로 나누어떨어진다(44.1 kHz·30 fps = 1470, 44.1 kHz·24 fps = 1837.5 → 절반 올림 — 시제품 시험).
- 원본 시각 고정 격자 덩어리(권고 8초) + 앞뒤 여유(권고 1초)로 덩어리마다 새 리더를 쓴다. 같은 덩어리는 늘 같은 범위로 디코딩한다.
  - **[근거·측정]** AAC fixture(2500 Hz + 표본 20000의 클릭)에서 원본과 표본 어긋남 0, 덩어리(0.25초 + 0.05초 여유)로 읽은 것 = 한 번에 읽은 것(차이 0), 첫 버퍼 PTS 어긋남 0(이 Mac·이 OS). 다른 인코더·파일에서 같은지는 확인하지 않았다.

### 2.3 창 조립과 이득(표본 단계)

- 프레임 k의 창은 **타임라인 표본** [중심 − N/2, 중심 − N/2 + N), 중심 = sample(k) + 오프셋 표본. 각 타임라인 표본은 그 자리를 덮는 조각의 원본 표본(조각의 원본 시작 기준)으로 바꾼다 — 자른 곳(이웃한 두 조각)에서도 창이 끊기지 않는다. 덮는 조각이 없거나 원본 범위 밖이면 0.
- **[승인]** 소스 클립의 클립 음량·페이드·음소거와 그 레인의 음량·음소거를 반영한다. **[권고·근거]** 이득은 **표본마다** 곱한다: `이득(n) = 레인 이득 × 클립 이득 × 페이드 모양(클립 시각)`. 지금 내보내기·프리뷰 믹스가 쓰는 규칙과 같은 함수(`CompositionPlanner.clipRamps` = 레인 % × `ClipAudio.gain` × `ClipAudio.envelope`, 꺾이는 점 사이 직선)를 공유한다.
  - 최종 막대 높이에 이득을 곱하는 방식은 이득이 창 안에서 바뀌면(페이드) 맞지 않는다. 시제품: 페이드 시작 가장자리 프레임에서 두 방식이 다른 값을 냄(0.1722 대 0.1714).
  - AVFoundation이 오디오 믹스 경사를 표본마다 어떻게 보간하는지는 Apple 문서로 확인하지 않았다 — 같은 직선 식을 쓰지만 표본 단위 동일성은 미확인.

### 2.4 창·FFT·채널·밴드

- 분석 길이 D(ms) = 창 길이 N = D·R/1000, Hann 창, 0 채워 2의 거듭제곱 M(90 ms → 4320 → 8192). `vDSP.FFT`(실험·시제품) 또는 `vDSP.DiscreteFourierTransform`.
- 진폭 정규화: 진폭 A 사인 → 칸 값 A.
- **[권고·측정] 채널 결합:** 채널마다 파워 스펙트럼 → 채널 평균 → 제곱근(채널 에너지 평균). L = R이면 한 채널과 같고, 한쪽만 있으면 −3 dB, 반대 위상이면 사라지지 않는다. 시제품: 반대 위상 1000 Hz 진폭 0.2에서 에너지 결합 0.764(기대 0.767), L/R 평균 뒤 FFT는 0.0(완전히 사라짐), 한쪽만 0.717(−3 dB).
- **[승인] 로그 밴드:** 경계 `f_i = f_lo·(f_hi/f_lo)^(i/B)`, 밴드 값 = 경계 안 칸의 최댓값, 칸이 없는 좁은 밴드는 가운데 주파수에서 이웃 칸 선형 보간. 낮은 쪽 밴드는 창의 주파수 해상도(Hann 약 1.44/D Hz)보다 좁아 이웃 막대가 비슷하게 움직인다.
- 크기 → 높이: dB, 바닥 −60 dB ~ 0 dB를 0~1로, 높이 = 값 × 최대 높이.
- 시간 다듬기: 첫 단계는 없음(미룸). 결정적인 다듬기는 가능하다 — 그 프레임과 앞 고정 개수 프레임의 분석 값만으로 계산하면(같은 함수로 다시 계산) 탐색 순서와 무관하다. 넣을 때 계산 비용(프레임마다 앞 프레임 몇 개 더)을 재야 한다.

### 9.D 그리기·내보내기(시험 안 구조 R 차례, 제품 내보내기 코드 변경 없음)

- 프리뷰 프레임 선택: **직접 호출 흉내만** — 항목 시각 k/30 + δ(δ < 1/30)는 프레임 k를 고르고 그 분석 값은 내보내기와 같다. 실제 재생·디스플레이 링크는 확인하지 않았다.

### 10.2 방법

- fixture: 기존 생성 파일 otf-TA를 4번 이어 붙인 480프레임(1920×1080 30 fps). 화면 코드 = 원본 프레임 번호(16비트 칸), 움직이는 흰 상자(프레임마다 12 px), 소리는 440 Hz + 원본 프레임 30·50·75·100의 클릭. 스펙트럼은 기준선 y 960 위쪽만, 64밴드, 시제품 분석기(같은 원본 파일).
- 프레임 고르기(§3.2 제안 그대로): 재생 중이고 진행 중인 탐색이 없으면 `itemTime(forHostTime: targetTimestamp)` → `frame(containing:)`, 그 밖에는 화면에 나온 것으로 아는 프레임(자막 시간 창의 값: 완료한 마지막 탐색 또는 멈춘 재생 헤드). 분석은 뒤 큐 하나, 값이 없으면 비움, 재생 중 앞 12프레임 미리.
- 관찰: 디스플레이 링크 콜백마다(이 Mac 화면 약 120 Hz, 간격 중앙값 8 ms·99% 20 ms) 그 콜백에서 스펙트럼 층에 넣은 프레임의 원본 번호(타임라인으로 계산)와
  - **멈춤:** `AVPlayerLayer.displayedPixelBuffer()`의 화면 코드 = 이 층이 지금 표시하는 버퍼(실제 표시).
  - **재생:** 같은 항목 시각의 비디오 출력 버퍼 코드 = **대리**. 재생 중 실제 표시를 자동으로 볼 수단이 없다 — `displayedPixelBuffer`는 재생 중 nil(Apple 헤더), 화면 캡처는 화면 기록 권한을 바꾸지 않으므로 쓰지 않음, `CALayer.render(in:)`은 영상을 그리지 않는다.
- 허용 오차 0프레임. 비교 모형의 한계: 이 콜백에서 넣은 그림은 다음 화면 갱신에 나오고 표시 버퍼는 지금 값이라 ±1콜백(≈8 ms)은 모형에서도 생길 수 있다(앞 콜백 값과 비교하면 1차 실행 멈춤 불일치가 41 → 104로 늘어 같은 콜백 비교를 썼다).

### 10.11 컴파일 캐시 조사(2026-10-24, 빌드·삭제 없음)

- **로컬 관찰:** Xcode 27.1(27A9275), Apple Swift 6.4, Apple clang 21.0.0. 저장소·DerivedData 볼륨 `/Volumes/LunaData`는 **Journaled HFS+(외장 USB)**, 내부 디스크는 APFS. 남은 캐시 파일 세 개(15:09:43)는 크기 = 할당이며 내용은 거의 0이다. 지금 이 파일을 연 프로세스는 없다(lsof, 빌드 서비스 없음).
- **소스에 적힌 사실(Apple LLVM 포크 `swiftlang/llvm-project` next 브랜치와 상위 LLVM — Xcode 27.1에 든 정확한 판은 확인 못 함):** 온디스크 CAS 파일 이름은 `index.`·`data.`·`actions.` + 형식 판(`v1.x` 디렉터리). 최대 매핑 크기 기본값은 index 12 GiB·data 24 GiB·actions 1 GiB(관찰과 정확히 같음). 만들 때 파일을 최대 크기로 `resize_file_sparse`하며 macOS(Unix)에서는 `ftruncate`이고, 상위 LLVM 주석은 "공간을 할당할 수도 아닐 수도 있다 — 적어도 OS X HFS+에서는 할당한다"고 적는다. 실제 사용 공간은 1 MB씩 `F_PREALLOCATE`로 늘리고, 닫을 때 다른 프로세스가 쓰지 않으면 사용한 크기로 줄인다. 작은 매핑(1·2 GiB)은 tmpfs에서만 쓴다. `LLVM_CAS_MAX_MAPPING_SIZE` 환경 변수가 최대 매핑을 바꾼다(소스에만 있음).
- **Xcode 설정:** Xcode 안의 설정 정의(xcspec)에 설명이 있는 것은 `COMPILATION_CACHE_ENABLE_CACHING`(기본값 `$(COMPILATION_CACHE_ENABLE_CACHING_DEFAULT)`)과 진단 옵션뿐이다. `COMPILATION_CACHE_CAS_PATH`·`COMPILATION_CACHE_LIMIT_SIZE`·`COMPILATION_CACHE_LIMIT_PERCENT`·`COMPILATION_CACHE_KEEP_CAS_DIRECTORY` 등은 Swift Build 소스·바이너리에만 있고 Apple 공식 문서를 찾지 못했다. Apple 공식 문서에서 캐시 위치·크기 제어를 찾지 못했다.
- **해석(근거가 강한 가설):** HFS+에는 희소 파일이 없어 CAS를 처음 열 때 최대 크기 37 GiB가 그대로 할당된다. 정상 종료라면 닫을 때 줄어들었을 것이나(소스), 감시가 빌드를 죽여 줄지 않은 채 남은 것으로 보인다. 이전 정상 빌드가 28 KB만 남긴 이유(CAS를 열지 않았는지, 닫으며 줄였는지)는 확인하지 못했다. 명령줄 덮어쓰기는 원인이 아니다(기본 빌드에서도 일어남).
- **가장 작은 지원되는 대책(제안, 소유자 결정):** (가) [권고] DerivedData를 APFS 볼륨(내부 디스크)에 둔다 — `xcodebuild -derivedDataPath`는 문서화된 옵션이고 LLVM CAS가 가정하는 희소 파일이 된다. 산출물 위치 규칙(데이터 볼륨) 변경이라 승인이 필요하고, 예산 측정에 그 경로를 더한다. (나) HFS+에 두고 빌드마다 37 GiB 여유를 일시로 두며, 캐시 파일 생성만으로 빌드를 멈추지 않고, 끝난 뒤 줄었는지 잰다. 소스에만 있는 환경 변수·설정은 쓰지 않는다.

#### 대안 1: 재생 헤드·오버레이를 실제 표시 프레임에 맞춤(영상은 움직이지 않음)

- **필요한 정보:** 멈춘 뒤 표시 버퍼가 k인지 k+1인지. 위처럼 직접 주는 API가 없다. 가능한 추론: 표시 버퍼 내용을 k·k+1 기준 그림(같은 composition을 `AVAssetImageGenerator`로 정확한 시각에 그림, 또는 비디오 출력 버퍼)과 비교 — 내용 추론이며 공식 보장이 아니다. 이웃 프레임이 거의 같으면(정지 화면) 가릴 수 없다(그때는 어긋남도 보이지 않는다).
- **효과(맞힌 경우):** 재생 헤드·자막·스펙트럼 선택 = k+1 = 화면, 편집 시각도 k+1(화면에 보이는 것을 자르게 됨), 내보내기의 k+1 프레임 = 화면. 그러나 player 시각은 프레임 k 안(ta)에 남는다 — (가) 그대로 두면 재개 때 재생 헤드가 k+1 → k로 한 번 뒤로 갔다가 진행하고 소리는 ta에서 이어진다, (나) 맞춘 뒤 (k+1)/30으로 앞으로 정밀 탐색하면 모두 일치하나(층이 이미 k+1이라 화면 변화가 없을 것으로 예상 — 미확인) 재개가 프레임 경계에서 시작하고 탐색 한 번이 든다.
- **방해 경우:** 판정이 비동기(기준 그림 생성 수 ms–수십 ms)라 탐색 번호·항목 회차로 무효화해야 한다 — 그사이 재개·새 탐색·항목 교체가 있으면 버린다.
- **판정이 틀리거나 불확실하면:** 재생 헤드가 화면에 없는 프레임을 가리키거나((가)), 영상이 앞으로 한 칸 움직인다((나)) — 지금보다 나빠진다. 그래서 확실할 때만 맞추고 아니면 지금 동작으로 둔다. 판정 비용·오판율은 재지 않았다. 실제 소스에서 확인 필요.

#### 대안 2: 멈춤과 표시를 맞춰 어긋남을 처음부터 피함(멈춤 시점 조정)

- **생각:** 어긋남은 다음 경계 직전에 멈출 때만 났다. 멈춤 요청이 그 "위험 구간"에 들어오면 실제 `player.pause()`를 다음 경계를 조금 지난 시각까지(최대 위험 구간 + 여유, 지금 측정으로 약 10 ms 안팎) 미룬다 — 경계 관찰자 사용. 구간 밖이면 지금처럼 바로 멈춘다. 탐색은 하지 않는다.
- **필요한 정보:** 실행 중에는 프레임 정체가 필요 없다(player 시각과 경계 관찰자만). 대신 "어느 위상에서 멈추면 안전한가"를 미리 재야 하며 그것은 측정에 기댄 것이지 API 보장이 아니다. 화면 갱신율(120 Hz·60 Hz·가변)과 부하에 따라 달라질 수 있다(가설).
- **효과:** 편집 시각·자막·스펙트럼 = 멈춘 시각의 프레임 = (측정이 맞으면) 화면. 내보내기 일치는 지금 어긋나지 않는 회차와 같다. 소리는 미룬 만큼(약 10 ms 안팎) 더 나온 뒤 멈추고, 뒤로 가거나 다시 프리롤하지 않는다. 재개는 지금처럼 멈춘 시각에서(동작 변경 없음). 대가: 위험 구간에서 누른 멈춤이 그만큼 늦게 걸린다 — 그동안 UI를 바로 "멈춤"으로 보일지, 실제로 멈출 때 바꿀지 정해야 한다.
- **방해 경우:** 미룬 멈춤 중 재생 요청 → 미룬 멈춤 취소(계속 재생), 새 탐색·한 칸 이동 → 미룬 멈춤 취소하고 바로 멈춘 뒤 탐색(탐색 경로는 그대로), 항목 교체 → 관찰자 제거 후 바로 멈춤. 관찰자는 player에 붙으므로 항목이 바뀌면 반드시 지운다.
- **안전 구간이 확실하지 않으면:** 남는 어긋남은 지금과 같은 종류(나빠지지 않음)지만 제품에서는 알아챌 수 없다(정체를 모름). 실제 소스·다른 화면에서 다시 재야 한다.

#### 권고: 가장 작은 다음 실험(측정만, 제품 동작 변경 없음)

- **멈춤 위상 쓸기(Debug, 기존 시험 틀 재사용):** 경계 관찰자로 (n + φ)/30 s에 제품 `store.pause()`를 부른다. φ = 0.05 … 0.95(0.05 간격) + 경계 직전 촘촘히(경계 앞 0.5–10 ms). 위상마다 다섯 fixture에서 회차를 모아 실제 표시 버퍼 원본 번호(화면 코드) vs 멈춘 시각의 기대 원본으로 고정 어긋남 비율을 위상별로 그린다. 화면 갱신율(`NSScreen.maximumFramesPerSecond`, 디스플레이 링크 간격)을 함께 적는다. 화면 설정은 바꾸지 않는다.

- **채택하지 않은 것:** 멈춘 뒤 정밀 탐색(맞춤) — 소유자 결정(DECISIONS 2026-10-24). 미루는 멈춤 — 만들지 않았고 채택하지 않음(늦음 크기 미측정, 의도 처리 위험). 제품 재생 동작은 그대로다. Debug 실험 코드와 결과는 증거로 보존한다.
- **풀리지 않은 것:** 멈춘 뒤 한 프레임 앞 표시(원인 가설만), 재생 중 실제 표시 일치(자동 증명 없음), 탐색 전환 1~2콜백, 실제 미디어 판별이 회차의 약 절반에서 안 됨, 소리(자동 측정 없음), 다른 화면·갱신율·기계, F 23.976 자막 선택 없음 1회(제품 동작, 원인 미확인), 실험 코드 Sendable 경고 1개.
- **두 문제를 나눔:**
  - **멈춤·표시 문제**는 기존 제품 재생(영상 층과 player 시각)의 문제다. 스펙트럼이 없어도 재생 헤드·자막과 화면 영상 사이에 같은 어긋남이 생길 수 있다. 스펙트럼 프리뷰는 재생 헤드를 따르므로 이 문제를 물려받을 뿐 만들지 않는다.
  - **스펙트럼 분석 정확성**(어떤 소리 조각을 어떤 창·FFT·밴드로 분석해 타임라인 프레임 k의 값을 내는가)은 타임라인 프레임 번호의 함수이며 화면 표시와 무관하다. 시제품 시험(§9.B)이 이 쪽이다. 내보내기는 프레임 k를 정해진 시각에 그리므로 이 문제의 영향을 받지 않는다.
- **[권고] 독립적으로 진행해도 되는 것(작업 지시가 있을 때):**
  - SP-0 (3): 시제품 분석 함수·분석 일정을 제품 엔진 코드로 옮기고(앱 연결 없음) 분석 정확성 시험을 기본 실행 시험으로 — 프리뷰 타이밍과 독립.
  - 그 뒤 엔진 수준의 내보내기 그리기 경로(구조 R에 섞기, §3.3·§9.D)의 시험 — 프레임 k 기준이라 G-P와 독립. 단 제품 모델·형식 8·편집 동작(SP-1)은 D-S8 등 결정이 필요하다.
- **[권고] 막혀 있는 것:** 제품 프리뷰에 스펙트럼을 붙이는 통합(SP-1의 프리뷰 부분)과 그 방식 확정 — G-P가 부분 확인이라 소유자 결정 전까지 막는다. 결정 선택지(제안): (가) 지금 어긋남(경계 직전 멈춤 때 영상 층 한 프레임 앞)을 알려진 한계로 받아들이고 프리뷰 통합을 진행, (나) 기존 재생 문제를 따로 다룰 때까지 프리뷰 통합을 미룸.
- G-P: **부분 확인, 통과 아님.**

## 11. SP-0 (3) 제품 엔진 분석 부품(2026-10-24, 앱 연결 없음)

- **범위:** 시제품의 분석·디코딩·캐시·일정만 제품 엔진(`app/Engine/Sources/OnTheFrameEngine/`)으로 옮겼다.
  - 하지 않은 것: 앱 연결, 프리뷰·내보내기 연결, 저장 형식, 스펙트럼 레인·클립 모델·정보 패널, 재생 동작, 계보(소스 연결) 규칙.
  - 실험 그리기·멈춤 조사·비교 창은 Debug 실험 그대로 두었다(제품 코드에 넣지 않음).
  - 새 의존성은 없다(Accelerate·AVFoundation·os).
  - 앱 코드는 이 API를 부르지 않는다(확인).
- **API(`SpectrumAnalysis.swift`, `SpectrumAnalysisScheduler.swift`):**
  - `SpectrumFrameMap`: 프레임 ↔ 표본 정수 대응(절반 올림, 음수는 내림 나눗셈).
  - `SpectrumAnalysisSettings`: 창 ms·오프셋 ms·밴드 수·범위 Hz·dB 바닥.
    - `validationError(rate:)`: 창 2표본~1초, 밴드 1~1024, 0 < 낮은 끝 < 높은 끝 ≤ 나이퀴스트, 바닥 < 0, 오프셋 ±10초.
  - `SpectrumSourcePiece`: 타임라인 프레임 조각, 원본 시작, `ClipAudio`, 레인 배율.
    - `init(clip:lane:)`은 믹스 이득 규칙(`CompositionPlanner.gain(of:lane:atFrame:)`)과 같은 식이다(시험).
  - `SpectrumPCMProvider`(Sendable 규약): 정체·표본율·채널 수·덩어리 크기, `decodeChunk(_:) async throws`.
  - `SpectrumFileSource`: AVAssetReader로 덩어리 + 앞뒤 여유를 읽고 가운데만 쓴다. 채널 수는 열 때 정해 고정한다.
    - 정체 = 미디어 ID·경로·크기·수정 시각·표본율·덩어리·여유.
    - 트랙은 디코딩마다 asset에서 얻는다. `AVAssetTrack`은 SDK에서 Sendable로 표시되지 않아 공유 상태로 두지 않았고, `@unchecked`는 쓰지 않았다.
  - `SpectrumAnalysis.bands(frame:pieces:…:chunk:)`: 순수 계산(창 조립 → Hann·FFT → 채널 에너지 평균 → 로그 밴드 → dB 0~1).
    - `SpectrumAnalysis.chunks(…)`: 그 창이 읽는 덩어리.
  - `SpectrumAnalysisScheduler`:
    - `request(_:from:priority:completion:) -> SpectrumRequestID`, `cancel(_:)`, `cachedBands(_:from:)`, `bands(_:from:priority:) async throws`(작업 취소 → `.cancelled`), `invalidateSession()`, `statistics`.
    - 상한 `SpectrumSchedulerLimits`(기본: 기다림 8·동시 2·덩어리 캐시 32 MiB·밴드 캐시 600·끝나지 않은 호출 256 — 마지막은 §11.1에서 더함).
    - 오류 `SpectrumAnalysisError`: cancelled·dropped·invalidated·invalidSettings·invalidRequest·unsupportedChannelCount·overlappingPieces·noAudioTrack·decodeFailed(invalidRequest·unsupportedChannelCount는 §11.1).
- **캐시 열쇠:**
  - 밴드 = 원본 정체 + 프레임 + fps + 설정 + **그 창에 드는 조각**(위치·원본 시작·음량·음소거·페이드 길이·오프셋·레인 배율 비트). 창 밖 조각만 바뀌면 같은 열쇠다.
  - 덩어리 = 원본 정체 + 덩어리 번호(설정이 다른 스펙트럼도 같은 원본 덩어리를 나눔).
- **상한·수명:**
  - 기다리는 작업 상한: 넘치면 우선순위 값이 가장 큰 것을 `.dropped`로 버린다.
  - 동시 작업(디코딩 + 분석) 상한.
  - 덩어리 캐시 바이트 LRU(한 항목은 남김). 밴드 캐시 항목 LRU.
  - 같은 열쇠 요청은 한 작업으로 합치고, 같은 덩어리는 세션마다 한 번만 진행한다.
  - 모든 요청은 완료 큐에서 정확히 한 번 끝난다.
  - 취소: 기다리는 쪽이 없어진 미시작 작업은 버려 쥔 덩어리를 놓는다.
  - 세션 무효: 기다림을 `.invalidated`로 끝내고 캐시를 비운다. 그 전 작업은 끝나도 알리지 않고 캐시에 넣지 않는다.
  - 디코딩·FFT는 분리된 작업에서 돈다(주 스레드 아님, 가짜 원본으로 주 스레드 호출 0 확인).
  - 디코딩 실패는 `.decodeFailed`로 알리고 캐시하지 않는다(다시 시도).
- **옮기며 고친 시제품 가정·결함:**
  1. **[결함, 재현함]** 시제품 일정: 세션을 바꾼 뒤 같은 덩어리를 다시 요청하면, 이전 세션의 진행 중 디코딩을 기다리다 그 결과가 버려져 끝나지 않았다. 임시 검사(실행 뒤 지움)에서 3초 안에 끝나지 않음을 확인했다. → 진행 중 디코딩을 세션별로 구분했고, 회귀 검사를 더했다.
  2. 시제품은 디코딩 실패를 취소와 같은 nil로 알렸다 → 오류를 따로 알린다.
  3. 시제품은 창 안 겹친 조각 중 첫 것을 말없이 골랐다 → `.overlappingPieces` 오류로 바꿨다. 겹침 규칙(D-S8)은 정하지 않았다.
  4. 채널 수를 버퍼마다 정했다(파일 밖 덩어리는 1채널) → 열 때 고정한다. 다른 채널 수 버퍼는 오류다.
  5. 표본마다 사전 조회·LRU 갱신을 했다 → 덩어리 구간 복사로 바꿨다(같은 이득 식).
  6. 디코딩마다 asset을 다시 열고 세마포어로 비동기를 기다렸다 → 열 때 한 번, async 디코딩으로 바꿨다.
  7. 계산 객체를 잠금 없이 나눴다 → FFT 설정은 작업마다 새로, 상태는 잠금 하나 안에 두었다.

### 11.1 굳히기 검토(2026-10-24~25, 내보내기 그리기 전)

- **방법:** `SpectrumAnalysis.swift`·`SpectrumAnalysisScheduler.swift`와 그 시험을 코드로 다시 읽고, 의심 항목은 임시 시험(실행 뒤 지움)이나 변이 검사로 확인했다. 확인된 것만 고쳤다.
- **찾은 것(심각도순)과 고침:**
  1. **[높음, 확인]** 디코딩(동기 `AVAssetReader` 차례 읽기)이 Swift 협력 스레드에서 돌았다. `Task.detached`였고, 변이 검사에서 큐 이름이 `com.apple.root.user-initiated-qos.cooperative`로 나왔다. 협력 스레드 수는 한정되어 있어 다른 async 작업을 막을 수 있다.
     - 고침: 전용 작업 실행기 `SpectrumWorkExecutor`(`TaskExecutor`, 자기 동시 디스패치 큐)에서 `Task(executorPreference:)`로 디코딩·FFT를 돌린다. 동시 수는 그대로 `maxConcurrent`로 묶는다.
     - 시험: `testDecodesRunOnDedicatedWorkerQueue`. 되돌리는 변이에서 실패를 확인했다.
  2. **[높음, 시험 결함]** 앞 단계의 세션 교체 회귀 시험은 결함 있는 동작을 잡지 못했다. 이 설계에서는 늦은 결과가 진행 중 표시를 지운 뒤 다시 펌프해, 진행 중 디코딩을 덩어리만으로 구분해도 결국 끝났다.
     - 고침: `testNewSessionRequestDoesNotWaitForOldSessionDecode`. 이전 세션 디코딩이 취소를 보지 않고 끝나지 않을 때(동시 4) 새 세션 요청이 3초 안에 끝나야 한다.
     - 변이(진행 중 키에서 세션을 뺌)에서 3초 시간 초과로 실패, 원래 코드에서 통과를 확인했다.
  3. **[중간, 확인]** 세션을 무효로 해도 진행 중 디코딩 작업을 취소하지 않아, 끝날 때까지 동시 자리를 차지하고 새 세션을 늦췄다(상한은 유지됨).
     - 고침: 디코딩 작업 손잡이를 두고 무효 때 취소한다(작업 시작과 무효가 엇갈리면 바로 취소). 파일 원본은 버퍼마다 `Task.isCancelled`를 본다.
     - 시험: `testInvalidationCancelsInFlightDecodes`. 취소를 뺀 변이에서 실패했다.
     - 취소를 보지 않는 원본의 작업은 끝날 때까지 자리를 차지한다 — `statistics.retiredActive`로 보인다.
  4. **[중간, 코드로 확인]** 범위 밖 프레임·fps·조각 값(예: `Int.max`, `Int.min`)이 `2·k·R`·`abs` 등에서 넘쳐 프로세스를 멈출 수 있었다. 설정 검사에도 `highHz * 2`·`windowMs * rate`·`abs(offsetMs)` 넘침이 있었다.
     - 고침: `SpectrumAnalysis.requestError`(|프레임·조각| ≤ 2⁴⁰, fps 1~1000, 표본율 8 k~384 kHz, 레인 배율 유한·0 이상) → `.invalidRequest`. 설정 검사는 넘치지 않는 식으로 바꿨다.
     - 시험: `testOutOfRangeRequestsFailWithoutTrapping`.
  5. **[중간, 확인]** 3채널 이상을 에너지 평균으로 말없이 받았다(제품 가져오기 `MediaProbe`는 1~2채널만).
