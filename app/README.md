# ON THE FRAME 편집기 — M1

작업 승인: [A-005](../docs/DECISIONS.md)(2026-10-10). 계획: [docs/EDITOR-PLAN.md](../docs/EDITOR-PLAN.md).

**상태: M1 완료(2026-10-10).** 자동 검증과 소유자 최종 확인(정성)을 거쳐 [EDITOR-PLAN.md](../docs/EDITOR-PLAN.md) §3 완료 기준을 대조했다(§11). 완료는 이 문서의 M1 범위에 한한다: 입력은 30 fps 고정 간격 H.264·HEVC 영상(AAC 소리), 1920×1080 이하만 받고, 출력은 1920×1080 30 fps SDR H.264/AAC MP4, 영상 트랙 1개, 프로젝트 저장 없음(§4·§9). 일반 4K, 3시간 편집, 제품 준비 상태를 주장하지 않는다. 알려진 열린 문제(§10)와 미확인 항목(§8)은 그대로 남는다. **A-010(진행 중):** 입력 프레임레이트를 넓혔다(29.97·25·23.976·59.94 고정과 가변 원본, 생성 fixture로 검증). 출력은 FHD 30 fps 그대로다(§4·§12).

## 1. 빌드와 실행

필요한 것: 이 저장소를 확인한 Mac의 Xcode(관찰 환경: Xcode 27.0, macOS SDK 27). 설치나 전역 설정 변경은 필요 없다. 서명은 로컬 ad-hoc이다.

```sh
cd app
scripts/build.sh            # Debug 빌드 → app/.build/DerivedData/Build/Products/Debug/OnTheFrame.app
open .build/DerivedData/Build/Products/Debug/OnTheFrame.app
```

- Xcode에서 열려면 `app/OnTheFrame.xcodeproj`를 열고 OnTheFrame 스킴을 실행(⌘R)한다.
- `scripts/build.sh Release`는 Release 빌드를 만든다. 이 빌드에는 자체 검사 코드가 들어가지 않는다.

엔진 테스트와 샌드박스 자체 검사:

```sh
cd app/Engine && swift test     # 모델·엔진 테스트(생성 fixture, 짧은 내보내기)
cd app && scripts/selftest.sh   # 샌드박스 앱 자체 검사(Debug 빌드 필요)
cd app && scripts/shortcut-test.sh   # 단축키 경로 자체 검사(Debug, 내보내기 없음)
cd app && scripts/preview-test.sh    # 편집 뒤 프리뷰 갱신 자체 검사(Debug, 내보내기 없음)
cd app && scripts/close-test.sh      # 닫기·종료 경고 자체 검사(Debug, 두 번 실행: window, quit-export)
cd app && KEEP=1 scripts/visual-test.sh   # 진행 카드·완료 시트 시각 자체 검사(Debug, PNG는 selftest-work/visual-*/visual/)
cd app && scripts/lane-test.sh       # 레인·연결·레인 이름 자체 검사(Debug, 내보내기 판정 포함)
cd app && scripts/layout-test.sh     # 창·편집기 배치 자체 검사(Debug, 세 번 실행, 사용자 설정과 따로 둔 저장소)
cd app && scripts/project-test.sh    # 프로젝트 저장·열기·재연결·최근 목록 자체 검사(Debug, 다시 연 프로젝트 내보내기 판정 포함)
cd app && scripts/savepanel-test.sh  # 실제 저장 패널(확인 단추는 사람이 눌러야 함). 검사 스크립트는 APP=다른 빌드 경로로 앱을 바꿀 수 있다
cd app && scripts/multilane-test.sh  # 여러 레인·소리 파일·형식 2 자체 검사(Debug, 내보내기를 otf-dev verify-multilane이 판정)
cd app && scripts/transform-test.sh  # 영상 크기·위치 자체 검사(Debug, 프리뷰 테두리 끌기, 내보내기를 otf-dev verify-overlay가 격자 판정)
```

`scripts/selftest.sh`의 결과는 `app/selftest-work/last-verify-result.json`에 남는다.

빌드·검증 산출물은 모두 Git에서 무시한다: `app/.build/`, `app/Engine/.build/`, `app/selftest-work/`. 이 산출물은 실험 산출물과 함께 4 GiB 상한 안에서 관리한다.

단축키(Premiere 방식 기본값, [D-019](../docs/DECISIONS.md)):

- Premiere Pro의 몇 가지 기본 단축키를 따른다. 완전한 Premiere 호환이 아니다. J/K/L 셔틀, ↑/↓ 편집점 이동, ⇧Delete, ⇧←/→ 등은 없다.
- 사용자 지정·프리셋은 없다. 복사·붙여넣기는 M2다.

키 처리 방식(`KeyRouting.swift`):

- 모든 편집기 단축키는 한 곳에서 실제 상태로 판단하고, 처리하면 이벤트를 소비한다(한 번 누름 = 한 번 동작).
- 다음 경우에는 처리하지 않고 이벤트를 그대로 보낸다: 편집기 창이 키 창이 아님, 알림 시트·모달, 드래그 중, 꺼진 동작.
  - ⌘ 조합이 꺼진 동작이면 경고음만 낸다.
- 텍스트 입력 칸에 초점이 있으면 Space·Delete·화살표·Home/End는 텍스트 칸으로 간다. ⌘Z/⇧⌘Z는 텍스트 실행 취소가 되고, ⌘K·⌘E는 동작하지 않는다.
- Space·Delete·⌘ 명령의 자동 반복은 무시하고, 화살표만 반복을 허용한다.
- 메뉴는 표시·마우스 선택용이다. 수정 키 없는 키는 메뉴 제목에 적는다.
  - 이유: 메뉴 키 등가물로 두면 텍스트 입력보다 먼저 처리되어 입력을 가로챈다.
  - SwiftUI 메뉴 항목의 사용 가능 상태는 메뉴를 열 때만 갱신되었다. 그래서 실행 시 꺼져 있던 항목(⌘B 분할, ⌘E 등)은 상태가 바뀐 뒤에도 키로 실행되지 않았다. 합성 이벤트 검사로 확인했고, M1 처음 구현에 있던 결함이다.
- 한글 등 라틴 문자가 아닌 입력 소스에서는 ⌘ 조합을 키 코드로 맞춘다.
  - 한국어 2벌식에서 ⌘K는 `characters` "k", `charactersIgnoringModifiers` "ㅏ"(U+314F) 모양으로 온다. 현재 입력 소스에서 시스템이 채운 이벤트를 읽어 확인했다.
  - 라우터는 `charactersIgnoringModifiers`가 라틴 문자가 아니면 키 코드(K=40, Z=6, E=14)로 맞춘다.
- 처리 층:
  1. 로컬 키 감시가 먼저 처리한다. 앱 `sendEvent` 안에서 불린다(검사로 확인).
  2. 보조로 편집기 창 보기의 `performKeyEquivalent`(⌘ 조합)와 타임라인 `keyDown`(수정 키 없는 키)이 같은 판단을 쓴다.
  - 같은 이벤트는 한 번만 처리한다.
- 편집기 창이 키 창이 아니어도 주 창이고 앱이 활성 상태면 단축키를 받는다. 다만 키 창이 없거나, 주 창이 될 수 없고 시트·모달이 아니며 텍스트 입력 중이 아닌 보조 창이어야 한다.
- 실행 판단은 캐시된 초점 값이 아니라 실제 창 상태로 한다.
- Esc(드래그 취소)는 타임라인이 직접 처리한다.
- 진단: `--args -OTFKeyTrace`로 실행하면 키 이벤트가 지난 층, 창·첫 응답자, 현재 입력 소스 ID, 처리 결과를 시스템 로그에 남긴다.
  - 글자는 ⌘ 조합과 단축키 키에만 기록한다.
  - 읽기: `/usr/bin/log show --last 10m --predicate 'subsystem == "dev.ontheframe.app" AND category == "keys"' --style compact`

한국어 입력 소스 문제(2026-10-10, 소유자 관찰: 영어 입력에서는 동작, 한국어 입력에서는 동작하지 않음. 어떤 단축키가 영향을 받는지는 아직 전부 확인되지 않음):

- 확인한 것:
  - 한국어 모양 이벤트(위)를 앱 이벤트 큐에 넣거나 `sendEvent`로 보내면 ⌘K·⌘Z·⇧⌘Z·Space가 한 번씩 처리된다. 문자 해석·키 코드 대체 경로 자체는 원인이 아니었다.
  - 로컬 감시는 `sendEvent` 안에서 불린다. 따라서 "다시 전달된 이벤트가 로컬 감시를 건너뛴다"는 처음 가설은 맞지 않는다.
  - 소유자 세션 기록: 입력 소스를 바꾼 순간 앱 안에 입력 소스 표시 창(TextInputUI)이 생겼다. 그 직후 내보내기는 메뉴를 마우스로 골라 실행했다.
- 고친 약점(원인 후보, 실제 키보드로 미확정):
  1. 편집기 창이 키 창이 아니면 모든 단축키를 거부하던 조건 → 보조 창이 키이거나 키 창이 없을 때도 받도록 완화했다.
  2. ⌘K가 캐시된 초점 값(`editorFocused`)을 써서, 키 창 변화 알림 뒤 값이 낡으면 경고음만 내던 문제 → 실제 상태로 판단한다.
  - 둘 다 합성 검사로 재현해 고쳤다(음성 대조 포함).
- 소유자 실제 키보드 확인(2026-10-10 15:38–15:39 KST, 한국어 2벌식):
  - 결과: 소유자 보고 기능 통과(PASS). 한국어 입력 소스에서 단축키가 동작한다고 보고했다.
  - 근거 기록(`-OTFKeyTrace`, 이 Mac의 시스템 로그에서 다시 읽어 확인): 키 이벤트 28개가 모두 입력 소스 `com.apple.inputmethod.Korean.2SetKorean`이었다. ⌘K·⌘Z·⇧⌘Z·⌘E·Space·←·→는 모두 `handled@localMonitor`였다. ⌘Q 한 번은 처리하지 않고 메뉴로 넘겼다(정상).
  - 보조 처리 층(performKeyEquivalent·타임라인 keyDown)이 처리한 이벤트는 없다.
  - 한계:
    - 기록은 라우터가 이벤트를 받아 처리했다는 것까지만 보여 준다. 타임라인 결과(자르기 위치, 실행 취소 상태 등)가 맞았다는 근거는 소유자 보고뿐이다.
    - 원래 원인은 여전히 확정되지 않았다. 고친 두 약점(창 조건 완화, ⌘K의 캐시 의존 제거) 중 어느 것이 관련됐는지 기록으로는 구분할 수 없다.
    - 이 기록 구간에는 영어 입력 소스 이벤트가 없다(영어는 이전 소유자 관찰에서 동작).
  - 미확인: Delete, Home/End, 드래그 중 Esc 취소, 저장 패널 이름 칸의 텍스트 편집
- 합성 검사는 입력기(IME)와 하드웨어 입력 계층을 거치지 않는다. 그 증거로, 한국어 입력 소스에서 합성 "a"를 텍스트 칸에 넣으면 "ㅁ"이 아니라 "a"가 된다. 그래서 실제 한국어 입력 확인과 한글 조합 확인은 소유자가 실제 키보드로 해야 한다(§8).

편집 규칙:

- 빈틈(D-020):
  - 타임라인은 클립의 시작 위치와 길이를 따로 갖는다. 클립은 겹치지 않고, 클립이 없는 구간은 빈틈이다(영상 검정·소리 없음).

  - 일반 삭제는 마지막·유일한 클립을 지워도 길이를 유지한다. 빈 새 프로젝트의 길이는 0이다.
- 빈틈과 함께 쓰는 편집 규칙(기존 리플 규칙을 빈틈에 맞춘 것):
  - 자르기: 클립 안에서만. 재생 헤드가 빈틈에 있으면 아무 일도 하지 않고 상태 줄에 알린다.
  - 삽입(+ 단추, 끌어 놓기): 기존 클립의 시작이나 타임라인 끝에 끼워 넣고, 그 뒤를 민다. 끝에 추가하면 끝 빈틈 뒤에 붙는다. (§18에서 바뀜: + 단추는 고른 레인 쌍의 마지막 클립 뒤, 끌어 놓기는 놓은 시각. 리플 없음.)
  - 트림: 클립 시작 위치는 고정하고 길이만 바꾼다. 뒤 클립은 길이 변화만큼 움직이고 빈틈은 유지된다(빈틈을 채우거나 덮지 않는다).
  - 이동: 클립의 원래 구간을 닫고(리플) 대상 지점에 끼워 넣는다. 그래서 이동하면 원래 자리에 빈틈이 남지 않는다. 일반 삭제와 다르니 주의한다. 제자리 이동은 아무것도 바꾸지 않는다. (§18에서 바뀜: 끌기는 옮기기이고 원래 자리는 빈틈이 된다.)
  - 빈틈 자체는 선택하거나 지울 수 없다.

- 편집을 시작하면 재생을 멈춘다.
- 재생 헤드는 유지하고, 타임라인이 짧아지면 새 끝으로 당긴다.
- 편집할 때마다 불변 타임라인 스냅샷에서 프리뷰 composition을 비동기로 다시 만든다. 세대 번호가 지난 결과는 버린다.
- 트림·이동 드래그 중에는 타임라인 그림만 바뀌고, 프리뷰는 드래그를 끝낸 뒤 다시 만든다.

내보내기:

- 저장 패널에서 위치를 고르면 시작 시점의 타임라인 스냅샷을 1920×1080, 30 fps, SDR, H.264/AAC MP4로 내보낸다.
- 진행 카드는 창을 막지 않는다. 내보내는 동안 편집해도 결과는 바뀌지 않는다.
  - 카드 내용(A-011): 진행률·취소, "경과 00:12", "남은 시간 약 00:35" 또는 "남은 시간 계산 중…", 검증·승격 중에는 "마무리 중…"
  - 끝난 뒤: 완료 알림에 걸린 시간을 보인다. 취소·실패에도 경과 시간을 보이지만 완료로 보이지 않는다(§13).
- 진행률(A-009): 한 내보내기 안에서 유한하고 [0, 1] 안이며 줄어들지 않는다. 순서대로 전달된다.
  - 인코딩 중에는 0.99까지만 보인다. 100%는 출력 검증과 대상 위치로의 승격이 성공한 뒤에만 보인다.
  - 취소·실패는 완료로 보고하지 않는다.

닫기·종료 경고(A-009, 프로젝트 저장은 M1 범위 밖):

- 영상을 가져왔거나 타임라인이 있으면, 창 닫기(닫기 단추·⌘W·모두 닫기)와 종료(⌘Q, Dock 메뉴)에서 한국어 경고를 띄운다. 경고 내용: 아직 저장할 수 없음, 닫으면 편집 내용이 사라짐, 내보낸 영상은 편집 가능한 프로젝트가 아님.
- 단추는 "취소"(기본, Return)와 "버리고 닫기"·"버리고 종료"(파괴적 표시)다. Esc는 경고를 닫지 않는다.
- 빈 새 프로젝트는 경고 없이 닫힌다. 내보내기를 마쳐도 프로젝트는 저장되지 않으므로 경고가 나온다.
- 내보내는 중이면 경고에 "진행 중인 내보내기는 취소되고 임시 파일은 정리된다"가 더해진다. 버리기를 고르면 내보내기를 취소하고 정리가 끝난 뒤 닫는다. 취소를 고르면 내보내기는 계속된다.
- 같은 확인을 겹쳐 띄우지 않는다(대기열 AppKit 알림). 앱이 숨겨졌거나 창이 최소화돼 있으면 경고가 보이도록 창을 앞으로 가져온다.
- 구현:
  - 창 닫기: SwiftUI 창 대리자를 감싸 `windowShouldClose`만 가로챈다. 나머지는 원래 대리자에 넘긴다.
  - 종료: `applicationShouldTerminate`가 이번 요청은 취소(terminateCancel)하고 경고를 띄운다. 버리기를 고르면 다시 종료한다.
  - terminateLater로 기다리면 AppKit의 중첩 실행 루프에서 주 actor 작업이 돌지 않아 내보내기 정리를 기다리다 멈출 수 있었다(자체 검사로 확인).
  - 그래서 시스템 로그아웃·재시동 중에는 저장하지 않은 작업이 있으면 앱이 그 과정을 한 번 취소한다.
  - 마지막 창이 닫혀 종료하는 것은 사용자가 창을 닫은 경우만이다(실행 직후 창 복원 과정의 일시적 닫힘으로 끝나지 않게).
- 파일을 열며 실행하거나 Dock 아이콘을 눌렀는데 보이는 창이 없으면 편집기 창을 앞으로 가져온다. 자체 검사에서 폴더를 열며 실행할 때 창이 화면에 나오지 않는 경우를 보았다.
- 완료, 실패, 원본 보호 거부는 알림으로, 취소는 상태 줄로 알린다. 내보내기 중에 앱을 끝내면 취소하고 임시 파일을 정리한 뒤 끝낸다.

## 3. 구조와 실험 코드의 관계

| 경로 | 내용 | 앱 번들 포함 |
| --- | --- | --- |
| `OnTheFrame/` | SwiftUI 셸(`ContentView`), AppKit 타임라인(`TimelineView`), 앱 상태(`ProjectStore`), AppKit 알림(`AlertPresenter`), Debug 자체 검사(`SelfTest`) | 예(`SelfTest`는 Debug만) |
| `Engine/Sources/OnTheFrameEngine` | `MediaProbe`(입력 판정), `Timeline`·`EditHistory`(불변 모델·실행 취소), `CompositionPlanner`(프리뷰·내보내기 공유 구성), `ExportService`(출력 보호 내보내기), `RenderSettings` | 예 |
| `Engine/Sources/OTFDevSupport`, `otf-dev` | 검증용 생성 fixture(`DevFixtures`)와 내보낸 파일 판정(`ExportJudge`) | 아니요 |
| `Engine/Tests` | 모델·엔진 테스트 | 아니요 |
| `Config/` | Info.plist, 엔타이틀먼트(App Sandbox, 사용자 선택 파일 읽기·쓰기) | — |

앱은 `OnTheFrameEngine`만 쓰고, 실행 시 실험 패키지(E1Core, E2Core)에 의존하지 않는다. 실험에서 확인한 규칙은 앱 범위에 맞게 다시 썼다.

- 프리뷰와 내보내기는 같은 구성 함수(`CompositionPlanner.plan`)를 쓴다(E1~E3 원칙).
  - 빈틈은 앞·중간에서는 빈 구간으로 넣는다. 끝 빈틈은 원본 구간으로 채우되 화면에 보이지 않게 한다(레이어 없는 검정 지시).
  - AVComposition은 트랙 끝의 빈 구간을 길이에 넣지 않는다. 1프레임을 늘려 채우면 내보내기가 샘플 하나만 만든다. 둘 다 검사로 확인했다.
  - 끝 빈틈 구간의 소리 트랙은 비어 있다.
- composition 트랙의 원본 `AVURLAsset`을 붙잡아 둔다(E2에서 −12780 원인).
- 새 대상은 배타적 이름 바꾸기(`renamex_np RENAME_EXCL`)로 옮긴다(E1 `OutputGuard`의 승격 방식).
- 재생 중에만 디스플레이 유휴 절전을 막는다(E3-1에서 화면이 꺼지면 프리뷰 표시가 멈춘 기록).

M1에는 자막과 스펙트럼이 없어 AVFoundation 기본 합성기(레이어 지시)를 쓴다. 따라서 E2의 사용자 정의 합성기 경로와 그 미해결 원본 프레임 불일치는 앱 경로와 관계없다. 그 결함은 해결된 것이 아니다. 자막·스펙트럼이 들어오는 마일스톤에서 사용자 정의 합성기를 다시 쓸 때 다시 다룬다.

회귀 범위:

- 앱 검증 도구는 E2의 생성 fixture 작성기(`SourceVideoSpec`, FHD 배치)와 프레임 측정(`E2Metrics`, `E2Decoder`)을 재사용한다. 이 재사용은 테스트·검증 전용이다.
- 실험 러너, 실험 결과, 증거 파일은 바꾸지 않았다.
- E1·E2 단위 테스트는 이번 작업에서 다시 실행해 통과했다(§6).

## 4. 입력 범위(A-010에서 프레임레이트 확장)

M1은 30 fps 고정 간격만 받았다. 이것은 검증 범위였지 제품 요구가 아니었다(소유자 방향, 2026-10-10). A-010에서 입력 프레임레이트를 넓혔다. 받는 것은 앱 경로에서 생성 fixture로 확인한 것뿐이다.

받는 것:

- 컨테이너는 AVFoundation이 여는 MP4·MOV·M4V다. 가져오기 패널은 `public.movie` 형식을 고르게 한다.
- 영상 트랙 1개(H.264 `avc1`, HEVC `hvc1`·`hev1`)와 오디오 트랙 0~1개(AAC만)
- 프레임레이트: 고정 프레임레이트와 가변 프레임레이트(VFR) 모두 받는다.
  - 고정: 30, 29.97(30000/1001), 25, 23.976(24000/1001), 59.94(60000/1001) 등
  - 판정 방법: 모든 압축 샘플의 표시 시각(PTS)을 정확한 유리수로 모아 비교한다. 간격이 모두 같으면 고정, 아니면 가변으로 표시한다.
  - 확인한 원본: 30, 29.97, 25, 23.976, 59.94 fps와 가변 간격(1/60~0.3 s). 모두 생성 fixture다.
- 영상 트랙 편집 목록이 1구간이고 속도 변화가 없는 것. 미디어 시작 오프셋(B 프레임 재정렬로 생기는 것)은 받는다.
- 회전 정보가 90도 단위인 것. 표시 크기에 반영하고, 1920×1080 안에 비율을 유지해 가운데 맞춘다. 세로 영상은 1080×1920 이하만 받는다.
- 표시 크기: 긴 변 1920·짧은 변 1080 이하, 16 px 이상
- 길이 10분 이하. 잠정 상한이며, 앱 경로로는 짧은 길이만 검증했다.

**시간 대응(A-010):**

- 타임라인과 내보내기는 30 fps 그대로다. 입력 프레임레이트와 출력 프레임레이트는 따로다.
- 클립의 원본 위치는 원본 트랙 시작에서 잰 시각을 1/30 s 단위로 나타낸다. 타임라인 프레임 k의 원본 시각은 정확히 (sourceIn + k − 시작)/30 s다.
- 각 타임라인 프레임에는 그 시각에 표시 중인 원본 프레임, 즉 PTS가 그 시각 이하인 마지막 프레임이 나온다.
  - 25·23.976 fps 원본: 일부 프레임이 두 번 보인다.
  - 29.97 fps 원본: 약 1000프레임마다 한 프레임이 두 번 보인다.
  - 59.94 fps 원본: 프레임을 건너뛴다.
  - 가변 원본: 긴 간격 동안 같은 프레임이 유지된다.
  - 프레임 보간이나 속도 변경은 없다.
- 소리는 영상과 같은 원본 시각 구간을 쓰므로 원본 프레임레이트와 관계없이 동기가 유지된다.
- 원본 길이 안에 들어가는 타임라인 프레임 수(내림)가 그 원본의 최대 클립 길이다.
- 원본 구간 표시(클립 정보)는 원본 시작에서 잰 시각을 타임라인 30 fps 타임코드로 보인다. 원본 자체의 프레임 번호가 아니다. 목록과 클립 정보에 원본 프레임레이트("29.97 fps", "가변 평균 22.4 fps")를 함께 보인다.

거부하는 것(가져오기 알림에 이유를 보이고, 변환하지 않는다):

- 같은 표시 시각의 샘플이 있는 영상, 평균 프레임레이트가 1~240 fps 밖인 영상(잠정 범위)
- 영상 트랙이 없거나 2개 이상인 파일, 오디오 트랙이 2개 이상인 파일
- H.264·HEVC 외 영상 코덱(ProRes 등), AAC 외 오디오(PCM 등)
- 1920×1080을 넘는 원본(4K 포함). 앱 경로에서 확인하지 않았기 때문이다.
- 편집 목록이 여러 구간인 파일(앞에 빈 구간이 있는 파일 포함), 속도가 바뀌는 구간, 90도 단위가 아닌 회전

원본 파일은 읽기만 한다. 자동 트랜스코딩이나 원본 수정은 없다. 넓은 호환 목표(ProRes, 4K, 다른 소리 형식, MKV·AVI·WebM)는 §12에 따로 적었다. 아직 지원하지 않는다.

## 5. 출력 보호(샌드박스)

1. 대상이 가져온 원본이면 거부한다. 같은 경로이든, 장치·inode가 같은 하드 링크이든, 대치 확인이 있어도 마찬가지다.
2. 기존 파일은 저장 패널에서 대치를 확인한 경우에만 바꾼다. 확인 시점의 파일 식별(장치, inode, 크기, 수정 시각)을 기록해 두고, 승격 직전에 다시 비교해 달라졌으면 바꾸지 않는다.
3. 결과는 `FileManager.url(for: .itemReplacementDirectory, in: .userDomainMask, appropriateFor: 대상)`이 준 임시 디렉터리에 쓴다. 검증(영상 트랙 1개, 프레임 수)한 뒤 옮긴다.
   - 새 대상: `renamex_np(RENAME_EXCL)`. 그 사이 같은 이름이 생기면 덮어쓰지 않는다.
   - 대치: `FileManager.replaceItemAt`
   - 대상 옆에 형제 임시 파일을 만들지 않는다.
4. 취소·실패 시에는 이 내보내기가 만든 임시 디렉터리만 지운다.

관찰(자체 검사): 데이터 볼륨의 대상에 대해 임시 디렉터리는 `/Volumes/<볼륨>/.TemporaryItems/folders.<uid>/TemporaryItems` 아래에 만들어졌다. 샌드박스 앱이 그곳에 쓰고 옮길 수 있었다.

## 7. 충돌 기록(2026-10-10)

**증상**

- 첫 자체 검사 실행에서 앱이 시작 2.03초 뒤 주 스레드 `EXC_BAD_ACCESS`(주소 0)로 끝났다.
- 충돌 당시 빌드는 첫 Debug 빌드다. 실행 파일 slice UUID는 c7aa2c37…이고, 그 뒤 같은 경로에 다시 빌드했다.
- 실행 방식은 `scripts/selftest.sh` → `open -n -W -a … --args -OTFSelfTest`였다.
- 원 충돌 보고서는 로컬 진단 보고서 폴더에 그대로 두었다. 기기 식별자와 경로가 들어 있어 저장소에는 넣지 않는다.

**스택**

1. SwiftUI 레이아웃 갱신(`NSHostingView.layout` → `ViewGraph.updateOutputs`)
2. 알림 다리(`DeprecatedAlertBridge.preferencesDidChange`)가 떠 있는 NSAlert 시트의 모달 세션을 끝냄(`NSWindowEndWindowModalSession`)
3. 시트 닫기 애니메이션(`NSSheetMoveHelper closeSheet` → `NSMoveHelper _doAnimation`)이 중첩 실행 루프를 돎
4. `UC::DriverCore::continueProcessing` 관찰자가 다시 들어와 주소 0 호출

**원인이 된 사건**

- 시스템 로그상 충돌 직전 0.6초 안에 가져오기 7개가 동시에 시작됐다(거부 fixture 4개 포함). 23.878초에 알림 시트가 키 창이 된 흔적이 있고, 24.12초에 충돌했다.
- 당시 코드는 거부가 하나 끝날 때마다 표시 중인 알림을 새 id의 알림으로 바꿨다(`reportRejection`).
- 자체 검사는 가져오기 직후 알림을 코드로 지우고 곧바로 편집을 시작했다.
- 23.612초에 AppKit 레이아웃 재진입 경고(`layoutSubtreeIfNeeded … already being laid out`)가 한 번 기록됐다.

**재현**

당시 코드(사용 중단된 `.alert(item:)`와 진행 시트)를 별도 빌드로 되살려 시험했다.

- 알림만 바꾸기 20회, 알림만 코드로 닫기 20회, 거부 가져오기만: 각 3회 실행에서 충돌 0
- 원래 자체 검사 전체: 3회 중 2회 충돌, 스택 동일
  - 한 번은 시작 0.9초 뒤 가져오기 단계
  - 한 번은 시작 14.5초 뒤, 원본 대상 내보내기가 진행 시트를 열고 닫는 순간 실패 알림이 겹친 단계

첫 수정 시도(현재 SwiftUI `.alert(isPresented:presenting:)` + 진행 카드 + 알림 대기열)도 자체 검사 2회 중 2회 충돌했다. 스택은 `AppKitDialogBridge.updateExistingPresentation` → `NSWindowEndWindowModalSession` → 같은 시트 닫기 경로였다. 두 번 모두 알림을 코드로 닫은 직후 다른 상태 변화(내보내기 시작)가 같은 갱신에 겹쳤다. 따라서 사용 중단된 API 자체가 원인은 아니었다.

**결론(확인된 것)**

SwiftUI 알림 다리가 표시 중인 NSAlert 시트를 레이아웃 갱신 안에서 닫을 때 충돌이 재현된다. 닫는 계기는 알림 교체나 코드로 닫기였고, 다른 화면 변화가 같은 갱신에 겹쳤다. 알림 교체·닫기만 따로 하면 재현되지 않았다.

**남은 불확실성**

- 주소 0 호출이 어느 프레임워크 구성 요소의 결함인지는 이 증거로 정할 수 없다. OS 결함으로 단정하지 않는다.
- 레이아웃 재진입 경고는 구형 빌드의 충돌 실행에서만 보였고, 현재 다리 충돌에서는 보이지 않았다. 충돌의 필요조건은 아니다.
- E2의 영상 프레임 결함과 연결할 증거는 없다.

**수정**

- 알림을 SwiftUI `.alert` 다리로 띄우지 않고 `AlertPresenter`가 AppKit `NSAlert.beginSheetModal`로 직접 띄운다.
- 표시 중인 알림은 바꾸거나 코드로 닫지 않는다. 새 알림은 대기열에 넣는다. 다음 알림은 앞 시트가 끝난 뒤 띄운다(완료 처리에서, 시트가 아직 붙어 있으면 `didEndSheetNotification` 뒤).
- 가져오기는 묶음 단위로 처리해 거부 이유를 알림 하나로 모은다.
- 내보내기 진행은 시트가 아닌 카드로 보여 모달 전환이 겹치지 않는다.
- 임의의 지연은 넣지 않았다.

**검증**

- 수정 뒤 자체 검사 연속 7회: 매회 41/41 통과, 새 충돌 보고서 0, 레이아웃 재진입 경고 0
- 매회 알림 16개를 차례로 표시하고 닫았고, 취소 4회 반복과 일반 실행도 확인했다.
- 수정 전 대비 표본은 작다(구형 2/3, 첫 수정 2/2 충돌). 사람이 직접 알림을 여러 번 닫는 확인은 §8에 있다.

## 8. 소유자 상호작용 확인 목록

소유자가 직접 확인하는 항목이다. 각 항목 앞의 표시는 받은 소유자 보고(정성, 측정 아님)다. 표시가 없거나 "미보고"인 항목은 M1 완료를 막지 않는 미확인 기록이다(§11). 생성 fixture는 `app/.build/test-work/fixtures`에 있다. `scripts/selftest.sh`나 `swift test`를 한 번 실행하면 만들어진다. 직접 찍은 영상은 30 fps H.264·HEVC, 1080p 이하일 때만 가져와진다.

1. 앱을 실행하면 빈 상태 안내(왼쪽 목록, 프리뷰, 타임라인)가 보이고, 내보내기 단추가 꺼져 있다.
2. 가져오기 패널에서 `otf-A.mp4`, `otf-B.mp4`와 `reject-*` 파일을 함께 고르면, 받는 파일은 목록에 들어가고 거부 이유는 알림 하나에 모여 나온다.
3. 목록에서 타임라인으로 끌어 놓기, + 단추 추가, 재생·일시정지, 프레임 이동, 눈금자 탐색이 자연스럽다.
4. ⌘K 자르기, 가장자리 트림, 가운데 드래그 이동(노란 선), 드래그 중 Esc, Delete, ⌘Z/⇧⌘Z가 기대대로 동작한다. 드래그 하나가 실행 취소 한 번에 되돌아간다.
5. 재생 중 편집하면 재생이 멈추고, 재생 헤드가 유지되거나 끝으로 당겨진다.
6. 끝 위치에서 마지막 프레임이 보인다(D-018 끝 프레임 유지). 이것은 앱 경로에서 자동 확인하지 않았다.
7. [저장 패널 새 파일·대치 내보내기, 진행 중 취소, 결과 MP4 재생(이전 보고): 소유자 보고 통과 / "Finder에서 보기": 미보고] 내보내기: 저장 패널로 새 파일을 내보내고, 진행 카드와 취소, 완료 알림의 "Finder에서 보기"를 확인한다. 결과 MP4를 재생해 편집 경계와 소리가 프리뷰와 같은지 본다.
8. [소유자 보고 통과, 2026-10-10 최종 확인] 저장 패널에서 기존 파일 대치를 확인한 경우만 바뀌고, 가져온 원본 이름을 고르면 거부된다. 이것이 파일 하나만 허락되는 실제 샌드박스 경로다.
9. 알림이 떠 있는 동안 다른 작업을 이어서 해 보고, 알림을 여러 번 열고 닫아도 앱이 멈추거나 끝나지 않는다.
10. [내보내는 중 종료(취소 → 내보내기 계속·완료, 버리고 종료 → 앱 종료·대상 없음): 소유자 보고 통과 / 내보내는 중 창 닫기: 자동 검사만] 내보내는 중 창을 닫거나 앱을 끝내면 임시 파일 없이 끝나고, 대상 파일이 생기지 않는다.

11. [한국어 2벌식: 소유자 보고 통과 2026-10-10 15:38–15:39, 키 경로 기록 있음 / 영어(ABC): 이전 소유자 관찰에서 동작] 한국어 입력 소스(2벌식)와 영어(ABC)에서 각각, 실제 키보드로 ⌘K·⌘Z·⇧⌘Z·⌘E가 한 번씩 동작하는지 확인한다(A-007). 입력 소스를 앱 안에서 바꾼 직후에도 확인한다. 동작하지 않으면 `-OTFKeyTrace`로 다시 실행해 같은 키를 누르고, 로그를 함께 전달한다.
12. [Space·←/→: 소유자 보고 통과(위와 같은 기록) / Delete: 이전 리플 동작에서 소유자 보고 통과, 입력 소스 미기록] 한국어 입력 소스에서 Space·←/→·Delete도 확인한다. 텍스트 칸이 생기는 다음 마일스톤에서는 한글 조합 입력이 가로채지지 않는지 확인한다(M1에는 텍스트 칸이 없음).
13. [이전 동작에서 소유자 보고 통과: 트림, 이동, 드래그 중 Esc 취소, 삭제(당시 리플), 실행 취소 / 미확인: Home/End] 실제 키보드로 단축키(⌘K, Space, ←/→, Home/End, Delete, ⌘Z/⇧⌘Z, 드래그 중 Esc)가 한 번씩 동작한다. 한글 입력 소스에서도 ⌘K·⌘Z가 동작한다. 자동 검사는 합성 이벤트만 썼다.
14. [저장 패널 이름 칸 편집: 이전 동작에서 소유자 보고 통과 / 메뉴 항목 상태: 미확인] 메뉴(타임라인·재생)를 열면 항목의 사용 가능 상태와 적힌 키가 맞다. 내보내기 저장 패널의 이름 칸에서 Space·⌫·←/→·⌘Z가 정상 입력·편집으로 동작한다. 저장 패널은 다른 프로세스라 자동 검사하지 않았다.

소유자 관찰(이전 동작, 정성 통과·자동 정확도 측정 아님): 트림, 이동, 드래그 중 Esc 취소, 삭제(당시 리플 삭제), 실행 취소, 저장 패널 이름 칸 편집, MP4 내보내기가 기대대로 동작한다고 보고했다(A-008 이전 빌드).

소유자 관찰(A-008 빌드, 정성 통과 — 프레임·샘플 측정 아님): 가운데 클립 일반 삭제는 빈틈과 뒤 클립 위치를 유지한다. 빈틈 재생은 검정·무음이다. 실행 취소로 클립이 돌아온다. 리플 삭제는 구간을 닫고 타임라인을 줄인다. 마지막 클립 일반 삭제는 길이를 유지하고 끝에서 검정을 유지한다. 내보낸 MP4의 끝 검정·무음 구간이 프리뷰와 같다. 한국어 입력 소스에서 Delete와 ⇧Delete가 동작한다. 이 보고에 포함되지 않은 것: Home/End, 영어 입력 소스의 삭제, 첫 클립 삭제(앞 빈틈), 내보낸 파일의 중간 빈틈.

15. [소유자 보고 통과] 새 삭제 동작(A-008): 가운데 클립을 Delete로 지우면 빗금 친 빈틈이 남고 뒤 클립이 움직이지 않는다. ⇧Delete는 뒤 클립을 당긴다. 각각 ⌘Z로 정확히 되돌아간다.
16. [마지막 클립·빈틈 재생·끝 검정: 소유자 보고 통과 / 첫 클립(앞 빈틈): 미보고] 첫·마지막 클립을 Delete로 지우면 앞·끝 빈틈이 남고 타임라인 길이가 그대로다. 빈틈 구간을 재생하면 화면이 검정이고 소리가 없다. 끝이 빈틈이면 끝 위치에서도 검정이다.
17. [끝 빈틈: 소유자 보고 통과 / 중간 빈틈: 미보고] 빈틈이 있는 타임라인을 내보내 재생하면 빈틈과 유지된 클립의 위치·소리가 프리뷰와 같다.
18. [한국어: 소유자 보고 통과 / 영어: 미보고] 한국어·영어 입력 소스에서 Delete와 ⇧Delete가 한 번씩 동작한다(실제 키보드).
20. [소유자 보고 통과(정성), 2026-10-10] 이전에 거부된 소유자의 29.97 fps 영상: §12 "소유자 확인 목록"
21. [미확인, A-011] 가져오기·내보내기 진행 카드와 시간 표시: §13 "소유자 확인 목록"
19. [소유자 보고 통과, 2026-10-10 최종 확인] 닫기·종료 경고(A-009): 영상을 가져온 상태에서 창 닫기 단추·⌘W·⌘Q를 누르면 한국어 경고가 나오고, "취소"·Return이면 편집기가 그대로 남는다. 내보내기를 마친 뒤에도 경고가 나온다. 아무것도 가져오지 않은 새 창은 경고 없이 닫힌다.

소유자 최종 확인(2026-10-10, A-009 빌드, 정성 통과 — 화면 캡처는 닫기 경고, 그 뒤 편집기, 저장 패널 대치 확인을 보여 줄 뿐 파일 내용·무결성을 증명하지 않으며 자동 측정이 아니다): §11의 최종 확인 목록 1–3을 모두 설명대로 동작한다고 보고했다. 명시적으로 든 것은 닫기·종료 경고와 취소·Return으로 편집기 유지, 버려도 되는 기존 내보내기 파일을 새 편집 영상으로 대치, 가져온 원본과 같은 경로·이름으로 내보내기 거부와 원본 보존, 진행 중 내보내기 취소 뒤 새 대상 파일 없음, 내보내는 중 종료 취소 뒤 내보내기 완료, 내보내는 중 버리고 종료 뒤 앱 종료와 새 대상 파일 없음, 내보내기 성공 뒤에도 닫기 경고다.

## 9. 남은 한계(M1 범위 밖 또는 미확인)

- 프로젝트 저장·다시 열기가 없다. 창을 닫거나 앱을 끝내면 편집 내용이 사라진다(A-009부터 닫기 전에 경고한다).
- 복사·붙여넣기, 편집 가능한 자막·스펙트럼, 이미지·오디오 가져오기는 다음 마일스톤이다.
- 썸네일, 파형, 음량 표시가 없다. 재생 중 타임라인이 재생 헤드를 따라 스크롤하지 않는다.
- 트림·이동 드래그 중에는 프리뷰가 바뀌지 않는다(놓은 뒤 갱신).
- 앞 가장자리 트림은 리플이라 클립 시작 위치가 고정되고, 뒤가 움직인다.
- 빈틈(A-008):
  - 클립이 하나도 없고 빈틈만 남은 타임라인은 프리뷰가 검정이고, 재생·내보내기를 하지 않는다(내보내기 꺼짐).
  - 빈틈 자체를 선택·삭제(빈틈 닫기)하는 동작은 없다. 빈틈을 닫으려면 뒤 클립을 리플로 옮기거나 지운다.
  - 이동은 원래 자리를 닫는다(빈틈이 남지 않음).
  - 앱 화면 프리뷰(AVPlayerLayer)의 빈틈 표시는 자동 검사하지 않았다. 프리뷰 경로는 같은 composition의 AVPlayerItemVideoOutput으로 검사했다.
- 회전 영상은 판정과 변환 계산만 자동 확인했다. 화면 내용 판정은 하지 않았다.
- 4K 원본, 10분 근처 길이, 긴 내보내기는 앱 경로에서 확인하지 않았다. 30 fps가 아닌 원본은 생성 fixture로만 확인했고, 실제 카메라·휴대폰 파일은 소유자 확인(§8 20)에 의존한다.
- 다른 볼륨(외장 디스크 등)으로 내보내는 경우는 확인하지 않았다. `EXDEV`는 복사 이동으로 처리한다.
- 단축키: 영상 목록이나 단추에 키보드 초점이 있어도 Space·←/→는 편집기 동작이 된다. 목록의 화살표 선택 이동이나 Space 단추 누르기는 되지 않는다.
- 단축키: 앱 안의 텍스트 입력 칸은 M1 화면에 아직 없다. 텍스트 초점 동작은 검사용 칸으로만 확인했다.
- 배포 대상 macOS 15는 잠정이다. 실행 확인은 관찰 환경(macOS 26.6.2, Apple M2)에서만 했다.

## 10. 알려진 열린 문제(M1 완료 기준 8)

- E2 사용자 정의 합성기의 원본 프레임 불일치: 해결되지 않았다([experiments/e2-4k/README.md](../experiments/e2-4k/README.md)). M1은 기본 합성기를 써서 그 경로를 지나지 않는다. 자막·스펙트럼 마일스톤에서 다시 다룬다.
- E3-1 프리뷰 관찰기에 전달되지 않은 고유 프레임 9개(15 191, 15 198, 15 199, 15 204, 15 205, 15 206, 16 461, 17 865, 17 927): 원인 미확인이다. 내용 불일치는 아니다([experiments/e3-fhd-10min/README.md](../experiments/e3-fhd-10min/README.md)).
- 레이어 갱신 지연: E2·E3-1에서 디스플레이를 다시 켠 직후 일시정지 탐색이나 다시 재생 뒤 AVPlayerLayer 표시 버퍼가 비디오 출력보다 1.3~1.8 s 늦게 바뀐 기록이 있다. 다른 실행에서는 0~19 ms였다. 원인 미확인이다. 앱 화면의 레이어 표시는 자동 검사하지 않는다.
- A-010 프리뷰 경로 프레임 0 불일치(가끔, 미해결): 프리뷰 출력이 새 항목 첫 탐색에서 다음 키프레임 버퍼를 요청 시각으로 넘긴 것으로 보인다. composition 대응 결함은 아니다(§12 조사).
- 다른 프레임레이트 원본: A-010부터 시간 기준으로 받는다(§4·§12). 30 fps가 아닌 출력, 프레임 보간, 편집 목록이 여러 구간인 파일은 지원하지 않는다. 출력 정책은 미정이다(O-03, O-04).
- 한국어 입력 소스 단축키: 소유자 확인으로 동작하지만, 원래 원인은 확정되지 않았다(§2).

## 12. 입력 호환 확장(A-010, 2026-10-10)

작업 승인 A-010. M2 기능(자막·스펙트럼·복사·붙여넣기) 전에 흔한 실제 영상을 받도록 입력을 넓힌다. 첫 대상은 이전에 거부된 소유자의 29.97 fps 영상이다. 출력은 FHD 30 fps SDR H.264/AAC MP4 그대로다.

**엔진 가정 점검:**

- composition은 이미 시각 기준이었다. 원본 구간을 `트랙 시작 + sourceIn/30 s`, 길이 `length/30 s`로 넣고, 출력 프레임 시각은 videoComposition의 1/30 s다.
- 30 fps를 가정한 곳은 두 군데였다.
  1. 가져오기 검사(30 fps 고정 간격만 받음)
  2. 원본 길이를 압축 샘플 수로 센 것(`frameCount`)
- 바꾼 것:
  - `frameCount`를 "원본 길이 안의 타임라인 프레임 수"(정확한 정수 계산, 내림)로 바꿨다.
  - 표시 시각 분석(`SourceTiming`: 샘플 수, 고정·가변, 정확한 프레임 길이, 평균·최소·최대 간격)을 더했다.
  - 거부 검사는 없애지 않았다. 같은 표시 시각, 범위 밖 프레임레이트, 여러 편집 구간, 속도 변화, 코덱·크기 검사는 그대로다.
- 끝 빈틈 채움은 첫 클립 원본을 쓴다. 25 fps 원본으로 채워도 프레임 수가 맞는지 확인했다(아래).

## 13. 가져오기·내보내기 진행 표시(A-011, 2026-10-10)

**진행 카드:**

- 가져오기·내보내기 모두 프리뷰 위쪽의 창을 막지 않는 카드로 보인다. 모양은 공용 카드(`TaskProgressCard`)다.
- 작업 상태는 따로 둔다. 가져오기는 `importProgress`, 내보내기는 `exportPhase`와 `exportEstimator`다.
- 영상 목록 아래의 "확인 중…" 표시는 없앴다.
- 좁은 창에서는 파일 이름을 가운데에서 잘라 보인다.
- 카드는 묶음 요소로 손쉬운 사용에 노출된다. 진행 막대의 이름은 카드 제목이고, 값은 백분율이거나 "진행률 알 수 없음"이다.

**차례 실행(겹침 없음):**

- 가져오기와 내보내기는 한 번에 하나만 진행한다. 카드도 하나뿐이다.
- 내보내는 동안 고른 가져오기(끌어 놓기, Finder에서 열기 포함)는 대기열에 들어가 내보내기가 끝난 뒤 시작한다.
- 가져오는 동안에는 내보내기 단추와 ⌘E가 꺼진다.
- 이전에는 두 작업이 동시에 진행될 수 있었다.

**가져오기:**

- 카드 제목: "영상 가져오는 중…". 현재 파일 이름과 "끝난 수/전체 수개 확인 완료"를 보인다.
- 파일 안의 진행률은 알 수 없어 진행률 없는 막대를 보인다. 백분율은 만들지 않는다.
- 검사가 끝난 파일만 끝난 수로 센다. 거부된 파일도 검사가 끝난 것으로 센다.
- 처리 순서:
  - 파일은 고른 순서대로 하나씩 검사한다. 이전에는 파일별로 병렬 검사했다. 현재 파일을 정확히 보이기 위해 바꿨고, 여러 파일 묶음은 조금 느려질 수 있다.
  - 받은 파일은 묶음이 모두 끝난 뒤 고른 순서대로 한꺼번에 목록에 들어간다(기존 묶음 반영 규칙).
  - 거부 이유는 기존 알림 대기열로 알림 하나에 모인다.
- 취소:
  - 남은 파일은 검사하지 않는다. 검사 중인 파일은 샘플 읽기를 멈춘다(`AVAssetReader.cancelReading`).
  - 카드는 멈출 때까지 "가져오기 취소하는 중…"을 보인다.
  - 이번 묶음에서 이미 검사를 마친 파일도 목록에 넣지 않는다. 묶음 반영 전이기 때문이다.
  - 앞서 가져온 영상과 편집은 그대로다. 대기 중인 가져오기 묶음도 함께 버린다.
  - 앱은 보안 범위 접근(`startAccessingSecurityScopedResource`)을 따로 열지 않으므로 닫을 접근 핸들은 없다.
- 늦은 결과:
  - 취소·버리기·창 닫기 때 가져오기 회차 번호를 올린다. 이전 회차의 검사 결과는 도착해도 버린다.
  - 닫기·종료 확인에서 "버리기"를 고르면 가져오기도 취소하고, 검사가 멈춘 뒤 닫는다. 경고 문구에 "진행 중인 가져오기는 취소되고"가 더해진다.
  - 작업이 없어 확인 없이 닫는 창도 진행 중인 가져오기를 취소한다.
  - 버리거나 닫은 뒤의 가져오기·내보내기 요청은 시작하지 않는다.

**내보내기 시간:**

- 시계: 단조 시계 `ContinuousClock`를 쓴다. 시스템 시계 변경과 무관하다.
- 언제 재는가:
  - 저장 패널이 닫힌 뒤 실제 작업이 시작될 때(`beginExport`) 재기 시작한다. 패널에 머문 시간은 빼고, composition 준비·인코딩·검증·승격은 모두 넣는다.
  - 성공·실패·취소가 끝난 시점에 멈춘다. 취소는 정리가 끝날 때까지 센다.
  - 내보내기마다 표본과 추정을 처음부터 다시 시작한다.
- 표시 형식: "경과 MM:SS", 1시간 이상이면 "H:MM:SS"다. 표시 형식일 뿐 긴 프로젝트 지원을 뜻하지 않는다.
- 단계: 준비 → 인코딩 → 마무리(검증·승격). ExportService가 단계를 알리고, 진행률 값은 바꾸지 않는다. 100%는 여전히 검증·승격 성공 뒤에만 나온다.
- 남은 시간 추정(`ExportTimeEstimator`):
  - "남은 시간 계산 중…"을 보이는 경우: 준비 중, 시작 뒤 3초 미만, 진행률 2% 미만, 진행률 표본 3개 미만, 최근 5초 동안 진행률이 늘지 않음(멈춤), 속도가 거의 0
  - 경과 시간 ÷ 진행률로 계산하지 않는다(진행률이 0에 가까울 때 값이 터지고, 느려짐을 숨긴다).
  - 속도는 최근 5초 동안의 진행률 증가 ÷ 5초다(조회 시각 기준). 짧은 흔들림은 창 안에서 평균되고, 창보다 긴 느려짐은 그대로 드러난다. 남은 양은 인코딩 상한 0.99까지다.
  - 표시는 "남은 시간 약 MM:SS"(올림)다. 인코딩 진행률이 상한에 닿았거나 마무리 단계면 "마무리 중…"을 보이고 "0초 남음"은 보이지 않는다.
  - 취소를 누르면 "내보내기 취소하는 중…"과 "취소 중"을 보인다.
- 끝난 뒤:
  - 성공: 완료 알림에 "걸린 시간 MM:SS"
  - 실패: 실패 알림에 경과 시간
  - 취소: 상태 문구 "내보내기를 취소했습니다(경과 MM:SS)"
  - 취소·실패는 완료로 보이지 않는다.

  - `import.cancel`: 첫 파일 검사가 끝난 뒤 취소했다. "취소하는 중" 표시, 이번 묶음 추가 없음, 1초 뒤에도 늦은 결과 없음, 취소 문구를 확인했다.
  - `ops.serializedNoOverlap`: 내보내는 중 가져오기가 대기열에 들어갔다(카드 하나, 내보내기 단추 꺼짐). 대기 중 가져오기 취소와 내보내기 취소 뒤 파일이 생기지 않았다.
  - `import.ignoredAfterDiscard`: 실제 버리기 처리 뒤 진행 중이던 가져오기 결과와 새 요청이 모두 들어오지 않았다.
  - `exportTime.success`: 시작 때 초기화, 단계 준비 → 인코딩 → 마무리, 알림의 걸린 시간 = 멈춘 경과 시간, 첫 표시 "남은 시간 계산 중…"을 확인했다.
  - `exportTime.cancelNotCompleted`, `exportTime.failureNotCompleted`: 마무리 단계 없음, 경과 표시, 완료 알림 아님을 확인했다.
- 검사 fixture의 내보내기는 약 2.5초라 3초 문턱을 넘지 않았다. 그래서 앱 경로에서 관찰한 표시는 "남은 시간 계산 중…" → "마무리 중…"뿐이고, 숫자 추정은 엔진 테스트로만 확인했다. UI 지연을 일부러 넣지 않았다.

**한계:**

- 남은 시간은 근사다. AVAssetExportSession의 진행률이 시간에 고르게 비례한다는 보장이 없고, 검증·승격 시간은 추정에 넣지 않는다.
- 3초보다 짧은 내보내기는 숫자 추정 없이 끝난다.
- 카드를 여러 창 크기에서 보는 확인은 소유자 확인에 의존한다. 화면 기록 권한을 쓰지 않으므로 자동 화면 캡처는 하지 않았다.

**시각 조정(소유자 피드백 반영, 2026-10-10 소유자 시각 승인 — 정성):** 소유자가 새 진행 카드와 완료 시트의 모양을 승인했다. 취소·Finder·키보드 동작은 이 승인에 포함되지 않는다(미보고).

- 진행 카드:
  - 위치: 편집기 루트 겹침의 가운데(가로·세로)다. 창 크기를 바꿔도 가운데에 있다.
  - 모양: 불투명 남색(#172334) 바탕, 흰 제목·백분율, #CBD5E1 보조 글자(13 pt 이상), 청록·파랑(#38BDF8) 채움과 어두운 막대 바탕, 옅은 테두리와 그림자

  - 순서: 제목·백분율 → 파일 이름·개수 → 막대 → 경과·남은 시간 → 취소
  - 투명·흐림에 기대지 않고, 밝은·어두운 모양 모두 같은 고정 색이다.
  - 취소 단추는 바탕·흰 글자가 보이고, 키보드 초점(전체 키보드 접근)일 때 청록 테두리가 생긴다.

- 내보내기 완료 시트:
  - 기존 대기열(AlertPresenter) 안의 사용자 정의 AppKit 시트(`CompletionSheet`)다. NSAlert로는 바탕·단추 색을 바꿀 수 없어서 바꿨다.
  - 위치: 창 대리자 `willPositionSheet`로 편집기 내용 영역(툴바 아래) 가운데에 놓는다. 다른 확인·실패 알림은 기본 위치다.
  - 내용: 같은 남색과 글자색, 초록 체크 → "내보내기 완료" → 파일 이름 → "걸린 시간 MM:SS" → 청록 "Finder에서 보기" → 회색 "닫기"
  - 파일 이름은 고를 수 있고 최대 3줄로 줄 바꿈한다. 잘리면 도움말과 손쉬운 사용 이름으로 전체 이름을 준다.
  - Return·Esc는 "닫기"다. Finder는 그 단추를 눌러야만 연다(단추 번호와 동작은 기존과 같음).

  - SwiftUI 알림 다리나 코드로 닫기를 쓰지 않는다. 사용자가 단추·키로만 닫는다.
  - 성공(검증·승격 뒤)에만 쓴다. 취소는 상태 문구, 실패는 기존 NSAlert다.
  - 시트 모서리는 시스템 시트 모양을 따른다. 카드의 12 pt와 정확히 같지 않을 수 있다.
- 확인 방법: `scripts/visual-test.sh`가 위치·단추·키를 검사하고, 밝은·어두운 모양에서 창·카드 상태별·시트를 PNG로 그린다.
  - 앱 자신의 보기만 그리며 화면 기록 권한은 쓰지 않는다.
  - 프리뷰(AVPlayerLayer)는 그림에 나오지 않는다.
  - 모양을 바꾼 직후 그린 창 그림에는 옆 패널 일부가 이전 모양으로 남는 캡처상의 어긋남이 있었다. 카드·시트 그림에는 없었다.
  - 키보드 초점 테두리는 전체 키보드 접근을 켜지 않아 그림으로 확인하지 않았다.

**소유자 확인 목록(짧게):**

1. 여러 파일(받는 파일과 거부되는 파일 섞어서)을 한꺼번에 가져온다.
   - 프리뷰 위쪽 카드에 "영상 가져오는 중…", 현재 파일 이름, "n/N개 확인 완료"가 보이는지 본다.
   - 끝나면 받는 파일이 목록에 들어오고, 거부 이유가 알림 하나에 모이는지 본다.
2. 큰 파일 몇 개를 가져오다가 카드의 "취소"를 누른다. 카드가 사라지고, 이번에 고른 파일이 추가되지 않으며, 기존 목록·타임라인이 그대로인지 본다.
3. 30초 이상 걸리는 내보내기를 시작한다(긴 타임라인).
   - 경과 시간이 1초마다 늘고, 처음 몇 초는 "남은 시간 계산 중…", 그다음 "남은 시간 약 MM:SS"가 실제와 대략 맞는지 본다.
   - 끝 무렵 "마무리 중…"이 보이고, 완료 알림에 걸린 시간이 나오는지 본다.
4. 내보내는 중 취소한다. "취소하는 중…" 뒤 완료 알림 없이 취소 문구(경과 포함)가 나오는지 본다.
5. 창을 좁게·넓게 바꿔 카드 글자가 겹치거나 잘려 읽을 수 없게 되지 않는지 본다.

## 14. 영상·원본 소리 레인, 레인 이름, 창 배치(A-012, 2026-10-10, 진행 중)

작업 승인 A-012, 결정 D-021(레인·연결)·D-022(창·나눔). 입출력 호환과 내보내기 설정(FHD 30 fps H.264/AAC)은 그대로다.

**레인과 연결:**

- 타임라인은 영상 레인("원본소스")과 원본 소리 레인("원본소리")으로 나뉜다.
  - 소리가 있는 영상을 넣으면 같은 위치·원본 구간의 연결된 영상·소리 클립이 생긴다. 각 클립은 안정된 ID를 갖고, 연결은 묶음 ID로 표시한다.
  - 소리 없는 영상은 영상 클립만 생긴다.
- 연결된 쌍:
  - 함께 선택된다(소리를 눌러도 쌍이 선택됨).
  - 자르기·트림·이동·일반 삭제·리플 삭제가 쌍에 함께 적용되어 동기가 유지된다.
  - 어긋난 쌍을 자를 때는 같은 원본 위치에서 나눈다. 그래서 어긋남이 그대로 유지된다.
- 연결 해제·연결:
  - 메뉴: 타임라인 메뉴와 클립 문맥 메뉴의 "연결 해제(영상·소리 따로 편집)"와 "연결(⌘-클릭한 클립과)"
  - 연결하려면 한 클립을 누르고 다른 레인의 클립을 ⌘-클릭한다.
  - 연결해도 위치·원본 구간을 바꾸지 않는다(다시 맞추지 않음).
  - 어긋나면 두 클립에 빨간 "+15f" 같은 표시가 나온다. 소리가 영상보다 늦으면 +다. 정보 패널에는 프레임과 초로 보인다.
- 연결 해제 뒤:
  - 각 클립을 따로 선택·이동·트림·자르기·삭제할 수 있다.
  - 따로 끌어 옮기면 같은 레인 안에서 원하는 위치(빈틈 포함)에 놓인다. 원래 자리는 빈틈이 된다.
  - 다른 클립과 겹치면 놓을 수 없다. 끄는 동안 제안 위치가 빨갛게 보이고, 놓으면 원래대로 남으며 상태 줄에 이유가 나온다(덮어쓰지 않음).
- 삭제:
  - 일반 삭제(Delete)는 묶음만 지운다. 다른 위치와 타임라인 길이는 그대로다.
  - 리플 삭제(⇧Delete)는 묶음 구간을 두 레인에서 닫는다. 그 구간에 다른 클립이 걸치면 설명과 함께 거부한다.
- 실행 취소·다시 실행은 두 레인, 연결, 위치, 원본 구간, 길이, 레인 이름을 함께 되돌린다. 드래그 하나는 한 단계이고, 드래그 중 Esc는 취소한다.
- composition:
  - 영상 트랙은 영상 레인, 소리 트랙은 원본 소리 레인에서 따로 만든다. 레인마다 빈틈(검정·무음)이 따로다.
  - 원본 시각 규칙(영상 트랙 시작 + sourceIn/30 s)은 영상·소리가 같다. 그래서 연결을 해제해 옮긴 소리는 옮긴 만큼 어긋나 들린다.
  - 소리 레인만 남으면 영상은 검정이다.
- 프리뷰·내보내기의 같은 composition, 시작 시점 스냅샷, 오래된 재구성 거부, 원본 보호는 그대로다.

**구현 선택(소유자 미확인, 바꿀 수 있음):**

- 연결된 쌍과 소리 없는 영상 클립의 끌어 옮기기는 기존 끼워 넣기 이동(D-020 리플, 노란 선)이다. 빈틈에 놓는 자유 이동은 연결을 해제한 클립에만 쓴다.
- 연결은 같은 원본의 연결되지 않은 영상·소리 한 쌍만 된다.
- 리플 삭제뿐 아니라 리플 트림·끼워 넣기 이동·삽입도 그 지점·구간에 다른 클립이 걸치면 거부한다(동기 보호).
- 연결을 해제한 클립을 트림해도 뒤 클립은 두 레인에서 함께 밀리거나 당겨진다(리플 트림).
- 레인 이름 편집은 다른 곳을 눌러 초점을 잃어도 확정한다.

**레인 이름:**

- 레인 머리를 두 번 클릭하거나 문맥 메뉴 "레인 이름 바꾸기…"로 바꾼다.
  - Return은 확정, Esc는 취소다.
  - 빈 이름(공백만 포함)이면 이전 이름을 유지하고 상태 줄에 알린다.
  - 바꾸기 한 번이 실행 취소 한 단계다.
- 이름은 레인 ID(영상·소리 고정 ID)에 붙고 클립·파일 이름과 따로다. 모델(`Lane`)은 Codable이라 이후 프로젝트 파일에 그대로 넣을 수 있다. 프로젝트 저장은 하지 않았다.
- 편집 중에는 텍스트 칸이 첫 응답자라 Space·Delete·⌘K 같은 타임라인 단축키가 입력을 가로채지 않는다. ⌘Z는 텍스트 실행 취소다.
- 레인 머리는 가로 스크롤 영역 밖의 고정 열이다. 세로로만 타임라인과 함께 움직인다.

**창과 편집기 배치:**

- 처음 실행(저장된 위치 없음):
  - 바깥 창은 대상 화면의 쓸 수 있는 영역(`NSScreen.visibleFrame`, 메뉴 막대·Dock 제외, 논리 포인트) 너비·높이의 70%이고, 그 가운데에 놓인다.
  - 최소 크기가 들어가면 최소 크기 이상이고, 쓸 수 있는 영역은 넘지 않는다.
- 이후 실행:
  - 마지막 보통 창(전체 화면·확대 아님)의 위치·크기를 되살린다.
  - 저장값이 화면 밖이거나 화면보다 크면 가장 많이 겹치는 화면의 쓸 수 있는 영역 안으로 옮기고 줄인다.
  - SwiftUI 창 복원은 끄고 이 규칙만 쓴다.
- 최소 크기:
  - 패널 최소 크기에서 정한다. 목록 160·프리뷰 320·정보 180 pt, 위 패널 240·타임라인 150 pt. 이전에는 1100×680이었다.
  - 작은 화면에서는 창 최소 크기를 쓸 수 있는 영역에 맞춰 줄인다.
- 나눔:
  - 처음 나눔(툴바와 나눔선 두께 제외): 위 패널 70%·타임라인 30%, 위 패널은 목록 15%·프리뷰 70%·정보 15%(2026-10-10 조정, 이전 20/60/20)
  - 나눔선은 끌 수 있고, 바꾼 비율을 기억한다. 이미 저장된 비율은 재설정하기 전까지 그대로 쓴다(이전 기본값으로 저장된 비율 포함).
  - 목록·정보 패널은 툴바의 사이드바 단추나 보기 메뉴("영상 목록 접기/펼치기", "클립 정보 접기/펼치기")로 접고 편다. (§19: 메뉴 이름은 "왼쪽 패널 접기/펼치기".)
    - 접으면 패널과 그 나눔선이 사라지고, 남는 폭은 프리뷰가 쓴다.
    - 펼치면 이전 너비로 돌아온다. 접힘 상태도 기억한다.
  - 보기 메뉴 "기본 배치로 재설정"은 비율 70/30·15/70/15와 양쪽 패널 펼침으로 되돌린다. 창 위치·크기는 바꾸지 않는다.
  - 공간이 모자라면 패널 최소 크기를 지키고 프리뷰를 먼저 지킨다. 목록·정보·타임라인은 패널 안에서 스크롤한다.
- 프리뷰는 영상 비율을 유지한다(AVPlayerLayer `resizeAspect`).
- 진행 카드와 완료 시트는 크기를 바꾼 편집기 내용의 가운데에 그대로 놓인다.
- 저장소는 UserDefaults다. 자체 검사는 따로 둔 저장소(`-OTFLayoutSuite`, Debug 전용)를 써서 사용자 저장값을 건드리지 않는다.

## 15. 프로젝트 저장·열기(A-013, 2026-10-10, 진행 중)

작업 승인 A-013, 형식 결정 D-023. 편집기 창 하나에 프로젝트 하나다.

**파일 메뉴:**

| 항목 | 키 | 동작 |
| --- | --- | --- |
| 새 프로젝트 | ⌘N | 빈 프로젝트(저장하지 않은 변경이 있으면 확인) |
| 프로젝트 열기… | ⌘O | 열기 패널(.ontheframe), Finder에서 열기와 같은 처리 |
| 최근 프로젝트 ▸ | — | 최근에 열거나 저장한 프로젝트(최대 10, 최신이 앞, 중복 없음), "목록 지우기" |
| 가져오기… / 내보내기… | ⌘I / ⌘E | 기존 그대로. 찾을 수 없는 원본이 있으면 내보내기는 이유를 보이고 하지 않는다 |
| 미디어 재연결… | — | 찾을 수 없는 원본을 고른 파일로 다시 연결 |
| 프로젝트 저장 | ⌘S | 처음에는 저장 패널, 이후 현재 위치 |
| 다른 이름으로 저장… | ⇧⌘S | 새 위치에 쓰고 그 위치가 현재 프로젝트가 된다 |

- ⌘N·⌘O·⌘S·⇧⌘S는 다른 편집기 단축키처럼 KeyRouting이 처리한다(한국어 입력 소스에서도 한 번). 텍스트 칸 편집 중에는 메뉴로 넘긴다.
- 가져오기·내보내기가 진행 중이면 새 프로젝트·열기·최근·Finder 열기를 하지 않고, 끝나거나 취소한 뒤 다시 하라고 알린다.
- 창 제목은 프로젝트 이름이고, 저장하지 않은 변경이 있으면 "— 편집됨"과 창 닫기 단추의 점(문서 편집 표시)을 보인다. 툴바의 이름 뒤에도 •를 붙인다.

**저장하지 않은 변경:**

- 마지막으로 저장하거나 연 상태와 지금 상태(미디어 목록, 클립·위치·원본 구간, 연결, 레인 이름, 길이, 재연결)를 비교한다. 실행 취소로 저장 상태에 돌아오면 표시가 사라진다.
- 재생 헤드·선택·창 배치는 프로젝트 변경이 아니다. MP4 내보내기는 프로젝트 저장이 아니다.
- 미디어 가져오기는 실행 취소로 사라지지 않는 프로젝트 변경이다. 이전에는 실행 취소로 미디어 등록이 빠질 수 있었다(잠재 결함, 고침).
- 새 프로젝트·열기·창 닫기·종료 때 확인한다. "변경 사항을 저장할까요?"
  - 단추: 저장(기본, Return) · 취소(Esc) · 저장 안 함(파괴적)
  - 저장을 취소했거나 실패하면 이어지는 동작을 하지 않는다.
  - 내보내기·가져오기 중 창 닫기·종료는 이전처럼 그 작업을 취소·정리한 뒤 닫는다.
  - 이전의 "아직 저장할 수 없습니다" 경고를 대신한다.

**저장:**

- 원본 보호: 가져온 원본 미디어(같은 경로, 심볼릭 링크, 하드 링크)에는 저장하지 않는다.
- 원자적 저장: 대상과 같은 볼륨의 대치용 임시 디렉터리에 쓴 뒤 옮긴다. 기존 파일은 `replaceItemAt`, 새 파일은 `renamex_np(RENAME_EXCL)`이다.
- 실패하거나 취소하면 이전 프로젝트 파일, 저장하지 않은 상태, 최근 목록이 그대로다.
- 원본마다 앱 범위 보안 북마크(`com.apple.security.files.bookmarks.app-scope` 엔타이틀먼트)를 새로 만들어 넣는다.

**열기:**

- 파일 전체를 읽고 검사한 뒤에만 현재 프로젝트를 바꾼다.
- 거부하는 파일: 손상된 파일, 형식이 다른 파일, 더 새로운 버전, 지원하지 않는 렌더 설정, 겹침·원본 범위·연결 쌍·ID 중복이 잘못된 파일. 이유를 알리고 현재 상태는 그대로다.
- 원본 찾기 순서: 북마크(보안 범위 접근 시작) → 프로젝트 기준 상대 경로 → 절대 경로
  - 찾은 파일은 다시 검사한다. 그 원본을 쓰는 모든 클립 구간을 덮고, 소리 클립이 쓰면 소리가 있어야 쓴다.
  - 오래된 북마크는 다음 저장 때 새로 만든다.
- 찾지 못해도 편집 구조는 연다. 그 원본은 다음처럼 보인다:
  - 목록에 경고와 "미디어 재연결…"
  - 타임라인에 주황 빗금 "원본 없음"
  - 재생 헤드가 그 구간이면 프리뷰에 "원본 미디어를 찾을 수 없는 구간"(의도한 빈틈과 구별)
  - 프리뷰는 그 구간을 검정·무음으로 구성한다(편집 상태는 그대로).
  - 내보내기는 이유를 보이고 막는다.
- 보안 범위 접근은 프로젝트를 바꾸거나(새 프로젝트·열기) 앱을 끝낼 때 모두 멈춘다.

**재연결:**

- 고른 파일을 다시 검사한다. 그 원본을 쓰는 모든 클립의 원본 구간이 새 파일 안에 있어야 하고, 소리 클립이 쓰면 소리가 있어야 한다. 아니면 거부한다(클립을 조용히 줄이지 않음).
- 클립·ID·위치는 그대로다. 재연결은 실행 취소 한 단계이고, 실행 취소하면 다시 "찾을 수 없음"이 된다.

**최근 프로젝트:**

- 성공적으로 열거나 저장한 프로젝트만 들어간다. 실패·취소는 넣지 않는다.
- 목록은 앱 설정(UserDefaults)에 앱 범위 보안 북마크와 함께 있다.
- 열 수 없는 항목은 이유를 알리고 목록에 남긴다. "목록 지우기"는 목록만 지우고 프로젝트 파일은 그대로다.

**파일 형식(버전 1, A-014부터 버전 2 — §16):**

```json
{
  "format": "dev.ontheframe.project",
  "version": 1,
  "projectID": "UUID",
  "settings": { "width": 1920, "height": 1080, "fps": 30 },
  "durationFrames": 210,
  "lanes": [ { "id": "UUID", "kind": "video", "name": "원본소스" }, { "id": "UUID", "kind": "audio", "name": "원본소리" } ],
  "media": [ { "ref": { "id": "UUID", "name": "a.mp4", "path": "/절대/경로/a.mp4", "frameCount": 120, "hasAudio": true,
                        "size": 123, "modifiedNs": 456, "codec": "avc1", "width": 1920, "height": 1080 },
               "relativePath": "../media/a.mp4", "bookmark": "base64…" } ],
  "videoClips": [ { "id": "UUID", "mediaID": "UUID", "start": 0, "sourceIn": 0, "length": 60, "link": "UUID" } ],
  "audioClips": [ { "id": "UUID", "mediaID": "UUID", "start": 75, "sourceIn": 60, "length": 60, "link": "UUID" } ]
}
```

- 시각: `start`·`sourceIn`·`length`·`durationFrames`·`frameCount`는 타임라인 30 fps의 정수 프레임이다. 원본 시각은 정확히 `sourceIn/30` s(A-010)이고, 부동소수점 시각은 저장하지 않는다.
- 연결: 같은 `link` 값을 가진 영상 1·소리 1이 한 쌍이다. 빈틈은 클립이 덮지 않는 `[0, durationFrames)` 구간이다(따로 저장하지 않음).
- 렌더 설정: 버전 1은 1920×1080 30 fps만 연다.
- 버전 처리: 먼저 `format`·`version`만 읽는다. 형식이 다르면 "프로젝트 파일이 아님", 버전이 더 높으면 "더 새로운 버전에서 만듦"(앱 업데이트 안내), 더 낮거나 0이면 지원하지 않는 버전이다. 같은 버전일 때만 전체를 읽어 검사한다. 이후 버전은 읽는 쪽에서 이전 버전을 옮겨 읽게 한다(아직 없음).
- 키는 정렬해 저장한다(같은 내용이면 같은 바이트). 북마크는 이 Mac·사용자에서만 쓸 수 있으며, 다른 Mac에서는 상대·절대 경로와 재연결에 의존한다.

**검증:**

- 엔진 테스트 40/40(새 4개, `ProjectFileTests`)
  - 왕복: 빈틈, 어긋난 소리(+15), 연결, 바꾼 레인 이름, 렌더 설정, ID, 북마크, 상대 경로(`../a.mp4`)가 같다. 저장 파일에 소수점 숫자가 없고, 다시 저장하면 같은 바이트다.
  - 거부 13가지: JSON 아님, 다른 형식, 더 새로운 버전 99, 이전 버전 0, 필수 키 없음, 4K 설정, 클립보다 짧은 길이, 겹침, ID 중복, 모르는 미디어, 원본 범위 밖, 짝 없는 연결, 빈 레인 이름
  - 재연결: 짧은 파일과 소리 없는 파일은 거부, 클립·ID는 그대로. 프리뷰용 사본은 길이를 유지한다. 가져오기는 실행 취소로 사라지지 않는다.
  - 생성 fixture: 저장 → 다시 읽은 타임라인을 다시 검사한 원본(저장된 ID)으로 구성해 내보냈다. 210프레임과 클릭 4개(손 계산 30·50·90·115프레임)가 오차 0 샘플이었고, 빈틈은 무음, 프리뷰 경로 경계 5프레임은 내보내기와 같았다.
- 프로젝트 자체 검사 `scripts/project-test.sh`(샌드박스 앱, 저장·열기 패널 대신 같은 내부 함수 호출): 모든 항목 통과
  - 처음 상태, 가져오기 → 편집됨, 새 위치 저장(제목·최근 목록·파일 내용·북마크 2/2), 실행 취소로 저장 상태에 돌아오면 표시 사라짐
  - 원본 미디어·하드 링크에 저장 거부(원본 해시 그대로), 실패한 저장은 이전 파일 바이트·편집됨 표시·최근 목록 그대로
  - 새 프로젝트 확인(단추·키), 취소는 그대로, 저장은 현재 위치에 저장한 뒤 새 프로젝트

  - 손상·더 새로운 파일 거부(상태·최근 목록 그대로), 가져오는 중 열기 거부, 저장 안 함 → 열기
  - 원본을 지운 프로젝트: 편집 구조는 열림, 내보내기 막힘과 이유, 재생 헤드 위치 표시. 짧은 파일 재연결 거부, 맞는 파일 재연결 → 실행 취소로 다시 찾을 수 없음 → 다시 실행
  - 옮긴 원본을 북마크로 찾고(보안 범위 접근 1), 새 프로젝트로 바꾸면 접근 0
  - 최근 목록 순서·중복·상한, 지우기는 파일 그대로, Finder 열기(앱 대리자 경로)
  - 다시 연 프로젝트 내보내기: `otf-dev verify-project`가 210/210프레임, 클릭 4개 오차 0 샘플로 판정
- 회귀: 최종 보고 참고

**실제 사용 중 저장 실패(2026-10-11, 고침):**

- 증상(소유자 보고): 실제 저장 패널에서 바탕화면을 고르고 확인했지만 파일이 없었다. 알림이 나오지 않았고, 창 제목은 "편집됨" 그대로였다.
- 확인한 원인:
  - `saveProject`가 패널 결과를 `done?(writeProject(to: u))`로 넘겼다.
  - Swift의 선택적 호출은 `done`이 nil이면 인자 계산까지 건너뛴다. 메뉴 "프로젝트 저장"·⌘S·"다른 이름으로 저장"은 완료 처리기 없이 부르므로, 패널이 확인을 돌려줘도 `writeProject`가 한 번도 불리지 않았다(처음 저장과 이후 저장 모두).
  - 저장하지 않은 변경 확인의 "저장"은 완료 처리기를 넘기므로 정상이었다. 자체 검사가 이 경로와 `writeProject` 직접 호출만 써서 놓쳤다.
- 확인 방법: 저장 단계 기록(`SaveTrace`, 컨테이너 `Library/Logs/OnTheFrame-save.log`)을 더한 진단 빌드로 실제 패널을 띄웠다. "패널 응답 1(확인), 바탕화면 URL" 뒤에 쓰기 단계가 하나도 없었다. 소유자 앱의 설정에도 최근 프로젝트가 없었고, 바탕화면과 Spotlight에도 .ontheframe 파일이 없었다. 샌드박스·북마크 문제가 아니었다.
- 고침:
  - 결과를 먼저 계산한 뒤 `done`에 넘긴다. 코드 전체에서 같은 꼴(부작용 있는 선택적 호출 인자)은 이 두 곳뿐이었다.
  - 임시 파일을 다시 읽어 같은 프로젝트(타임라인·프로젝트 ID)인지 검사한 뒤에만 대상 위치로 옮긴다. 잘못 쓴 파일이 이전 프로젝트 파일을 바꾸지 않는다.
  - 옮긴 뒤 대상에 같은 크기의 파일이 있을 때만 저장 상태·최근 목록에 넣는다.
  - 저장 단계 기록은 256 KB를 넘으면 비운다.
  - 패널 취소(중단 포함)는 상태 줄에 "프로젝트 저장을 취소했습니다", 확인인데 위치가 없으면 알림을 보인다.
  - 저장 실패는 알림과 상태 줄에 함께 보인다.
- 소유자 확인(2026-10-11, 진단 빌드, 정성): 고친 빌드에서 프로젝트 저장과 다시 열기가 된다고 보고했다. 보고에 없는 항목(다른 이름으로 저장, 원본 재연결, 저장하지 않은 변경 확인, 최근 목록 지우기, Finder 열기 등)은 미확인으로 둔다.
- 회귀 검사:
  - `project-test.sh`: 완료 처리기 없는 처음 저장(패널 결과만 주입, 뒤 경로는 실제)과 이후 저장이 파일을 쓰는지 본다.
  - `savepanel-test.sh`: 실제 패널을 띄운다. 샌드박스 저장 패널은 다른 프로세스라 앱 안에서 확인 단추를 누를 수 없었다(응답 −1001 중단). 그래서 확인은 사람이 해야 한다.

**한계:**

- 편집기 창 하나에 프로젝트 하나다. 여러 창·탭은 없다.
- 자동 저장·자동 복구, 버전 기록, 미디어 모으기(프로젝트 폴더로 복사)가 없다.
- 북마크는 이 Mac·사용자 전용이다. 다른 Mac에서 열면 경로가 맞고 접근 권한이 있을 때만 찾고, 아니면 재연결해야 한다.
- (A-014) 버전 2가 생겼고 버전 1은 옮겨 읽는다(§16).
- 재연결은 한 번에 원본 하나다(폴더에서 한꺼번에 찾기 없음). 재연결 검사는 길이·소리 유무만 본다. 다른 내용의 같은 길이 파일을 막지 못한다.
- 저장·열기 패널 자체와 실제 Finder 두 번 클릭은 자동 검사하지 않았다(소유자 확인).
- 저장 파일 이름은 사용자가 고른다. 앱 안 이름 바꾸기는 없다.

**소유자 확인 목록(짧게):**

1. 편집 뒤 ⌘S → 저장 패널 → 저장. 제목의 "편집됨"이 사라지는지 본다. 앱을 끝내고 다시 실행해 파일 > 최근 프로젝트로 열면 레인·연결·어긋남·빈틈·레인 이름이 그대로인지 본다.
2. 편집 뒤 ⌘N·⌘O·창 닫기·⌘Q에서 "변경 사항을 저장할까요?"가 나오는지 본다. 저장·취소(Esc)·저장 안 함이 설명대로인지 본다.
3. Finder에서 .ontheframe 파일을 두 번 클릭해 열리는지 본다.
4. 원본 영상을 다른 폴더로 옮기거나 이름을 바꾼 뒤 프로젝트를 연다. 찾거나, 못 찾으면 "미디어 재연결…"로 다시 연결되는지 본다. 짧은 다른 파일은 거부되는지도 본다.
5. 저장 패널에서 원본 영상 파일 이름을 고르면 거부되는지 본다.

## 16. 여러 레인과 소리 파일(A-014, 2026-10-11, 진행 중)

작업 승인 A-014, 동작 결정 D-024, 형식 D-023(버전 2). 구현 선택(소유자 미확인)은 [DECISIONS.md](../docs/DECISIONS.md) 감사 기록 2026-10-11에 있다.

**레인:**

- 레인은 종류(영상·오디오), 안정된 ID, 이름을 가진다. 오디오 레인은 음소거와 음량(0–100%, 100 = 원래 크기)도 가진다.
- 화면 순서는 위에서 아래로 영상 레인들 → 오디오 레인들이다. 각 종류는 하나 이상이다. 레인 수에 낮은 상한은 없고, 타임라인은 세로로 스크롤한다(레인 머리도 함께 움직이고, 가로 스크롤에는 고정).
- 레인 추가: 타임라인 메뉴·타임라인 위 "레인 추가" 메뉴·레인 머리 문맥 메뉴의 "영상 레인 추가"·"오디오 레인 추가". 새 이름은 "영상 N"·"오디오 N"이고, 고른 레인이 같은 종류면 그 바로 아래에 들어간다. (§18에서 바뀜: 가운데 경계에서 바깥쪽 — 새 영상 레인은 맨 위, 새 오디오 레인은 맨 아래, 이름은 "영상"·"오디오"이고 번호 V2·A2는 따로 보인다.)
- 레인 머리: 한 번 누르면 레인을 고르고(정보 패널에 레인 설정, §19부터 레인 설정은 왼쪽 "클립 조정" 탭), 두 번 누르면 이름을 바꾼다(한국어 입력, Return 확정, Esc 취소). 문맥 메뉴에는 이름 바꾸기·위로·아래로·음소거(오디오)·레인 삭제…·레인 추가가 있다. 음소거한 레인은 아이콘이 바뀌고 클립이 흐려지며, 100%가 아닌 음량은 머리에 보인다.
- 순서 바꾸기는 같은 종류 안에서만 한다. 영상 레인 순서는 겹친 영상 중 무엇이 보이는지를 바꾼다.
- 레인 삭제: 빈 레인은 바로, 클립이 있으면 확인("레인 삭제"·"취소") 뒤 한 단계로 지운다. 지운 레인의 클립과 연결된 다른 레인의 클립은 남고 연결만 풀린다. 각 종류의 마지막 레인은 지우지 않는다.
- 모든 레인 편집(추가·이름·순서·삭제·음소거·음량)은 실행 취소 한 단계이고 저장하지 않은 변경이 된다.

**클립:**

- 같은 레인 안에서는 겹치지 않고, 다른 레인과는 겹쳐도 된다.
- 끌어 놓기(미디어 목록 → 타임라인):

  | 놓은 곳 | 영상 파일 | 소리 파일 |
  | --- | --- | --- |
  | 클립이 있는 첫(맨 위) 영상 레인, 눈금자 | M1처럼 끼워 넣기(리플) — §18에서 바뀜: 놓은 시각에 놓기 | 거부(안내) |
  | 다른 영상 레인, 빈 첫 영상 레인 | 그 위치에 놓기, 겹치면 거부. 연결된 소리는 그 구간이 빈 첫 오디오 레인, 없으면 파일 이름의 새 오디오 레인 | 거부(안내) |
  | 오디오 레인 | 거부(안내) | 그 위치에 놓기, 겹치면 거부 |
  | 레인 아래 빈 곳(끄는 동안 점선 안내) | 파일 이름의 새 영상 레인 | 파일 이름의 새 오디오 레인 |

- 목록의 + 단추는 첫 영상·오디오 레인에 끼워 넣는다(소리 파일은 첫 오디오 레인 끝). (§18에서 바뀜)
- 옮기기: 연결을 해제한 클립은 끌어서 위치와 같은 종류 레인을 함께 바꾼다(겹치면 빨간 제안 위치, 놓으면 거부). 연결된 쌍은 기존처럼 끼워 넣기 이동을 하고(§18에서 바뀜: 연결된 쌍도 옮기기), 레인은 정보 패널의 "레인"·"연결된 소리 레인" 고르기로 바꾼다. 쌍의 한쪽이라도 겹치면 둘 다 옮기지 않는다. 한 번의 끌기가 한 단계이고 Esc는 끌기 전으로 돌린다.
- 일반 삭제는 빈틈을 남긴다. 리플 삭제·리플 트림·삽입·끼워 넣기 이동은 모든 레인에 적용되고, 묶음이 아닌 클립이 그 지점·구간에 걸치면 이유와 함께 거부한다.

**영상 겹침:**

- 각 시각에 클립이 있는 가장 위 영상 레인이 보인다. 위 레인의 빈틈에는 아래 레인이 보이고, 어느 레인에도 없으면 검정이다. 클립은 불투명 전체 화면(기존 비율 유지 맞춤)이고 하드 컷이다. 불투명도·전환은 없다.
- 구성: 엔진이 먼저 "보이는 조각"(각 시각의 가장 위 클립 부분)을 계산하고, 그 조각만 영상 트랙 하나에 넣어 기본 AVFoundation 합성기로 그린다. 프리뷰와 내보내기가 같은 계획(CompositionPlanner)을 쓴다. 가려진 아래 클립은 디코딩하지 않는다.

**소리 파일 가져오기:**

- 받는 것: WAV·AIFF(PCM), MP3, M4A(AAC·ALAC). 소리 트랙 1개, 모노·스테레오, 8–192 kHz, 10분 이하. 가져오기 패널(영상·소리 함께)과 목록에 끌어 놓기 모두 기존 가져오기 카드·묶음 거부 알림을 쓴다.
- 거부: 3채널 이상("소리 채널이 N개입니다"), 범위 밖 표본율, 다른 소리 형식, 소리 트랙 여러 개.
- 시각: 원본 길이는 정확한 표본 수·표본율로 기록하고, 편집 격자 길이는 1/30 s로 올림한다. 클립의 원본 시각은 `소리 트랙 시작 + sourceIn/30` s이고, 클립 안의 소리는 프레임으로 반올림하지 않는다. 마지막 부분 프레임에서 원본이 끝나면 그 뒤는 무음이다.
- 목록에는 파형 아이콘, 정확한 길이(초, 소수 셋째 자리), 형식(PCM·AAC·ALAC·MP3, kHz, 모노·스테레오)을 보인다. 정보 패널도 같은 정보를 보인다.
- 소리 파일만 있고 영상 원본이 하나도 없으면 프리뷰는 검정·소리만이고, 내보내기는 출력 영상 바탕이 없어 이유를 보이고 막는다.

**소리 섞기:**

- 음소거하지 않은 오디오 레인을 모두 더한다. 레인 음량은 오디오 믹스(트랙 음량)로 프리뷰 항목과 내보내기 세션에 같은 값을 붙인다. 소리 트랙이 있으면 음량이 모두 100%여도 늘 오디오 믹스를 붙여, 내보낸 MP4의 소리는 섞인 트랙 하나다(§18에서 바뀜, 이전에는 100%뿐이면 믹스가 없어 트랙이 레인마다 따로 써졌다). 내보내기 검증은 소리 트랙이 하나(소리가 없으면 0)가 아니면 승격하지 않는다. (§20에서 바뀜: 음량은 레인 음량 × 클립 음량 × 클립 페이드의 선형 경사.)
- 정규화·리미터가 없다. 여러 레인의 합이 크면 내보낸 소리가 잘릴 수 있다(정보 패널에 안내).
- 구성(관찰에 따른 선택): 레인마다, 원본의 (표본율, 채널 수)마다 소리 트랙을 하나 두고, 클립 밖 구간은 같은 모양의 무음 원본(임시 폴더의 16비트 PCM WAV 10초, 사용자 미디어 아님)으로 채운다. 빈 편집을 쓰면 이 Mac에서 44.1 kHz 구간이 빈 편집 길이에 비례해 앞당겨졌고(80/30 s 뒤 −161표본), 다른 모양의 무음 뒤에서는 −59표본 앞당김이나 스테레오 √2배가 나타났다. 지금 방식에서 클릭 위치는 ±1표본이다. 이 변경은 영상 파일 소리의 빈틈에도 적용된다.

**프로젝트 형식 버전 2:**

- 더한 것: 레인 목록의 임의 순서·개수, 오디오 레인 `muted`·`volumePercent`(정수), 클립의 `lane`(레인 ID), 미디어의 `hasVideo`·`sampleRate`·`sampleCount`·`channels`. 시각은 여전히 정수 프레임과 정수 표본이며 부동소수점이 없다.
- 버전 1 파일: 레인 2개, 클립에 레인이 없으면 그 종류의 첫 레인, 음소거 없음·음량 100%, 영상 있음으로 읽는다. 잃는 것이 없고, 다시 저장하면 버전 2다.
- 검사 추가: 음량 0–100, 영상 레인이 오디오 레인 위, 각 종류 하나 이상, 클립이 자기 종류의 레인에 있음, 영상 클립은 영상 있는 미디어만.
- 북마크·상대 경로·재연결·원본 보호·저장하지 않은 변경·최근 목록은 소리 파일에도 같다. 재연결은 영상 클립이 쓰면 영상, 소리 클립이 쓰면 소리가 있어야 한다. 찾을 수 없는 소리 원본은 주황 빗금 "원본 없음"으로 빈틈과 구별하고 내보내기를 막는다.

**한계:**

- MP3는 이 Mac에서 만들 수 없어(afconvert에 MP3 인코더 없음) 생성 fixture로 검증하지 않았다. 검사 코드는 MP3를 받지만 실제 MP3 파일의 시각·길이는 미확인이다.
- 파형 표시, 페이드, 효과, 정규화·리미터, 레인 단위가 아닌 클립 음량, 소리 클립과 영상 클립의 새 연결(다른 원본)은 없다.
- 소리 파일만 있는 프로젝트는 내보낼 수 없다(영상 원본 필요).
- 연결된 쌍의 레인 바꾸기는 끌기로 하지 않는다(정보 패널).
- 리플 트림 규칙 때문에 다른 레인 클립 위에 겹친 클립의 끝 트림은 대개 거부된다(자르기 + 일반 삭제를 쓴다).
- 미디어 목록 → 타임라인 끌어 놓기는 자체 검사에서 실제 끌기 세션 대신 놓은 위치 해석을 직접 불렀다. 음량 슬라이더도 놓을 때의 동작을 직접 불렀다.
- 레인이 많을 때의 성능, 긴 소리 파일, 44.1·48 kHz 밖 표본율(8–192 kHz는 받음)의 시각은 짧은 생성 fixture 밖이라 미확인이다.
- A-010 프리뷰 경로 프레임 0 불일치와 E2 사용자 정의 합성기 문제는 따로이며 미해결이다.

**소유자 확인 목록(짧게):**

1. 타임라인 위 "레인 추가"로 영상 레인을 더하고 레인 머리 문맥 메뉴 "위로"로 맨 위로 올린다. 그 레인에 영상을 끌어 놓아 아래 영상 위에 겹친다. 프리뷰에서 위 레인이 보이고, 위 레인의 빈틈에서 아래 레인이 보이는지 본다. 내보낸 MP4도 같은지 본다.
2. WAV·MP3·M4A 같은 소리 파일을 가져와 레인 아래 빈 곳에 끌어 놓는다. 파일 이름의 새 오디오 레인이 생기는지 본다. 프리뷰·내보내기에서 원래 소리와 함께 들리는지 본다(실제 MP3는 처음 확인).
3. 오디오 레인 머리를 눌러 정보 패널에서 음량을 낮추고 음소거를 켠다. 프리뷰·내보내기 소리가 그에 맞는지, ⌘Z로 한 단계씩 돌아가는지 본다.
4. 클립이 있는 레인을 문맥 메뉴로 삭제한다. 확인이 나오고, ⌘Z로 되살아나는지 본다.
5. 저장하고 다시 열어 레인·순서·이름·음소거·음량이 그대로인지 본다. 이전에 저장한 프로젝트(형식 1)도 열리는지 본다.
6. 레인 이름을 한국어로 바꾸는 동안 Space·Delete·⌘K가 타임라인을 바꾸지 않는지 본다.

## 17. 영상 클립 크기·위치(A-015, 2026-10-11, 진행 중)

작업 승인 A-015(§16 작업 위에 커밋하지 않고 이어서), 동작 결정 D-025, 형식 D-023(버전 3). 구현 선택(소유자 미확인)은 [DECISIONS.md](../docs/DECISIONS.md) 감사 기록 2026-10-11(A-015)에 있다.

**좌표계(`ClipTransform`):**

- 출력 화면 1920×1080 픽셀, 원점은 왼쪽 위, X는 오른쪽·Y는 아래쪽이 +다.
- (§19에서 바뀜: 저장은 크기 백만분율 `scaleMicro`·위치 1/1000 픽셀 `offsetXMilli`·`offsetYMilli`, 형식 4. 아래 정수 설명은 형식 3.)
- 크기 `scalePermille`: 기본 맞춤(원본 전체가 화면에 들어가게 비율을 유지해 맞추고 가운데 둔 크기)에 대한 천분율 정수다. 1000 = 100%이고, 화면 가운데를 기준으로 키우거나 줄인다. 가로·세로 비율은 늘 원본 그대로다.
- 위치 `offsetX`·`offsetY`: 그 뒤 영상 가운데를 화면 가운데(960, 540)에서 옮긴 정수 픽셀이다.
- 기본값(1000, 0, 0)은 변형 없음이고 파일에 쓰지 않는다. 범위: 크기 1%–1000%, X ±7680, Y ±4320. 화면 밖은 잘린다.
- 예: 640×480 원본은 기본 맞춤이 1440×1080(x 240–1680)이다. 40%, +400, +200이면 576×432, 가운데 (1360, 740), x 1072–1648, y 524–956이다.

**조작:**

- 정보 패널 "화면 크기·위치"(§19에서 왼쪽 "클립 조정" 탭으로 옮김, 소수 입력): 크기(%, 소수 첫째 자리)·X·Y 입력(Return이면 한 단계), 크기 ± 단추(5%씩), "크기·위치 초기화"(한 단계). 소리 클립을 골랐으면 연결된 영상의 값을 보인다. 소리 클립에는 변형이 없다.
- 프리뷰: 선택한 영상 클립(또는 고른 소리 클립의 연결된 영상)이 재생 헤드 위치에 있으면 영상 사각형에 테두리와 네 모서리 손잡이가 보인다.
  - 테두리 안쪽 끌기: 옮기기. 모서리 끌기: 반대 모서리 고정, 비율 유지 크기 조절.
  - 끌기 하나가 한 단계이고, 끌기 중 Esc는 끌기 전으로 돌린다(기록 없음).
  - 보기 좌표는 프리뷰 영역에 비율을 유지해 맞춘 출력 화면 사각형(검은 여백 제외)으로 옮긴다. 배율 k = min(폭/1920, 높이/1080)이고, 프리뷰 크기를 바꿔도 같은 식이다.
  - 테두리는 화면 위 AppKit 보기일 뿐이라 composition·내보내기에 들어가지 않는다.
  - 끌기 중 프리뷰 화면은 앞 재구성이 끝난 뒤에만 다시 만든다(놓았을 때의 상태는 늘 반영). 끌기 중 잠깐 깜빡일 수 있다. (§18에서 고침: 끌기 중에는 항목을 바꾸지 않고 겹친 정지 화면을 그린다.)

**겹침 규칙:**

- 시간 구간마다 위 레인부터 클립을 쌓고, 출력 화면 전체를 덮는 클립에서 멈춘다. 위 영상은 변형된 영상 영역만 덮고, 그 밖에는 아래 레인이 보이며, 아무것도 덮지 않은 곳은 검정이다.
- 동작 변화: 16:9가 아닌 위 레인 영상은 변형이 없어도 여백에 아래 레인이 보인다(§16에서는 맨 위 클립이 여백까지 검정으로 덮었다).
- 구성: 쌓은 깊이마다 영상 트랙을 하나 두고 레이어 지시의 변형으로 그린다(AVFoundation 기본 합성기, 사용자 정의 합성기 없음). 프리뷰와 내보내기는 같은 `CompositionPlanner.plan`을 쓰고, 프리뷰 테두리도 같은 `CompositionPlanner.displayRect`로 계산한다. 변형이 없는 16:9 타임라인은 §16의 한 트랙 구성과 같다.
- 변형은 자르기(두 조각 모두)·옮기기·레인 옮기기·트림·끼워 넣기 이동에서 그대로다. 연결된 소리의 시각·위치는 바뀌지 않는다.

**저장 형식 버전 3:**(§19에서 형식 4로 바뀜) 영상 클립에 `"transform": {"scalePermille": 400, "offsetX": 400, "offsetY": 200}`(정수)를 쓴다. 버전 1·2 파일은 변형 없음으로 연다. 소리 클립의 변형과 범위 밖 값은 거부한다. 버전 2를 읽는 이전 빌드가 변형을 조용히 버리지 않도록 버전을 올렸다.

**고친 결함(§16 작업분):** 레인 순서 바꾸기를 두 칸 이상 하면 두 레인을 맞바꿔 사이 레인 순서가 바뀌었다. 빼서 끼우는 방식으로 고쳤다. 앱 UI는 한 칸씩만 옮겨 사용자에게는 나타나지 않았다.

## 18. 소유자 보고 편집 문제 수정(2026-10-11, §16·§17 위에 커밋하지 않고 이어서)

소유자가 보고한 네 가지(앞 빈틈, 끌기, 변형 끌기 깜박임, 레인 배치)를 고쳤다. 동작 지시는 소유자 요청이고, 아래 "구현 선택"은 소유자 미확인이다([DECISIONS.md](../docs/DECISIONS.md) 감사 기록 2026-10-11 편집 수정).

**1. 원치 않는 앞 빈틈 — 확인한 원인:**

- + 단추는 첫 영상 레인 끝이 아니라 **타임라인 길이(`durationFrames`) 끝**에 리플 삽입했다(`Timeline.inserting`, index nil). 일반 삭제(D-020)는 길이를 유지하므로, 클립을 지워 빈 타임라인도 길이가 남아 다음 추가가 그 끝에서 시작했다. 다른 레인 클립이 첫 영상 레인보다 길어도 같은 일이 생겼다. 엔진 검사가 이전 동작을 재현한다(길이 100이 남은 빈 타임라인에 삽입 → 100에서 시작).
- 연결된 쌍은 끌면 끼워 넣기 이동(리플)이라, 레인에 클립이 하나뿐이면 제자리 판정으로 아무것도 바뀌지 않아 앞 빈틈을 닫을 수 없었다(`moving(toIndex:)`가 0·1을 제자리로 봄).
- 끌어 놓기 좌표 변환(창 → 문서 보기, 가로 스크롤·확대 반영)과 고정 레인 머리 폭은 맞았다(확대 10, 스크롤 0·400에서 검사).
- 재생 헤드는 원인이 아니었다(+ 단추는 재생 헤드를 쓰지 않았다).

**고침:**

- + 단추(`Timeline.appending`): 고른 대상 레인(쌍)의 **마지막으로 차지한 끝 뒤**에 놓는다. 레인이 비었으면 0. 리플 없음, 재생 헤드와 무관, 기존 빈틈은 그대로다.
  - 대상: 레인 머리에서 고른 레인이 있으면 그 레인과 같은 번호의 짝(V2 ↔ A2, 짝이 없으면 기본 레인), 없으면 V1·A1. 소리 없는 영상은 영상 레인만, 소리 파일은 오디오 레인만.
- 끌어 놓기: 놓은 레인의 **놓은 시각**에 놓는다(끼워 넣기 없음, 겹치면 거부). 눈금자 위는 그 종류의 기본 레인(V1·A1). 끄는 동안 놓일 시각을 세로선으로 보인다.
  - 영상 파일의 연결된 소리: 같은 번호의 오디오 레인이 그 구간에서 비었으면 거기, 아니면 경계에서 가까운 빈 오디오 레인, 없으면 파일 이름의 새 오디오 레인(맨 아래).
- 기존 프로젝트의 의도한 빈틈은 바꾸지 않는다. 연결된 쌍도 끌어서 0으로 되돌릴 수 있다(아래 2).

**2. 자연스러운 끌기:**

- 일반 끌기는 연결 여부와 관계없이 **옮기기**(`relocating`)다. 연결된 영상·소리는 함께, 상대 위치(어긋남 포함) 그대로 옮긴다. 원래 자리는 빈틈이 되고 다른 클립은 움직이지 않는다.
- 어느 레인에서든 겹치면 묶음 전체를 옮기지 않는다(빨간 제안 위치, 놓으면 상태 줄에 이유). 묶음의 가장 이른 시작은 0보다 앞서지 않는다.
- 끼워 넣기 이동은 일반 끌기·놓기에서 뺐다(엔진 API·이전 자체 검사의 저장소 경로로만 남김). 메뉴 동작은 만들지 않았다.
- 끄는 동안: 놓을 수 있으면 클립이 새 자리에 그려지고 원래 자리는 점선, 놓을 수 없으면 묶음 모두의 제안 위치가 빨강.
- 붙음: 0과 다른 클립(모든 레인)의 시작·끝에 화면 8pt 안이면 붙고 노란 안내선을 보인다. 거리는 반올림 전 포인터 위치로 잰다(확대가 커도 같은 화면 거리).
- 위아래로 끌면 같은 종류의 다른 레인으로(끈 클립만, 연결된 짝은 자기 레인에 남음). 짝의 레인은 정보 패널 고르기로 바꾼다.
- 끌기 하나가 한 단계, Esc는 끌기 전으로. 바뀐 것이 없거나 취소하면 프리뷰를 다시 만들지 않는다.
- 히트 판정·좌표는 문서 보기 좌표라 확대·가로 스크롤과 무관하다(확대 9, 스크롤 150에서 검사).

**3. 변형 끌기 깜박임 — 확인한 원인:**

- 끌기 중 마우스가 움직일 때마다 composition을 다시 만들고 AVPlayer 항목을 바꿨다(`replaceCurrentItem`). 새 항목의 첫 프레임이 준비될 때까지 AVPlayerLayer가 비어 검정이 보였다.
- 자체 검사로 재현(이전 경로를 Debug 전용 플래그로 남김): 같은 8단계 끌기에서 항목 교체 9번, 4 ms 간격 표본 중 빈 화면(정지 화면 없음·`isReadyForDisplay` 거짓) 51–52/321–324.

**고침:**

- 끌기 중에는 항목을 바꾸지 않는다. 끌기를 시작할 때 재생 헤드 시각에 보일 수 있는 영상 원본 프레임(모든 영상 레인에서 그 시각을 덮는 클립)을 한 번 디코딩해 두고(`InteractivePreview`), 마우스가 움직일 때마다 같은 쌓음·변형 해석(`CompositionPlanner.layeredSegments`·`layerTransform`)으로 겹친 화면을 그려 프리뷰 위 정지 화면 층에 보인다. 테두리만 옮기는 것이 아니라 실제로 겹친 그림이다. 요청이 밀리면 마지막 것만 그린다.
- 놓으면 최종 상태로 한 번 다시 만들고, 새 항목이 현재 항목이고 표시될 준비가 되면(`AVPlayerLayer.isReadyForDisplay`) 정지 화면을 내린다. 그동안 마지막 그림을 유지한다. 늦게 끝난 그리기는 회차 번호로 버린다.
- 정보 패널의 크기·위치 입력도 같은 방식(새 상태 정지 화면 → 다시 만들기 → 준비되면 내림)이다. (§19: 정지 화면은 GPU 레이어 무대로 바뀌고, 입력 칸은 왼쪽 "클립 조정" 탭으로 옮김.)
- Esc: 변형을 끌기 전으로 돌리고 정지 화면만 내린다(항목은 끌기 전 그대로라 다시 만들지 않음). 재생 헤드는 그대로, 끌기를 시작하면 재생을 멈춘다.
- 임의 지연이나 검사 완화는 쓰지 않았다.

## 19. 변형 끌기 부드러움과 패널 재배치(2026-10-11, §18 위에 커밋하지 않고 이어서)

소유자 관찰(그대로 기록): 바뀐 테두리 동작은 되지만, 프리뷰 손잡이로 크기를 바꾸면 정보 패널 입력보다 계단처럼 끊겨 느껴진다. 조정 칸은 미디어 목록 옆 새 탭에, 오른쪽 패널은 클립 정보로 두기를 원한다. 이 관찰이 이전 검사 전체의 통과를 뜻하지는 않는다.

### 19.1 변형 끌기

**측정 방법:** `scripts/transform-perf-test.sh`(Debug 자체 검사 `-OTFTransformPerfTest`). V1 otf-TA, V2 otf-TB(50%) 위에서 프리뷰 테두리의 오른쪽 아래 손잡이 크기 조절과 안쪽 옮기기를 합성 포인터 100번(약 8 ms 간격, 2 pt씩)으로 끈다. 포인터 처리 시간, 끌기 그림을 무대에 넣은 시각·값, 주 실행 루프 바쁜 시간(실행 루프 관찰자)을 잰다. 합성 이벤트 측정이며 손으로 끄는 느낌을 대신하지 않는다. "지연"은 포인터 이벤트에서 무대 레이어 갱신까지이고, 창 서버 합성(다음 화면 갱신)은 포함하지 않는다.

**확인한 원인(바꾸기 전 빌드, 2회 측정 + `sample`로 끌기 중 주 스레드 3초):**

- 끌기 중 주 스레드가 92–94% 바빴고, 한 번에 16.7 ms를 넘긴 실행 루프가 크기 조절 67–75번·옮기기 22–28번이었다(0.8초 끌기). 포인터 처리 자체는 0.1 ms였다.
- 주 스레드 표본(876개)의 약 22%: 매번 새로 그린 1920×1080 그림을 레이어 내용으로 넣을 때 Core Animation이 화면 색 공간으로 바꾸는 vImage 변환(`CA::Render::prepare_image` → `vImageConvert_AnyToAny`)이 그림마다 주 스레드에서 돌았다.
- 약 22%: 포인터가 움직일 때마다 편집 기록(관찰되는 타임라인)을 바꿔, 타임라인을 읽는 모든 SwiftUI 보기를 다시 계산했다(AttributeGraph 갱신).
- 약 9%: 그때마다 타임라인 보기와 레인 머리를 다시 그렸다(보이는 내용은 그대로).
- 주 스레드 밖: 그림마다 Core Graphics로 1920×1080 전체를 다시 그렸다(평균 12–15 ms, 최대 35 ms). 그래서 그림은 평균 21–23 ms(최대 44 ms) 간격으로 늦게(평균 39–45 ms, 최대 73 ms) 바뀌었고, 화면 갱신 사이 테두리 너비가 한 번에 6.3 pt까지 뛰었다(포인터는 2 pt씩).
- 값 반올림: 끌기마다 위치를 정수 출력 픽셀, 크기를 0.1%로 반올림했다. 시작 값에서 다시 계산해 쌓이는 오차는 없었고 화면에서 0.4 pt 정도라 끊김의 주원인은 아니었지만, 소유자 지시대로 소수로 바꿨다.

**바꾼 것:**

- 끌기 무대(GPU): 끌기를 시작할 때 재생 헤드 프레임의 원본 프레임을 한 번 디코딩해 두고(이전과 같음), 프리뷰 위 무대에 원본마다 CALayer 하나를 둔다. 끌기 중에는 내용(디코딩한 프레임)을 바꾸지 않고 레이어 변형만 바꾼다. 쌓음·변형은 내보내기와 같은 `CompositionPlanner.layerStack`(이번에 `layeredSegments`에서 나눔)·`layerTransform`이다. 캔버스는 출력 화면 1920×1080을 AVPlayerLayer의 resizeAspect와 같은 사각형에 맞추고 밖을 자른다. 프레임마다 그림을 새로 만들거나 색을 다시 바꾸지 않는다.
- 화면 갱신마다 한 번: 포인터 이벤트는 최신 값만 남기고(`CADisplayLink`), 화면 갱신마다 그 값을 무대와 테두리에 함께 넣는다. 놓을 때는 놓은 위치의 값을 바로 넣고 끝낸다.
- 편집 기록은 놓을 때만: 끌기 중 값은 관찰하지 않는 `gestureTimeline`과 조정 칸 표시용 `liveTransform`에만 두고, 놓을 때 그 값으로 한 단계를 기록한다. 끌기 중 SwiftUI 보기·타임라인 다시 그리기가 없다. Esc는 무대만 내린다(항목·기록 그대로).
- 소수 변형과 저장 격자: 포인터 값은 소수(보기 pt ÷ 배율 k)로 계산하고 `ClipTransform`의 정수 격자 — 크기 백만분율(`scaleMicro`, 0.0001%), 위치 1/1000 출력 픽셀(`offsetXMilli`·`offsetYMilli`) — 로만 맞춘다. 모서리 크기 조절은 크기를 격자로 맞춘 뒤 가운데를 계산해 반대 모서리가 0.001 px 안에서 고정된다. 끌기 중 보인 값 = 놓은 값 = 저장 값.
- 프로젝트 형식 4: 위 세 정수를 저장한다. 형식 3 이전 파일의 `scalePermille`·`offsetX`·`offsetY`는 같은 값으로 읽고, 다시 저장하면 형식 4다. 형식 3을 읽는 이전 빌드는 형식 4 파일을 "더 새로운 버전"으로 거부한다(새 키를 모른 채 열지 않음).
- 끝맺음: 놓으면 무대를 띄운 채 최종 composition을 한 번 다시 만들고, 새 항목이 표시될 준비가 된 뒤 무대를 내린다(§18과 같음). 정보 패널(이제 "클립 조정" 탭) 입력도 같은 무대를 쓴다.
- 고친 결함(이번 작업 중 발견): 첫 구현에서 `done?(show(t))`처럼 선택적 호출의 인자로 그리기를 넣어, 완료 처리가 없는 끌기 요청은 그리기가 아예 불리지 않았다(Swift는 nil이면 인자를 계산하지 않음). 측정에서 "보인 갱신 0"으로 드러나 고쳤다.

## 20. 소리 클립 음량·음소거·페이드(2026-10-11, §19 위에 커밋하지 않고 이어서)

동작 결정 D-026, 형식 D-023(버전 5). 같은 날 소유자가 형식 4와 그 변형 정밀도(§19)를 구현대로 승인했다. 표현·제한 규칙·트림 동작·화면 구성은 구현 선택(소유자 미확인)이며 [DECISIONS.md](../docs/DECISIONS.md) 감사 기록 2026-10-11(소리 클립 음량·페이드)에 있다.

### 20.1 모델과 소리 해석

- 소리 클립마다 `ClipAudio`: 클립 음량(정수 0–100%, 레인 음량과 같은 단위, 기본 100), 클립 음소거(기본 아님), 페이드 인·아웃(기본 0). 영상 클립에는 없다. 연결된 쌍의 영상 클립을 고르면 그 소리 클립에 적용한다(`Timeline.audioTarget`).
- 실제 크기(진폭 배율) = 레인 음량 × 클립 음량 × 페이드 모양. 레인·클립 어느 쪽이든 음소거면 0. 최대는 원래 크기(100%)이고 정규화·리미터는 없다.
- 페이드는 선형 진폭이다. 시간 단위는 타임라인 프레임(1/30 s)이라 자르기·트림 지점과 같은 격자다. 초 입력은 가장 가까운 프레임으로 맞춘다(0.05초 → 2프레임 = 0.0667초).
  - 페이드 하나 = (경사 전체 길이 `length`, 건너뛴 앞부분 `offset`). 페이드 인: 클립 시작에서 t 프레임 지난 곳의 배율 min(1, (t + offset)/length). 페이드 아웃: 끝까지 r 프레임 남은 곳의 배율 min(1, (r + offset)/length). 보통 페이드는 offset 0(무음에서 시작·무음으로 끝).
  - 보이는 길이 = min(length − offset, 클립 길이). 페이드 인·아웃의 보이는 길이 합은 클립 길이 이하(겹치지 않음). 잘못된 값의 파일은 열지 않는다.

**편집 규칙(결정적):**

| 편집 | 소리 설정 |
| --- | --- |
| 옮기기(같은·다른 레인), 끼워 넣기 이동, 리플로 밀림 | 그대로 |
| 자르기(k 프레임에서) | 음량·음소거는 두 조각 모두 그대로. 페이드 인은 클립 시작에 붙은 경사라 왼쪽 조각은 그대로, 오른쪽 조각은 경사의 앞 k 프레임을 건너뜀(offset + k). 페이드 아웃은 끝에 붙은 경사라 오른쪽 조각은 그대로, 왼쪽 조각은 뒤 (길이 − k) 프레임을 건너뜀. 남는 경사가 없으면 그 페이드는 없음. → 두 조각을 이은 소리 모양 = 자르기 전 모양(새 페이드 없음, 페이드 복사 없음). 페이드 밖에서 자르면 두 조각 모두 자른 곳에 페이드가 없다 |
| 트림(앞·뒤 가장자리) | 페이드는 자기 가장자리에 붙어 길이·offset 그대로 따라간다. 짧아져 겹치면 페이드 인을 두고, 페이드 아웃을 남은 길이(클립 길이 − 페이드 인 보이는 길이)의 보통 페이드로 줄인다. 페이드 안에서 자른 왼쪽 조각을 다시 늘리면 원래 경사가 이어진다 |
| 페이드 길이 입력·손잡이 | 보통 페이드(offset 0)가 되고, 다른 쪽 페이드를 침범하지 않게 (클립 길이 − 다른 쪽 보이는 길이)로 줄인다. 0이면 없음. 자른 조각의 부분 페이드를 다시 정하면 무음에서 시작하는 보통 페이드가 된다 |
| 실행 취소·다시 실행 | 타임라인 스냅샷이라 모든 값이 정확히 돌아온다 |

**프리뷰·내보내기:** 같은 `CompositionPlanner.plan`의 오디오 믹스(프리뷰 항목과 내보내기 세션에 같은 것)를 쓴다. 소리 트랙마다 클립의 꺾이는 점(시작·페이드 인 끝·페이드 아웃 시작·끝) 사이를 선형 음량 경사(`setVolumeRamp`)로 넣는다. 내보낸 MP4는 여전히 섞인 소리 트랙 하나다(§18).

- 관찰(이 Mac): 한 트랙의 음량이 끊어지는 곳(앞 경사 끝 값 ≠ 다음 경사 시작 값)에서 AVFoundation이 그 시각부터 약 512표본(48 kHz에서 10.7 ms) 동안 혼자 선형으로 옮겨 갔다(자른 곳 0.16 → 0.08이 72000표본에서 시작해 약 72500표본에 끝남). 그대로 두면 자른 곳 계단이 흐려지고, 앞 클립 음량이 다음 클립 페이드 인 머리에 새어 들어간다.
- 그래서: 음량이 끊어지며 맞닿은 클립은 다른 소리 트랙에 번갈아 넣고(같은 표본율·채널 묶음 안에서 트랙 둘까지, `volumeTracks`), 클립 사이 무음 구간에는 다음 클립의 시작 값을 미리 둔다(첫 값도 첫 클립의 시작 값). 각 트랙에서 음량이 끊어지는 곳은 무음 구간뿐이라 옮겨 가는 동안 소리가 없다. 끊어짐이 없는 레인(이전 파일, 모든 클립 기본값)은 이전과 같은 트랙 구성이다.

**저장(형식 5):** 소리 클립에 `"audio": {"volumePercent": 55, "muted": true, "fadeIn": {"length": 40, "offset": 15}, "fadeOut": {"length": 0, "offset": 0}}`. 기본값 클립은 `audio`를 쓰지 않는다. 형식 1–4 파일은 클립 기본값으로 열고 소리가 그대로다(레인 음량·음소거 그대로). 형식 4를 읽는 이전 빌드는 형식 5 파일을 "더 새로운 버전"으로 거부한다(클립 음량·페이드를 모른 채 열고 다시 저장해 잃지 않게).

### 20.2 화면

- 왼쪽 "클립 조정" 탭에서 소리 클립(또는 연결된 소리가 있는 영상 클립)을 고르면 "이 클립만 — 클립 소리"(영상 클립이면 "연결된 소리 클립만 — 클립 소리") 묶음: "클립 음소거" 체크 상자, "클립 음량" 슬라이더·숫자 칸(%), "페이드 인"·"페이드 아웃" 초 칸(소수 둘째 자리, Return을 누르면 한 단계, 누르지 않고 다른 곳을 고르면 입력은 버림). 자른 조각의 부분 페이드는 "원래 페이드의 뒷부분(50%에서 시작)"처럼 덧붙인다. 아래에 "레인 전체: A1 · 원본소리 — 음량 80%"와 "레인 조정…" 단추(레인 머리를 고름), "실제 크기 = 클립 음량 × 레인 음량 × 페이드".
- 레인 머리를 고르면 "레인 전체 — A1의 모든 클립" 묶음: "레인 음소거", "레인 음량". 클립을 골랐을 때는 레인 칸이 없고, 레인 머리를 골랐을 때는 클립 칸이 없다(§19에서는 클립을 고르면 그 레인의 음량 칸이 보였다).
- 음량 슬라이더(클립·레인)는 AppKit 보기(`GainSlider`)다. 끌기 중에는 값만 보이고 놓을 때 한 단계로 기록하며, 끌기 중 Esc는 시작 값으로 되돌리고 기록하지 않는다(SwiftUI Slider는 끌기 중 키를 받지 못했다). 손쉬운 사용의 증가·감소는 1%씩 한 단계다.
- 타임라인 소리 클립: 노란 선은 클립 음량 × 페이드 모양(레인 음량은 레인 머리에 따로 보임), 줄어든 부분은 어둡게, "클립 50%"·"클립 음소거" 표. 고른 소리 클립(연결된 쌍의 소리 포함)에는 위쪽에 흰 사각 페이드 손잡이 둘(페이드 인 끝·페이드 아웃 시작 위치, 커서 십자). 손잡이는 트림·옮기기보다 먼저 받고(손잡이 둘레 6 pt), 끄는 동안 "페이드 아웃 1.5초"를 보인다. 끌기 하나 = 한 단계, Esc는 끌기 전으로. 프리뷰 소리는 놓을 때 다시 만든다.
- 오른쪽 "클립 정보"(읽기 전용)에 "클립 소리: 클립 음량 50% · 페이드 인 1.5초 · 페이드 아웃 1.5초"(연결된 영상을 골랐으면 "연결된 소리 클립의 소리").
- 키보드: 페이드·음량 칸 편집 중에는 필드 편집기가 첫 응답자라 Space·⌘K·Delete 등을 가로채지 않는다(기존 KeyRouting 규칙, 한국어 조합 포함).

### 20.3 검증(2026-10-11, 이 Mac)

기대값은 구현 함수를 쓰지 않고 손으로 쓴 구간식(원본 진폭 × 레인 음량 × 클립 음량 × 선형 페이드)에서 계산했다. 소리는 새 생성 fixture `aud-steady48s.wav`(48 kHz 스테레오 6초, 1000 Hz 사인 진폭 0.2, 클릭 없음)를 원본 위치 = 타임라인 위치로 놓아 위상이 이어지게 하고, 48표본(1 ms, 한 주기) 창의 사인 진폭으로 쟀다(내보내기 AAC는 480표본 창).

- 엔진 테스트 80개 중 실패 0, 건너뜀 1(기존 MP3). 새 `ClipAudioTests` 9개:
  - 자른 두 조각 중 하나의 음량·음소거만 바뀌고 다른 조각·레인은 그대로, 범위 밖 음량 거부.
  - 레인 80% × 클립 50% × 페이드 인 30·아웃 20: 시작·가운데·끝 배율(0, 0.2, 0.4, 0.2, …) 1e−12 안. 클립 음소거·레인 음소거 따로(레인을 풀어도 클립 음소거 남음).
  - 페이드 인 40·아웃 30인 90프레임 클립을 1–89 모든 프레임에서 자르고, 0.25프레임마다 두 조각의 배율 = 자르기 전 손 계산 배율(1e−12). 페이드 밖에서 자르면 자른 곳에 새 페이드 없음. 페이드 안 세 번 자르기도 같음.
  - 트림: 앞 트림 뒤 페이드 그대로, 길이 50으로 줄이면 페이드 아웃 30 → 10, 길이 5면 페이드 아웃 없음, 페이드 안에서 자른 왼쪽 조각을 늘리면 원래 경사가 이어짐. 입력 제한(페이드 인 100 → 60, 페이드 아웃 50 → 30).
  - 연결된 쌍: 영상 클립 id로 소리 클립에 적용, 영상 클립에는 없음, 옮기기 뒤 그대로, 실행 취소·다시 실행이 정확히 같은 스냅샷.
  - 형식 5 저장·다시 읽기(같은 타임라인, 기본값 클립은 `audio` 없음), 손으로 만든 형식 4 파일은 클립 기본값·레인 음량 그대로, 겹치는 페이드 파일 거부.
  - 기본값 클립(이전 파일)은 트랙 나눔 없이 레인 음량 그대로의 경사(이전 구성과 같음), 끊어지며 맞닿은 클립만 트랙을 번갈아 씀.
  - 프리뷰 입력(같은 composition·오디오 믹스를 PCM으로 섞어 읽음)과 내보내기(MP4 디코딩): 배치 A1(레인 80%) 페이드 인 30을 45에서 자르고 오른쪽 조각 50%·페이드 아웃 15, A2 레인 음소거, A3(레인 50%) 클립 60%와 클립 음소거. 손 계산 진폭과 최대 차 프리뷰 0.00004, 내보내기 0.00024(200표본마다, 경계 근처 제외). 자른 곳(72000표본): 앞 96표본 최대 0.16001, 바로 다음 96표본 최대 0.08000(표본 단위 계단). 페이드 아웃 끝 뒤·음소거 클립·음소거 레인은 0.0005 미만. MP4 소리 트랙 1개. 저장·다시 열기 뒤 같은 PCM.
  - 페이드 안 두 곳(30·80)에서 자른 세 조각과 자르기 전 한 클립의 프리뷰 PCM 최대 차 8.8e−6, 손 계산 진폭 0.002 안. 옮긴 조각은 같은 모양.

## 21. 소유자 보고 회귀: 프로젝트 열기·가져오기 멈춤(2026-10-11, §20 위에 커밋하지 않고 이어서)

소유자 보고(최신 빌드): 이전에 저장한 프로젝트가 열리지 않는다, 미디어 열기 패널 위 설명이 지나치게 길다, 전에 쓰던 MP4 두 개를 가져오면 "0/2개 확인 완료"와 첫 파일 이름에서 멈춘 것처럼 보인다, 길이를 모르는 진행 표시가 일부 채워진 백분율 막대처럼 보인다.

### 21.1 확인한 것(이 Mac, 생성 파일)과 가설

**확인함:**

- 미디어 검사(`MediaProbe.inspect`)의 프레임 표시 시각 분석이 `AVAssetReader`로 영상의 압축 샘플을 처음부터 끝까지 모두 읽었다(디코딩은 없음). 이 Mac에서 생성한 3분 1080p30 H.264+AAC MP4(5 400샘플, 11 MB)의 검사가 66.6 s 걸렸고 그중 64.5 s가 이 읽기였다(샘플당 약 9–12 ms, 다시 재면 47–50 s). 4초 fixture도 2.5 s였다. 같은 파일에서 샘플 커서(`AVSampleCursor`, 샘플 표만 걷고 데이터를 읽지 않음)는 같은 5 400개 표시 시각을 0.001 s에 모았고 정렬한 값이 같았다.
- 가져오기는 파일 하나의 검사가 끝나야 "완료 수"가 늘고, 그동안 카드에는 첫 파일 이름과 "0/2개 확인 완료"만 보였다(단계·경과 시간 없음). 주 스레드는 막히지 않았다(유휴 CPU 0%, 주 스레드 이벤트 대기).
- 프로젝트 열기는 저장된 원본 미디어마다 같은 검사를 차례로 한 뒤에야 프로젝트를 바꿨고, 그동안 화면에 아무 표시가 없었다(진행 카드·취소 없음). 원본이 몇 분짜리면 그 시간 동안 "열리지 않는" 것처럼 보인다. 파일 읽기(`Data(contentsOf:)`)도 주 스레드에서 했다.
- 이 읽기 방식은 M1(`80e84b6`)부터 지금까지 모든 커밋에서 같다(이번 작업들이 바꾼 경로가 아님).
- 진행 카드의 "길이를 모르는 막대"는 움직이는 30% 조각이라 멈춘 화면이나 정지 그림에서는 일부 채운 백분율 막대와 구별되지 않는다.
- 형식 1(커밋 `44943ea`의 실제 저장기로 쓴 파일)과 형식 2–5는 메뉴 경로로 모두 열렸다(아래 검증). 버전 해석 실패는 재현되지 않았다.

**가설(확인하지 않음):**

- 소유자의 프로젝트가 "열리지 않음"은 위 원본 검사 시간(표시 없음) 때문이라는 것. 소유자의 실제 프로젝트·MP4로는 재현하지 않았다(세션에 경로가 주어지지 않아 찾지 않았다).
- "전에는 쓸 수 있었다"는 것과의 차이: 같은 코드였으므로, 파일이 더 길거나 이 Mac의 읽기가 지금 더 느린 것(측정 중 부하 평균 약 4, `AVURLAsset` 트랙 불러오기도 처음 1–6 s)일 수 있다. 이전 빌드에서 같은 파일을 잰 기록은 없다.
- 소리 파일(WAV) 검사도 처음 1–2.4 s 걸렸다(트랙·길이 불러오기, 이번에 고치지 않음).

### 21.2 고친 것

- 표시 시각 분석: 샘플 커서로 샘플 표의 표시 시각을 모은다(편집 목록 구간 안의 샘플만, 읽기 출력과 같은 범위). 커서를 줄 수 없는 트랙만 이전 읽기로 되돌아간다. 판정(같은 표시 시각 거부, 평균 1–240 fps, 고정·가변)은 그대로다. 3분 파일 검사 66.6 s → 3.2 s(그중 첫 파일 열기 3.2 s는 새 프로세스의 AVFoundation 첫 호출, 다음 파일부터 3 ms), 앱 안에서 3분 MP4 + 짧은 MP4 가져오기 0.5 s.
- 검사 단계 알림(`MediaProbe.Stage`): 파일 여는 중 → 형식 확인 중 → 프레임 시각 확인 중(읽기로 되돌아간 경우 읽은 프레임 수) → 끝. 진행률이 아니다.
- 가져오기 카드: 막대 대신 회전 표시(진행률 없음), 현재 파일 이름, "k/n개 확인 완료", "경과 0:12 · 프레임 시각 확인 중"처럼 경과 시간·현재 단계. 가운데 남색 카드·글자색은 그대로. 제목 "미디어 가져오는 중…"(소리 파일 포함).
- 프로젝트 열기: 파일 읽기는 주 스레드 밖에서, 진행 카드("프로젝트 여는 중…", 원본 이름, "원본 k/n개 확인 완료", 경과·단계)와 취소. 취소·실패하면 현재 프로젝트는 그대로이고, 늦게 끝난 확인 결과는 회차 번호로 버린다. 실패 알림에 이유와 "현재 프로젝트는 그대로입니다". 여는 동안 가져오기·내보내기·다른 열기는 기다리거나 거부한다.

## 22. 가져오기 전체 진행 막대(2026-10-11, §21 위에 커밋하지 않고 이어서)

소유자 지시는 [docs/DECISIONS.md](../docs/DECISIONS.md) "2026-10-11 가져오기 전체 진행 막대".

### 22.1 동작

- 막대: 카드 너비 전체의 바탕 위에 왼쪽부터 채운다. 값 = 처리한 파일 수(받아들임·거부 모두) ÷ 전체, 단 반영 전에는 (전체 − 1) ÷ 전체에서 멈춘다. 백분율은 내림(반올림으로 100%를 미리 보이지 않게). 두 파일: 처음 0%, 첫 파일 처리 뒤 50%, 두 번째 처리 뒤에도 반영 전까지 50%, 반영에 성공하면 100%.
- 파일 하나의 진행률은 넣지 않았다. 검사는 단계(파일 여는 중·형식 확인 중·프레임 시각 확인 중)만 알리고, 읽기로 되돌아간 경우의 읽은 프레임 수도 전체를 모르기 때문이다. 대신 현재 파일 이름 옆에 작은 회전 표시를 둔다(막대와 따로). 그 아래 "k/n개 처리", 맨 아래 "경과 0:03 · 단계"와 취소.
- 100%: 묶음을 반영하고 하나 이상 추가했을 때만 같은 가운데 카드에 "가져오기 완료 100%"와 "n/n개 처리 · 추가 a개(· 가져올 수 없음 r개 · 이미 있음 s개)", 경과 시간을 보인다(취소 단추 없음). 1.2 s 뒤 사라지고, 다음 가져오기·내보내기·열기가 시작되면 바로 사라진다. 이 1.2 s는 보이는 시간이지 진행률이 아니다.
- 완료 카드가 없는 경우: 취소(카드는 실제 백분율 그대로 "가져오기 취소하는 중…" 뒤 사라짐), 모두 거부(추가 0, 거부 알림만), 버리기·창 닫기.
- 그대로인 것: 묶음 단위 반영(끝나기 전에는 목록에 넣지 않음), 회차 번호로 늦은 결과 버리기, 가져오기·내보내기 차례 실행, 가운데 불투명 남색 카드와 글자색, 주 막대에는 움직이는 조각이 없다(시계는 경과 시간 표시에만 쓴다).

## 24. 프로젝트 열기 ↔ 저장하지 않은 변경 확인 흐름 수정(2026-10-11, 커밋하지 않음)

소유자 보고: 작업 중 "프로젝트 열기…"가 열기 패널을 믿을 만하게 띄우지 않는다. 확인에서 "저장"을 고르면 저장 패널도, 이어지는 열기 패널도 안 보일 수 있다.

### 24.1 재현과 원인(실제 메뉴·확인 시트·패널, 이 Mac)

- 재현(자체 검사 `-OTFOpenFlowTest`, 고치기 전 코드): 변경 없는 프로젝트에서는 열기 패널이 보였다. 확인 시트에서 "저장 안 함"을 누르면 열기 패널이 runModal 되었지만 보이지 않은 채 약 0.04 s 만에 끝났고(진단 기록 `open panel response=-2`), "저장"을 누르면(제목 없음) 저장 패널이 같은 방식으로 곧바로 끝나(저장 기록 `panel response=-2`) 저장 취소로 처리되어 열기도 멈췄다.
- 원인: 확인 시트의 단추 처리기(시트가 창에서 떨어진 뒤 알림 표시기가 부름) 안에서 바로 저장·열기 패널을 runModal 했다. 그 호출 스택 안에서는 패널이 나타나지 않고 OK·취소가 아닌 값으로 끝났다. 처리기를 다음 주 대기열 차례로 옮기면 패널이 정상으로 보였다(아래 검증에서 11번 모두 시트가 사라진 것을 확인한 첫 차례에 이어짐, 마감 대체 0번). 왜 그 스택 안에서 패널이 바로 끝나는지(시스템 내부)는 확인하지 않았다.
- 함께 찾은 결함(8b01322에서 들어감): 열기 패널을 취소하거나 OK가 아니면 열기 요청 상태(`openRequested`)를 끝내지 않고 돌아가, 그 뒤 모든 열기·새 프로젝트가 "프로젝트를 바꿀 수 없습니다"로 거부되고 가져오기·내보내기가 대기열에 멈췄다.

### 24.2 고친 것(`ProjectStore.swift`)

- 확인 시트의 "저장"·"저장 안 함"·"취소" 처리를 `afterSheetSettles`로 잇는다: 알림 표시기가 시트가 창에서 떨어진 뒤 부르는 처리기에서, 다음 주 대기열 차례(그 뒤 20 ms마다)에 편집기 창에 붙은 시트·보이는 시트 창·앱 모달이 하나도 없는 것을 확인한 뒤에만 고른 동작을 한다. 창 닫기·종료·새 프로젝트 확인도 같은 경로다.
- 2 s 안에 사라지지 않으면 고른 동작(저장·저장 안 함)을 **하지 않고** 취소와 같게 멈춘다: 현재 프로젝트·변경 그대로, 열기 요청 상태를 풀고, 상태 줄과 알림("작업을 계속할 수 없습니다")으로 알리며 진단 기록(error)에 남긴다. 이어짐과 중단은 합쳐 한 번만 일어난다(완료 표시, 늦은 확인 콜백은 무시).
- 열기 패널의 모든 끝(취소·OK 아님·파일 없음)에서 열기 요청을 끝낸다(`open ended without a file (panel cancelled)` 기록).
- 동작: 변경 없음 → 열기 패널. 변경 + 저장 안 함 → 열기 패널. 변경 + 저장(제목 없음) → 저장 패널, 저장에 성공한 뒤에만 열기 패널. 변경 + 저장(저장된 프로젝트) → 같은 파일에 저장 후 열기 패널(저장 패널 없음). 확인 취소·저장 패널 취소·저장 실패 → 열기 없음, 현재 프로젝트 그대로. 열기 패널 취소 → 현재 프로젝트 그대로. 고른 프로젝트는 기존 읽기·확인을 통과한 뒤에만 현재 프로젝트를 바꾼다(그대로).
- Debug 전용: `panelWillRunForTest`(실제 저장·열기 패널을 runModal 하기 직전에 넘김).

## 25. 타임라인 클립 복사·붙여넣기(2026-10-11, 커밋하지 않음)

소유자 승인 순서(복사·붙여넣기 → 자막 → 오디오 스펙트럼 → 프로젝트 보호·배포 검증)의 첫 항목. 잘라내기·자막·스펙트럼은 하지 않았다.

### 25.1 규칙

- **고르기:** 기존 단일 선택 그대로. 복사 대상은 고른 클립과 그 연결된 짝(타임라인에서 함께 강조되는 묶음)이다. 여러 개 선택·레인 전체 복사는 없다.
- **복사(⌘C, 편집 > 복사하기):** 앱 안 클립 클립보드에 클립 값(미디어·원본 구간·길이·레인·연결·크기·위치·음량·음소거·페이드)을 담는다. 프로젝트를 바꾸지 않고 실행 취소 기록도 없다. 고른 클립이 없으면 아무것도 하지 않고 경고음만 낸다(클립보드도 그대로).
- **붙여넣기(⌘V, 편집 > 붙여넣기):** 묶음의 가장 이른 시작을 재생 헤드에 두고 묶음 안 상대 위치를 그대로 지킨다(어긋난 연결 쌍의 어긋남 포함). 재생 헤드는 타임라인 끝을 넘지 않으므로 끝에 붙여 넣으면 타임라인이 늘어난다.
  - 새 클립 ID, 연결 쌍은 새 연결 ID(원래 클립과 연결되지 않고 따로 편집된다). 원본 파일은 그대로이고 미디어를 복사하지 않는다(같은 미디어를 참조).
  - 소리 설정은 그대로 복사해 들리는 모양이 같다(자른 페이드의 이어지는 경사 offset 포함).
  - **레인:** 원래 레인별로 대상 레인 하나. 차례: 원래 레인 → 같은 종류의 다른 레인(가운데 경계에서 가까운 순서) → 새 레인(경계 바깥쪽 끝, 이름 "영상"·"오디오"). 그 레인의 기존 클립과 겹치면 다음 레인을 본다. 기존 클립은 움직이거나 덮어쓰지 않는다(리플 없음).
  - 한 단계: 붙여넣기와 필요한 새 레인이 실행 취소 한 번에 함께 사라지고, 다시 실행으로 같은 상태가 된다.
  - 붙여 넣은 클립(복사할 때 고른 클립의 복제)을 고른다. 새 레인을 만들었으면 상태 줄에 알린다.
- **거부(바꾸지 않음):** 클립보드가 비었거나 다른 프로젝트 것, 미디어가 이 프로젝트에 없거나 원본 범위가 맞지 않음, 끌기 중, 프로젝트를 여는 중. 일부만 넣지 않는다.
- **프로젝트 바꾸기:** 새 프로젝트·열기로 프로젝트가 바뀌면 클립보드를 비운다(다른 프로젝트의 미디어·권한을 다루지 않는다). 다른 이름으로 저장은 같은 프로젝트라 그대로다.
- **텍스트 입력:** 텍스트 칸에 초점이 있으면 ⌘C·⌘V와 편집 메뉴 복사하기·붙여넣기는 표준 텍스트 동작이다(라우터가 이벤트를 넘기고 메뉴는 응답자 체인으로 보낸다). 편집 메뉴 항목은 텍스트에서 늘 쓸 수 있게 끄지 않고, 편집기에서 할 수 없으면 경고음과 상태 줄로 알린다. 오려두기·모두 선택은 텍스트 전용이다.
- 시스템 클립보드와는 따로다(다른 앱과 클립을 주고받지 않는다). 프로젝트 형식은 바꾸지 않았다(형식 5 그대로).
