> **상태 (2026-10-10):** 작업 승인 A-003으로 구현·실행했다. **E2는 완료가 아니다.** 소스 프레임 정확도 결함 1건이 해결되지 않았다(§5.4). 소유자 화면 관찰은 다섯 항목 모두 정성적 통과로 보고되었다(§8). 자동 프레임 정확도 증거가 아니며, 이 결함을 해소하지 않는다.
> - 헤드리스 검사(편집, 오프라인 합성기, 4K 내보내기와 디코딩, 출력 보호·취소·실패): **19/19 통과**

> - **관찰된 완화:** 프레임 타이밍을 비디오 트랙 샘플에서 얻도록 바꾼 뒤, 원래 재현 조건에서 이 현상이 다시 나타나지 않았다.
>   - 그 뒤 프리뷰 자동 검사 13회 중 12회가 8/8이었다.

>   - 프레임 2는 요청되지 않았다.

## 2. 재현 명령

`experiments/e2-4k` 디렉터리에서 실행한다.

```sh
cd experiments/e2-4k
swift build -c release                  # Release 빌드(E1Core 포함, 경고 0개 확인)
swift test                              # 단위 테스트 5개(Debug)
.build/release/e2 fixtures              # fixture 생성(없을 때만)·디코딩 검증 → results/e2-fixtures-<시각>.json
/usr/bin/time -l .build/release/e2 all  # 전체 헤드리스 검사 → results/e2-run-<시각>.json, 출력 artifacts/runs/<시각>/
/usr/bin/time -l .build/release/e2preview auto   # 프리뷰 자동 검사(창이 약 35초 뜸, volume 0) → results/e2-preview-<시각>.json
.build/release/e2preview diag-start     # 탐색 뒤 재생 시작 진단(창이 약 1분 뜸) → results/e2-diag-start-<시각>.json
.build/release/e2 inspect [--no-reorder]                 # 소스 압축 샘플 구조·composition 구간 대응 → results/e2-inspect[-noreorder]-<시각>.json
.build/release/e2preview diag-fresh [--pixels] [--frame-duration-timing]   # 새 프로세스 첫 재생 + 다시 재생, 첫 요청부터 기록 → results/e2-diag-fresh-*.json
.build/release/e2preview diag-source [--reps N] [--frame-duration-timing] [--no-reorder] [--waits] [--seeking-waits]
                                        # 시작 위치별 합성기가 받은 소스 프레임(층별) → results/e2-diag-source-<구성>-<시각>.json
.build/release/e2preview window         # 소유자 관찰 창(소리 켬). --muted, --smoke N(N초 재생 뒤 종료)
```

- 내보내기 전에 두 실험(E1·E2)의 `artifacts/`와 `.build/` 합계에 예상 추가량(128 MiB, 시작 전 256 MiB)을 더해 2 GiB를 넘으면 `budgetExceeded`로 멈춘다.
- 결과 JSON에는 E2 소스 트리 해시, 재사용한 E1 소스 트리 해시, 실행 파일 SHA-256을 남긴다.

## 4. 편집과 실제 영상 디코딩 경로

### 4.1 편집 (실험 범위: 비디오 트랙 1개, 빈틈 없는 하드 컷)

비디오 트랙 하나에 클립을 순서대로 놓는 하드 컷만 다룬다. **실험 범위의 제한이며 제품 제한이 아니다.** 클립 오디오는 클립과 함께 움직인다.

1. A, B, C를 붙인다(22 s).
2. A를 [30, 120)으로 트림한다.
3. 타임라인 150에서 B를 B.1/B.2로 분할한다.
4. B.2를 [150, 210)으로 트림한다.
5. C를 [20, 110)으로 트림한다.
6. C를 A 다음으로 이동한다.

| 타임라인 프레임 | 소스 | 컷 경계 |
| --- | --- | --- |
| [0, 90) | A 30…119 | |
| [90, 180) | C 20…109 | 89 A119 → 90 C20 |
| [180, 240) | B 0…59 (B.1) | 179 C109 → 180 B0 |
| [240, 300) | B 150…209 (B.2) | 239 B59 → 240 B150 (같은 소스 안의 분할·트림) |

- 길이 300프레임(10 s), 마지막 유효 프레임 299(B 209). 끝 시각 300은 D-018에 따라 299를 유지한다.
- 자막 3개(가로 정렬 왼쪽·가운데·오른쪽): [0.5, 2.5), [2.5, 5.5)(컷 90을 걸침), [7, 9)(컷 240을 걸침).
- 음악 M은 원본 [2, 11) s를 타임라인 1.0 s부터 놓는다(트림 + 오프셋).

### 4.2 composition과 합성기

- **composition:** 비디오 트랙 1개에 편집 구간마다 소스 영상의 실제 비디오 구간을 넣는다(`insertTimeRange`). 같은 구간의 소스 오디오는 클립 오디오 트랙에, 음악은 별도 트랙에 넣는다. 프리뷰(`AVPlayerItem`)와 내보내기(`AVAssetReaderVideoCompositionOutput`)가 같은 함수로 만든 composition·videoComposition을 쓴다.
- **프레임 타이밍(2026-10-10 수정):** `sourceTrackIDForFrameTiming` = 편집 비디오 트랙. 합성 요청 시각이 비디오 트랙 샘플에서 정해진다. 수정 전에는 `kCMPersistentTrackID_Invalid`(frameDuration 기반)였다(§5.3).
- **합성기 `E2Compositor`:** 합성 명령이 비디오 트랙을 요구한다(`requiredSourceTrackIDs`). 요청마다 디코딩된 소스 프레임(BGRA 4K)을 `request.sourceFrame(byTrackID:)`로 받아 출력 버퍼에 그대로 복사하고, 그 위에 다음을 그린다.
  - 타임라인 프레임 코드
  - 선택 오디오 스펙트럼 막대 32개
  - 자막
- **소스 라벨은 다시 그리지 않는다.** 화면의 소스 ID·프레임 번호는 디코딩된 소스 픽셀에서 나온다.
- **끝 유지(D-018):** 마지막 유효 프레임은 E1의 `FrameGrid`로 타임라인 길이에서 유도한다. 그 뒤 시각의 요청에는 composition 구성 때 미리 디코딩해 둔 마지막 유효 프레임의 소스 이미지를 쓴다. 빈 타임라인은 composition 구성에서 거부한다.
- **스펙트럼:** 음악 파일만 분석한 캐시를 쓴다. 클립 오디오는 오버레이에 전달되지 않는다.
- **소스 버퍼 시각 검사(2026-10-10 추가):**
  - 요청마다 받은 소스 버퍼의 `kCVBufferMovieTimeKey` 첨부를 요청 시각과 비교한다.
  - 다르면 합성기 오류로 기록한다. 받은 이미지를 바꾸거나 버리지 않으므로 결함을 덮지 않는다.
  - 첨부가 없으면 "판단 불가"로 센다. 이번 실행에서는 모든 요청에 첨부가 있었다.
- **동시성:** 요청 처리는 직렬 큐에서 한다. `cancelAllPendingVideoCompositionRequests`는 세대 번호를 올린 뒤 큐가 빌 때까지 블록한다(E1과 같은 규칙). 오버레이·명령은 불변이다.

### 4.3 측정

4K 프레임에서 다음을 읽는다.
- 코드 칸: 가운데 24×24 평균 밝기
- 이동 상자 위치
- 자막 3개 영역의 흰 픽셀
- 막대 높이
- 배경색

수정 전 결함은 이전 프레임을 받았다. 이 실패는 **앞선 프레임(t3의 소스)**을 받았고 요청 하나가 빠졌다. 형태가 다르다. 그 실행은 요청 순서·시작 시각·movie time 값·사건 기록을 남기지 않았기 때문에 더 나누지 못한다.

**제한된 재현 시도**(소스 트리 `5cbbf09649c6…`, 같은 원래 fixture, 프레임 타이밍 = 비디오 트랙):
- **새 프로세스 첫 재생 진단(`e2preview diag-fresh`):**
  - 실패한 실행과 같은 순서를 따른다: 로드 → 창 → 500 ms → 0으로 정확 탐색 → 재생 1.2 s.
  - 이어서 같은 프로세스에서 다시 재생(대조)한다.
  - 합성기 기록을 지우지 않고 첫 요청부터 다음을 남긴다: 요청 순서·시작·완료 시각, movie time, 취소·렌더 컨텍스트 사건, 비디오 출력 전달과 폴링 간격.
- **실행:**
  - 13개 프로세스(소스 픽셀 측정 없음 9, 있음 4)
  - 두 프로세스를 동시에 4쌍(자원 경쟁, 8개). 21개 시작 시 부하 평균 4.6~6.7
  - 결과: **21개 프로세스의 첫 재생 21회와 다시 재생 21회 모두** 첫 30프레임에서 요청 빠짐·시각 불일치·픽셀 불일치·전달 불일치·완료 순서 역전이 0이었다(`results/e2-diag-fresh-*-2026-10-10T0139*`~`T0141*`).
- **전체 자동 검사:** 같은 트리에서 4회(`…014125Z`, `…014158Z`, `…014231Z`, `…014423Z`) 모두 8/8.
- **수정 전 구성 대조**(`--frame-duration-timing`, `…013937Z`): 새 프로세스 첫 재생과 다시 재생 모두에서 t2가 A31·movie time 20/600을 받았다. 진단이 원래 결함을 잡는다는 대조다.

**진단 중 확인한 사실:**
- 플레이어 항목은 준비 직후 시각이 520/600(프레임 26)이고 속도가 0이다. 그래서 첫 요청은 t26이고, 첫 재생은 26 → 0 탐색 뒤에 시작한다. 두 프레임 타이밍 구성에서 같았다. 이유는 확인하지 않았다.
- 다시 재생(대조)에서는 프레임 2가 요청되지 않는 경우가 있었다(`…013848Z`). 이때 받은 소스는 모두 요청 시각과 맞았다. 요청 빠짐이 항상 소스 불일치를 동반하지는 않는다(관찰 1건).

**시각 검사의 해석 확인:**
- 소스 픽셀 코드와 movie time을 함께 기록한 진단 요청 2,585건에서 두 신호가 모두 맞음 2,543건, 모두 틀림 42건, **엇갈림 0건**이었다(`results/e2-diag-source-*`).
- 이 composition에서는 movie time이 받은 소스 프레임의 합성 시각을 나타낸다.
- 그래도 시각 검사는 소스 픽셀 검사를 대신하지 않는다. 자동 검사는 비디오 출력·레이어·디코딩한 내보내기에서 소스 코드를 따로 판정하고, 시각 불일치는 별도 오류로 남긴다.

**상태:** 재현되지 않았고 원인이 확인되지 않았다. **고쳐지지 않았다.** 정당한 수정 근거가 없어 수정하지 않았다. 다음 실패에서는 위 진단 필드(요청 순서, movie time 값, 사건 기록)가 남는다(자동 검사의 `staleSourceDetail`, `firstRequests`). 구조적 선택지는 아래와 같다.
- (a) 시각 불일치를 감지하면 그 요청만 별도 디코더로 정확한 소스 프레임을 얻는다.
- (b) 합성기가 소스 디코딩을 직접 관리한다.
- (c) 편집용 중간 코덱으로 미리 변환한다(소유자 승인 필요).

## 7. 한계와 계획과의 차이

- **승인 범위와 계획 문서의 관계:**
  - [EXPERIMENT-PLAN.md](../../docs/EXPERIMENT-PLAN.md) §6은 E2의 더 넓은 제안이다(약 60 s, 컷 5~8개, 소스 30~60 s).
  - 이번 작업 승인 A-003이 정한 범위는 최종 타임라인 10 s다. 10 s는 승인된 범위이며, 계획에서 임의로 줄인 것이 아니다.
  - 그 범위에서 정한 실험 구성은 컷 4개, 소스 6~8 s다.
  - 계획 문서 항목 중 이번에 하지 않은 것:
    - LPCM 대조 출력
    - 컷별 화면 플래시(대신 클립 오디오 클릭 위치와 소스 프레임 대응을 따로 확인했다)
    - 시간에 따른 메모리 곡선, 길이가 다른 두 내보내기의 메모리 비교
- **편집 범위:** 비디오 트랙 1개, 빈틈 없는 하드 컷만 다룬다(실험 범위). 겹침·전환·여러 트랙·빈 구간·속도 변경은 다루지 않았다.
- **fixture:** 생성 영상이다. 실제 촬영 4K(복잡한 움직임, 다른 코덱·GOP 구조, 가변 프레임레이트)는 시험하지 않았다. 질감은 넣었지만 실제 영상과 압축 특성이 다르다.
- **프리뷰:** 수정 전 현상은 프레임 타이밍 변경 뒤 원래 재현 조건에서 나타나지 않았다(관찰된 완화, §5.3). 해결되지 않은 소스 프레임 실패 1건이 있다(§5.4). 완화는 30 fps CFR 소스·비디오 트랙 1개 조건에서만 관찰했다.
- **메모리(후속 과제):** 4K 프로세스 최대 RSS가 약 1.0~1.5 GB였다. 누수라고 판단하지 않았다. 프리뷰 프로세스 footprint는 검사 순서를 따라 올라갔고(170 → 745 MiB, `…012403Z`), 수렴 여부는 확인하지 않았다. 장시간 추세는 측정하지 않았다(E3 범위).
- **재생 중 화면 프레임:** 재생 중 실제로 표시된 프레임 수는 관찰할 수 없다. 레이어 표시 버퍼는 일시정지 중에만 읽힌다.
- **내보내기 속도:** 수정 전 실행은 실시간의 0.87~0.91배, 수정 후 1회는 1.28배였다(부하 있음, 원인 미확인). 기준이 없어 판정하지 않는다.
- **진단 fixture:** 재정렬 끈 비교 fixture는 진단 전용이다. 입력 제한(B프레임 금지)이나 변환 요구가 아니다.
- **실험 허용치**(제품 기준 아님): 상자 위치 ±3 px, 배경 ±12, 클릭 onset ±48샘플(1 ms), 자막 흰 픽셀 표본 > 1000, 클릭 반응 막대 96 px, 레이어 다시 재생 정지 프레임 ±1.
- **결과 파일의 경로:** 결과 JSON의 저장소 절대 경로는 `<repo>`로 바꿔 기록한다. 이 처리 전에 쓴 `e2-run-2026-10-10T003456Z.json`, `…003600Z.json`은 같은 치환만 적용했고 다른 내용은 바꾸지 않았다.
- **E1 공유 코드 변경:** 접근 수준과 product 선언만 바꿨다. E1 회귀로 빌드, 단위 테스트 9개, `e1 compositor`를 다시 실행했다. `e1 all`(경로 A·출력 보호)은 동작 변경이 없어 다시 실행하지 않았다.
- 앱 번들 없음, 대체 API(macOS 27 deprecation) 미사용, Swift 6 언어 모드 미시험은 E1과 같다.

## 8. 소유자 관찰 (소유자 보고, 2026-10-10 한국 시각)

소유자가 알려 준 **정성적 통과**다. 자동 프레임 정확도 증거가 아니다. §5.4의 해결되지 않은 소스 프레임 실패를 해소하지 않는다.

## 10. 다음 단계 판단

- 4K에서 실제 소스 영상 디코딩·합성을 거친 컷 편집이 다음에서 독립 기대값과 같았다: 오프라인 합성기, 내보내기 디코딩, 일시정지 탐색(레이어 포함), 재생 중 탐색, 그리고 수정 후의 0→끝 재생과 다시 재생.
- 수정 전 구성에서 직전 소스 버퍼가 다시 전달되는 것을 관찰했다. 프레임 타이밍을 비디오 트랙에서 얻도록 바꾼 뒤, 원래 fixture의 실패 위치에서 다시 나타나지 않았다(관찰된 완화, AVFoundation 내부 원인은 추정).
- **남은 것:**
  - §5.4의 해결되지 않은 소스 프레임 실패(재현되지 않음, 원인 미확인). 이 정확도 결함이 남아 있는 동안 E2를 완료로 표시하지 않는다.
  - 소유자 화면 관찰은 정성적 통과로 보고되었다(§8). 프레임 정확도 판정을 대신하지 않는다.
  - 수정의 일반성(가변·다른 프레임레이트, 여러 트랙)은 시험하지 않았다.
- E2는 완료가 아니다. 이 결과는 4K 제품 지원·3시간 지원을 입증하지 않는다. E3(길이 확대)와 P-003 판단은 별도 승인 사항이다.
