# E1 — FHD 통합 실험 (E1-a 헤드리스 내보내기, E1-b AVPlayer 프리뷰)

> **상태 (2026-10-10): E1 완료 — 합의된 범위(시험한 Mac 한 대에서의 짧은(10초) FHD 통합 실험)에 한한다.** E1-a 실행 완료(작업 승인 A-001). E1-b(작업 승인 A-002): 2026-10-09 **소유자 관찰에서 프리뷰 화면이 검게 나와 실제 시각 표시는 실패**했다(§6.6, 기록 유지). 원인을 확인해 수정했고 표시 경계 회귀 검사를 추가했다. 2026-10-10 수정된 창의 소유자 재확인은 **정성적 통과**(§8.2, 픽셀·샘플 단위 측정 아님). 소유자가 끝 프레임 유지(D-018)와 E1 완료 기준을 정했고, 구현·자동 검사(§6.8) 뒤 끝 프레임 소유자 재확인도 정성적 통과했다(§8.4). 높은 부하의 프레임 누락 등 후속 과제는 미해결로 남는다(§10). 제품 준비 상태·4K·3시간 지원을 뜻하지 않는다.
> 이 디렉터리의 코드는 버리는 실험 코드이며 제품 코드가 아니다. Swift + AVFoundation 사용은 잠정이며 P-003 승인이 아니다.
> fixture 설정(10초, 1920×1080, 30fps, SDR, H.264/AAC + LPCM 대조, 32밴드)은 실험용이며 제품 한계·사양이 아니다(O-03, O-04, O-05).
>
> **이 실험이 보여 주지 않는 것:** 실제 화면 픽셀과 소리·화면 동기의 측정값(소유자의 정성적 관찰만 있음), 재생 중 화면에 실제 표시된 프레임 수, 제품 준비 상태, 4K 지원, 3시간 지원.

## 2. 재현 명령

`experiments/e1-fhd` 디렉터리에서 실행한다(두 실행기 모두 다른 위치에서는 거부한다).

```sh
cd experiments/e1-fhd
swift build -c release                         # Release 빌드 (경고 0개 확인)
swift test                                     # 단위 테스트 9개 (Debug)
/usr/bin/time -l .build/release/e1 all         # 헤드리스: fixture → 분석 → 렌더 → 내보내기 A → 합성기 오프라인 → 내보내기 B → 보호 검사
/usr/bin/time -l .build/release/e1preview auto # 실제 AVPlayer 재생 자동 검사(창 없음, volume 0, 약 1분 40초) — 비디오 출력 경로
.build/release/e1preview present               # 표시 경계 회귀 검사: AVPlayerView 안 AVPlayerLayer(창이 잠깐 뜸, 약 20초)
.build/release/e1preview present --negative-control   # 대조: 수정 전 구성(빈 비디오 트랙)에서 위 검사가 실패하는지
.build/release/e1preview frames                # 창 부착 재생 프레임 계수(창이 잠깐 뜸, 약 1분 30초). §6.7
.build/release/e1preview diagnose              # 검은 화면 진단(창이 잠깐 뜸)
.build/release/e1 compositor --path-a-run <실행 ID>    # 합성기 경로 검사만 재실행(경로 A는 지정 실행의 출력을 디코딩)
.build/release/e1preview window --case c1-baseline   # 소유자 관찰용 창(소리 켬). §8
```

- `e1 all` → `results/e1-run-<UTC 시각>.json`, 출력은 `artifacts/runs/<UTC 시각>/`. 옵션 `--timing-reps N`, `--cancel-reps N`(기본 3).
- `e1preview auto` → `results/e1b-preview-<UTC 시각>.json`. `e1preview`는 `e1`이 만든 fixture를 쓰고, 디스크 해시가 정의에서 다시 만든 해시와 다르면 중단한다.
- `e1preview window` 종료 시 → `results/e1b-window-<케이스>-<UTC 시각>.json`(그 세션의 표시용 전달 프레임 요약).
- 각 내보내기 전에 실험 소유 산출물(`artifacts/` + `.build/`)이 2 GiB − 128 MiB를 넘으면 `budgetExceeded`로 중단한다.
- 모든 결과 JSON에 소스 트리 해시(Package.swift, Sources, Tests의 .swift 파일별 SHA-256과 전체 해시)와 실행 파일 SHA-256을 기록한다. 소스가 아직 커밋되지 않았으므로 Git HEAD 대신 이 값으로 결과를 구현에 귀속한다.

## 4. 구현 동작

### 4.1 시간 모델, 분석, 렌더링 (E1-a, 변경 없음)

- `ClipPlacement`: `t ∈ [t_start, t_start + d)`이면 `s = s_in + (t − t_start)`, 밖이면 신호 없음. 시각은 모두 `CMTime` 유리수이며, 프레임 시각은 `CMTime(n, 30)`이다.
- 스펙트럼은 `TimelineState.selected` 원본 파일만 분석한다. Hann 4096샘플 후행 창 `[s − 4096, s)`, hop 400(1/120 s), 40 Hz~16 kHz 로그 32밴드, 밴드 값은 [−80, 0] dB를 [0, 1]로 대응, 막대 높이 `round(값 × 480)` px. 채널은 (L+R)/2이며 실험 고정값이다(O-12 미결정).
- 렌더러는 불변 상태만 가지며 호출마다 CGContext·CTLine·색 공간을 새로 만든다. 여러 스레드에서 동시에 호출해도 된다(컴파일러가 확인한 `Sendable`).

### 4.2 두 내보내기 경로

| | 경로 A — 직접 writer (E1-a) | 경로 B — 공유 합성기 (E1-b) |
| --- | --- | --- |
| 비디오 공급 | writer의 비디오 공급 블록이 `FrameRenderer.render(frame: n)`을 직접 호출해 writer 풀 버퍼에 그림 | `AVAssetReaderVideoCompositionOutput` + 프리뷰와 같은 `AVVideoComposition`/`E1Compositor`가 만든 프레임을 writer에 넣음 |
| 프레임 시각 | 코드가 `CMTime(n, 30)`을 정함 | 합성 엔진이 `frameDuration = 1/30`, 빈 비디오 트랙의 시간 축으로 요청 시각을 정함 |
| 오디오 | 두 경로 동일: composition(S 트림·오프셋 + U)을 `AVAssetReaderAudioMixOutput`으로 읽음 | |
| 출력 보호 | 두 경로 동일: 사전 검사 → 같은 디렉터리 임시 → 재열기 검증 → `RENAME_EXCL` 승격 | |
| 공유하는 것 | `FrameRenderer`, `TimelineState`, `SpectrumCache` | 위 + `E1Compositor`, `AVVideoComposition`(프리뷰와 같은 객체 구성 코드 `CompositionBuilder`) |

경로 B는 프리뷰와 같은 합성기 경로를 실제로 실행한 내보내기다. 출력 보호 검사(P1~P11)와 시간 측정(M1)은 경로 A로만 실행했다.

### 4.3 프리뷰 (E1-b)

- **composition**: 오디오 트랙(S, U)과 **운반용 비디오 트랙**을 둔다. 비디오 트랙은 생성 fixture `artifacts/fixtures/carrier-160x90-10s.mov`(160×90 검은 화면, H.264, 300프레임, n/30)의 실제 샘플로 [0, 10 s)를 채운다. 합성기는 이 픽셀을 쓰지 않고(`requiredSourceTrackIDs = []`) 모든 픽셀을 렌더러가 만든다. `AVMutableVideoComposition`에 `customVideoCompositorClass = E1Compositor`, `frameDuration = 1/30`, `renderSize = 1920×1080`, `sourceTrackIDForFrameTiming = kCMPersistentTrackID_Invalid`, 명령 1개([0, 10 s))를 둔다. 프리렌더된 내보내기 파일은 재생하지 않는다.
  - 처음 구현은 **빈 구간만 있는 비디오 트랙**이었다. 이 구성에서는 `AVPlayerLayer`가 아무것도 표시하지 않았다(§6.6). 지금은 합성기 composition을 만들 때 운반 영상이 없으면 `CompositionBuilder`가 오류를 낸다(진단 재현용 옵션만 예외).
  - 운반 영상은 인코더 출력의 비트 재현성이 보장되지 않으므로 없을 때만 만들고 해시를 기록한다(`0a0c1e45…f474`). 원본처럼 보호 대상에 넣었다(경로 B 사전 검사, 해시 전후 비교).
- **끝 프레임 유지**(D-018): 합성 명령에 타임라인 프레임 격자에서 구한 마지막 유효 프레임을 넣고, 합성기는 그 뒤 시각(끝 시각 10.0 s)의 요청에 마지막 유효 프레임을 그린다. 빈 타임라인은 composition 구성에서 거부한다(§6.8).
- **합성 명령** `E1Instruction`: `containsTweening = true`(엔진이 프레임을 재사용하지 않게), `requiredSourceTrackIDs = []`(소스 프레임 불필요), 렌더러와 기록 객체를 운반한다(모두 불변 또는 잠금 보호).
- **합성기** `E1Compositor`: 요청은 직렬 큐에서 하나씩 처리한다. 출력 버퍼는 요청마다 렌더 컨텍스트 풀에서 새로 받고, `finish` 이후에는 건드리지 않는다. 렌더 컨텍스트와 세대 번호는 잠금으로 보호한다. `cancelAllPendingVideoCompositionRequests`는 문서 요구대로 세대 번호를 올린 뒤 큐가 빌 때까지 블록하며, 대기 중이던 요청은 `finishCancelledRequest`로 끝낸다. 합성 시각은 가장 가까운 n/30으로 바꾸고, 정확히 n/30인지 기록한다.
- **재생**: `AVPlayer(playerItem:)`, `automaticallyWaitsToMinimizeStalling = false`. 자동 검사는 `volume = 0`(§6.4 참조), 창 모드는 소리를 켠다.
- **관찰 장치**: `AVPlayerItemVideoOutput`(BGRA 요청)을 4 ms 간격으로 폴링해 표시용으로 전달된 프레임을 받는다. 선택 소스 트랙에만 `MTAudioProcessingTap`(PreEffects)을 붙여 재생 파이프라인이 처리한 샘플에서 클릭 onset을 기록한다.
- **창 모드**: 앱 번들 없이 실행 파일에서 `NSApplication`(activation policy regular) + `NSWindow` + `AVPlayerView`(inline 컨트롤, 프레임 이동 버튼)를 띄운다. 왼쪽 아래 진단 라벨은 **플레이어 시각** 기준 프레임 번호다(화면에 실제로 표시된 프레임과 다를 수 있음).

API 확인(설치된 macOS 27.0 SDK): `AVVideoCompositing`의 `newPixelBuffer`, `finish(withComposedVideoFrame:)`, `sourceFrame(byTrackID:)`, `AVPlayerItemVideoOutput`의 `init(pixelBufferAttributes:)`·`copyPixelBuffer(forItemTime:itemTimeForDisplay:)`, writer의 `requestMediaDataWhenReady` 등은 `API_DEPRECATED(..., macos(…, 27.0))`이다. 대체 API(`CVReadOnlyPixelBuffer` 계열, receiver의 async `append`)는 macOS 26/27 이상이다. 배포 대상 macOS 15에서는 기존 API를 써도 deprecation 경고가 나지 않으며, 대체 API 경로는 실행하지 않았다. `MTAudioProcessingTapCreate`는 deprecated가 아니다.

## 5. E1-a 재검토 결과와 수정 (E1-b 착수 전)

- **증명하지 않는 것:** 재생 중 움직이는 막대의 화면 표시, 창 서버 합성 후의 실제 화면 픽셀, 창 크기에 맞춘 축소 결과, 디스플레이 색, 소리와 화면의 체감 동기. 이 항목은 소유자 재확인이 필요하다(§8.2 — 2026-10-10 소유자 보고로 정성적 통과, 측정 아님).
- `AVPlayerView`의 내부 레이어 구조는 공개 API가 아니다. 검사는 레이어 트리에서 `AVPlayerLayer`를 찾지 못하면 실패로 기록한다.

### 6.8 끝 프레임 유지 (D-018, 2026-10-10)

**구현:**
- `FrameGrid.lastValidFrame(duration:frameDuration:)`: 프레임 n은 n·frameDuration에 시작하고, 시작 시각이 [0, duration) 안인 프레임만 유효하다. 마지막 유효 프레임 = ceil(duration / frameDuration) − 1(정수 연산). 10 s·1/30 s → 299. 299를 코드에 적지 않았다.
- `CompositionBuilder.build`: 타임라인에서 마지막 유효 프레임을 구해 합성 명령(`E1Instruction.lastValidFrame`, 불변)에 넣는다. 길이가 0 이하이거나 수치가 아니면 **빈 타임라인으로 거부**한다(오류 `empty timeline`).
- `E1Compositor`: 합성 시각의 프레임 번호 n을 `contentFrame(n) = min(max(n, 0), lastValid)`로 바꿔 렌더한다. 끝 시각 10.0 s(n = 300) 요청은 프레임 299를 그린다. 합성기 기록에 요청 프레임(`frame`)과 렌더 프레임(`renderedFrame`)을 모두 남긴다.
- 바뀌지 않은 것: 타임라인 길이(10 s), 비디오 composition 명령 범위, 내보내기 길이(300프레임, 0~299), 오디오 composition. 오디오를 반복·연장하지 않는다. 렌더러(`FrameRenderer`)도 그대로다.

**검토:**
- **자막·스펙트럼 상태:** 끝에서는 프레임 299의 내용이 그대로 보인다. 자막은 239에서 끝나므로 없음. 스펙트럼은 프레임 299의 값이 멈춘 채 보인다: c1은 8~10 s가 무음이라 막대 0, c2·c3·c4는 299에 톤이 있어 막대가 402~406 px로 남는다. 소리는 끝에서 멈추므로, c2~c4에서는 소리 없이 막대가 서 있는 화면이 된다. D-018의 "유지"를 그대로 따른 결과다.
- **탐색:** 끝으로 탐색하든, 끝까지 재생해 멈추든 요청 시각은 10.0 s이고 같은 규칙으로 299를 그린다. 끝에서 한 프레임 뒤로 가면 시각 299가 되고 내용도 299이므로 화면이 바뀌지 않는다. 한 번 더 가면 298이다.
- **취소·동시성:** 추가한 상태가 없다. `lastValidFrame`은 명령의 불변 `let`이고, `contentFrame`은 순수 함수다. 요청 처리 직렬 큐, 세대 번호, `cancelAllPendingVideoCompositionRequests`의 블록 동작은 바뀌지 않았다. strict concurrency(complete)에서 경고 0개.
- **내보내기:** 경로 B의 reader는 [0, 10 s) 범위만 요청하므로 끝 유지가 적용되지 않는다. C1이 이를 검사한다(`renderedFrame ≠ frame`이면 실패).
- **독립 기대값:** `Expect.lastValidFrame = 299`는 손으로 유도한 리터럴이다(10 s × 30 fps, 반열린 구간). 검사의 기준 해시는 `Expect.contentFrame(n)`을 렌더러로 직접 그린 값이며, 구현의 `FrameGrid`나 합성기 매핑을 쓰지 않는다.

## 7. 실패·한계·열린 질문

- **화면 표시 실패(수정 전)와 수정 후 재확인**: 수정 전 창은 소유자 관찰에서 검은 화면이었다(§6.6). 수정 후 자동 검사는 `AVPlayerLayer` 표시 버퍼까지만 확인한다. 수정 후 창의 실제 화면 모습과 귀로 듣는 동기는 소유자가 정성적으로 통과를 보고했다(§8.2). 픽셀·샘플 단위로 측정한 값은 아니며, 따로 관찰되지 않은 항목이 남아 있다(§8.3).
- **이전 검사의 한계**: 비디오 출력(`AVPlayerItemVideoOutput`) 기반 검사는 화면 표시 경로와 독립적으로 통과할 수 있음이 드러났다. 표시 판단에는 L1과 소유자 관찰을 쓴다.
- **끝 프레임**: D-018(P-007 채택)에 따라 끝에서 마지막 유효 프레임(299)을 유지하도록 고쳤다(§6.8). 소유자 화면 재확인은 정성적 통과했다(§8.4). 끝에서는 프레임 299의 스펙트럼이 멈춘 채 보이며, c2~c4에서는 소리 없이 막대가 서 있다.
- **부하 시 프레임 건너뜀**(§6.2, §6.7) — **E1 차단 요소 아님, 안정화·성능 단계의 미해결 후속 과제**(소유자 결정 2026-10-10): 부하 평균 6~7.6에서 재생 파이프라인이 합성 요청 자체를 건너뛴 실행이 있었다. 부하 평균 2.9~4.8에서는 재생 13회 모두 누락 0으로 재현되지 않았다. 높은 부하에서의 원인·빈도와 재생 중 실제 표시 프레임 수는 확인되지 않았다. 반복 재생 footprint는 한 실행에서 127.7 → 142.0 MiB로 올랐고, 2026-10-10 실행에서는 135.9 → 119.7 MiB로 내려갔다. 장시간 추세는 측정하지 않았다.
- **음소거 시 탭 동작**(§6.4): 제품에서 음소거 중 스펙트럼을 재생 오디오에서 계산한다면 문제가 될 수 있다. 이 실험의 스펙트럼은 원본 파일 분석 캐시를 쓰므로 영향이 없다.
- **경로 B 메모리**: 경로 B의 최대 footprint가 경로 A보다 약 60 MiB 높다. 장시간 추세는 E3 범위다.
- **출력 보호는 경로 A로만 검사**: 경로 B는 같은 `Exporter.run`(사전 검사·임시·승격·정리)을 쓰지만 취소·실패 검사는 실행하지 않았다.
- **E1-a 한계 유지**: 원본 이름 변경으로는 실패가 재현되지 않음(P5), 디스크 부족 시뮬레이션 안 함, 덮어쓰기 승인 경로 없음, 강제 종료 후 임시 정리 없음, AAC priming을 무시하는 플레이어 미확인, 대체 API 미사용, 분석 결과 전체를 메모리에 올림.
- **앱 번들 없음**: 창 모드는 번들 없는 실행 파일에서 `NSApplication`을 띄운다. 이 실험에서는 동작했지만, 번들 앱과 같은지(권한·메뉴·Dock 동작)는 확인하지 않았다.
- **측정 조건**: 개발 기기 1대, 다른 프로세스 부하 있음(§6.5 6~7.6, §6.7 2.9~4.8). 일반화하지 않는다.
- **열린 질문**: (1) 끝 위치 표시 정책은 D-018로 정해졌다(이 실험의 고정 길이 타임라인 기준. 편집 중 길이가 바뀌는 경우는 다루지 않았다). (2) 판정 허용치는 실험용이며 제품 기준(O-11)이 아니다. (3) 후행 창 정렬과 가운데 정렬 중 선택. (4) 화면 캡처 기반 자동 검증을 원하면 화면 기록 권한 부여가 필요하다(전역 설정 변경, 소유자 승인 필요).
